---
title: Configure environment variables
description: Change the settings a service reads at startup, or let multiple services read the same set of shared variables.
---

Open the service's **Variables** tab and click **Edit**. When you're done, click **Review changes** at the bottom of the page and apply them. Variables set directly on the service take effect when new replicas start. If a value comes from a shared config file or secret, edit the source and check which services need a restart.

## Before you begin

- You have a service and permission to edit it. If the service is marked as managed by Helm, Argo CD, or Flux, make changes in the original values or Git repository.
- You know the variable names and values the app needs, such as `APP_URL` or `LOG_LEVEL`. These settings are environment variables for the container at runtime. For [Git deployments](../deploy/git.mdx), edit build variables in the build settings.
- Store passwords and API keys in secrets. Values under **Set directly** appear in the service settings. When you choose **Secret** for shared variables, only people with permission to read secrets can reveal the values.

## Edit variables for this service

<Steps>
<Step>

### Open the editor

Open the project, select the service, then open **Variables** → **Edit**. Under **Set directly**, edit a name or value, or click **Add a variable** to add a row. If the service has multiple containers, choose which container should read the new variable.

![Environment variable editor: each row under Set directly has an editable name and value, with Add variable below](../images/shots/variables-edit.avif)

Paste multiple lines of `NAME=value` into the name field to add several variables at once. For a single container, you can also switch to the `.env` editor:

```dotenv
APP_URL=https://app.example.com
LOG_LEVEL=info
```

The `.env` editor supports quotes, `export`, and `#` comments. Removing an existing line from the editor marks that variable for removal.

</Step>
<Step>

### Review and apply

Check the rows marked **New**, **Changed**, or **Removed**, then click **Review changes** at the bottom of the page. Confirm the containers, variable names, and any other pending settings, then apply the changes.

Editing variables directly updates the service's replica template. Long-running services, such as Deployment and StatefulSet, replace their replicas with the new settings. CronJob reads the new values starting with its next run.

</Step>
<Step>

### Confirm the app reads the new settings

Return to **Overview** and wait for the replicas to be ready. Then check the app's behavior or **Logs** to confirm the change. For example, check whether newly generated links use the new `APP_URL`. The environment variable list shows the saved settings.

</Step>
</Steps>

Before applying, click **Discard** to discard the draft changes. To undo changes you've already applied, restore the previous values, then review and apply again.

## Edit values from config files or secrets

**From config files and secrets** lists the source of each variable. Click a source name to open its editor. For a secret, click **Reveal values** to read the current values. You can also enter new values without revealing the old ones. Use YAML to edit config file data marked **Binary**.

First, check **Read by** at the top of the editor. For example, if both `web` and `worker` read `app-config`, changing its values from the editor opened in `web` changes the source for both services. The list also includes services that mount the source as a file.

After editing a key or clicking **Add key**, submit the changes for review. When you open the source editor from a service page, it adds your changes to that service's draft. You still need to click **Review changes** at the bottom of the page and apply them. Opening the same source from the project's **Settings** takes you directly to the change review instead.

### Let running services read the new values

After you edit a config file or secret, environment variables in containers that are already running keep their old values. The change review lists services that need a restart and services that Reloader may restart automatically.

- To handle restarts manually, click **Restart** for each service that needs the new values, then check that its replicas are ready.
- To handle restarts automatically, open the service's **Settings** → **Compute**, enable **Restart when its config files or secrets change**, then review and apply. Stakater Reloader must be running in the cluster. The option alone restarts nothing.
- Once enabled, the service restarts when the source changes, whether you edit it in Zeabur or with another tool. If every service that reads the source has this option enabled, they'll restart together.

**May still use the old value until restarted** means the source changed after a replica started. Expand the notice to see which replicas are affected. A completed Job doesn't run again when its source changes.

## Create shared variables and connect them to a service

<Steps>
<Step>

### Add a set of shared variables

Open **Shared variables** in the project's **Settings** and click **Add shared variables**. Enter a **Name**, choose **Secret** or **Plain text** under **Store values as**, then enter one `NAME=value` per line under **Variables**.

Click **Review changes**, confirm the changes, then click **Create**. This only creates the shared variables. The service doesn't read them yet.

</Step>
<Step>

### Choose which keys the service reads

Return to the service's **Variables** tab and click **Use shared variables**. Select the set you just created. If the service has multiple containers, select a container too.

- **All keys**: Every key becomes an environment variable, including keys added later.
- **One key**: Select a **Key**, then set the **Variable name** in the container. For example, read `api-token` as `API_TOKEN`.

This side panel has its own **Review changes** and apply steps. It doesn't add changes to the draft at the bottom of the service page. After you apply, long-running services replace their replicas, and the new replicas read these variables.

</Step>
<Step>

### Confirm the service reads the source

Check the source name under **From config files and secrets** in the service. Then return to the project's **Settings** → **Shared variables** and confirm that the service appears under **Used by**. Once the new replicas are ready, check the app's settings.

</Step>
</Steps>

## Do the same with kubectl

Environment variables are stored in the workload's replica template. Shared variables are standard config files or secrets. Zeabur doesn't store a separate copy of this data. The examples below use project `demo` and service `web`.

Setting and removing a variable directly changes the container's `env`:

```sh
kubectl -n demo set env deployment/web NODE_ENV=production
kubectl -n demo set env deployment/web NODE_ENV-
```

Shared variables are config files or secrets with the label `zeabur.com/shared-variables: "true"`. The project's **Settings** → **Shared variables** lists them based on this label:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: demo
  labels:
    zeabur.com/shared-variables: "true"
data:
  APP_URL: https://app.example.com
  LOG_LEVEL: info
---
apiVersion: v1
kind: Secret
metadata:
  name: app-secrets
  namespace: demo
  labels:
    zeabur.com/shared-variables: "true"
type: Opaque
stringData:
  api-token: change-me
```

How a service reads shared variables is defined on the container. **All keys** uses `envFrom`, and **One key** uses `valueFrom` in `env`. **Restart when its config files or secrets change** sets the annotation `reloader.stakater.com/auto: "true"` on the workload itself, not its replica template. Only Deployment, StatefulSet, and DaemonSet support this option:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: demo
  labels:
    app.kubernetes.io/name: web
  annotations:
    reloader.stakater.com/auto: "true"
spec:
  replicas: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: web
  template:
    metadata:
      labels:
        app.kubernetes.io/name: web
    spec:
      containers:
        - name: web
          image: nginxinc/nginx-unprivileged:1.29
          env:
            - name: NODE_ENV
              value: production
            - name: API_TOKEN
              valueFrom:
                secretKeyRef:
                  name: app-secrets
                  key: api-token
            - name: LOG_LEVEL
              valueFrom:
                configMapKeyRef:
                  name: app-config
                  key: LOG_LEVEL
            - name: POD_NAME
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name
          envFrom:
            - configMapRef:
                name: app-config
```

To turn automatic restarts on or off, use annotate. This doesn't replace replicas:

```sh
kubectl -n demo annotate deployment web reloader.stakater.com/auto=true
kubectl -n demo annotate deployment web reloader.stakater.com/auto-
```

If you change a shared source without Reloader, restart the services that read it manually:

```sh
kubectl -n demo rollout restart deployment/web
```

After you remove Zeabur, Kubernetes continues to inject these variables into containers. Reloader is an independent component and continues to restart services based on the annotation.

## Verify the result

On the **Variables** tab, variables set directly appear under **Set directly**. Variables read from shared sources appear under **From config files and secrets**, along with their source names. In the project's **Settings** → **Shared variables**, **Used by** lists the services that read each source.

Use kubectl to check the settings in the replica template and the actual value in the container:

```sh
kubectl -n demo get deployment web -o jsonpath='{.spec.template.spec.containers[0].env}'
kubectl -n demo get configmap,secret -l zeabur.com/shared-variables=true
kubectl -n demo exec deploy/web -- printenv NODE_ENV
```

If `printenv` prints the new value, the replica started with the new settings. If it prints the old value, wait for the new replica to be ready, or restart it using the steps above.

## Troubleshooting

| Message or result | What to do next |
| --- | --- |
| **Another variable already uses this name** or **A config file, secret, or Kubernetes already sets this name** | Edit the variable at its source, or choose another name. Only one value takes effect for variables with the same name in a container. |
| **Use shared variables** is missing | Create at least one set of shared variables in the project's **Settings** first. This button also doesn't appear while you're editing the service's variables or when another tool manages the service. |
| **You don't have permission to read secrets, so values are hidden.** | Revealing secret values requires permission to read secrets, which is separate from permission to edit the service. See [Permissions](../reference/permissions.mdx). |
| The shared source changed, but the app still uses old values | Restart the services that read it. If automatic restarts are enabled, open the service's **Settings** → **Compute** to check whether Reloader is running. |
| The changes are marked as expired | Review the current source and values again, then apply the new changes. |

## Stop reading variables or remove settings

For a variable set directly, click its row's remove button in **Edit**, then review and apply.

For variables imported as a set, select **Stop reading** on the source row, then review and apply. This disconnects the service from the source but keeps the shared source.

For a variable that reads a single key, select **Remove variable** next to the source, then review and apply. This removes only the variable from the service. The shared source and all its keys remain.

To delete an entire set of shared variables, first confirm that **Used by** is empty in the project's **Settings** → **Shared variables**. Then open the corresponding ConfigMap or Secret in the project's **Objects**, click **Delete** under **YAML**, review, and apply. If a service still reads keys from this source, new replicas fail to start because they can't find the source.

If the app's public URL changes, also check its [domains](./domains.mdx) and variables such as `APP_URL`. Use [maintenance mode](./maintenance.mdx) to handle visitor traffic during maintenance.
