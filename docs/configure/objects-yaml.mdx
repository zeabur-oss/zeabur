---
title: Create and edit objects with YAML
description: Paste YAML in a project to create any Kubernetes object, or edit or delete existing objects from the YAML view.
---

Use YAML for settings the forms don't cover. On the project's **Objects** page, click **Create** and paste YAML to create a ConfigMap, Deployment, Service, or any custom resource the cluster provides. To edit or delete an existing object, open it, switch to the YAML view, and click **Edit** or **Delete**. Every write opens a review screen before you confirm and apply it.

## Before you start

- You need permission to create or modify that kind of object in the project. The form warns you if you don't have enough permissions, and the review checks with the cluster again.
- Zeabur only creates objects in the project's namespace. Use kubectl for cluster-wide objects, such as Namespace and ClusterRole.
- Objects managed by Helm, Argo CD, or Flux can't be edited or deleted here. Make changes in that tool instead. Restarting is an exception. See [Restart, roll back, and pause services](./restart-rollback.mdx).

## Create objects from YAML

<Steps>
<Step>

### Open the editor

Open the project and click **Create** on the **Objects** page, or choose **Create in demo…** in search. The screen title is **Create in demo**.

</Step>
<Step>

### Enter YAML

Paste one or more documents into **YAML to create**, separated by `---`. If you're not sure what to write, click **Insert example** and choose a kind from **Common kinds**, **Custom resources**, or **Other kinds you may create** to insert a template for that kind of object.

The following YAML creates a ConfigMap, a Deployment that reads it, and a Service:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: hello-config
  namespace: demo
data:
  MESSAGE: hello
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
  namespace: demo
  labels:
    app.kubernetes.io/name: hello
spec:
  replicas: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: hello
  template:
    metadata:
      labels:
        app.kubernetes.io/name: hello
    spec:
      automountServiceAccountToken: false
      securityContext:
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: hello
          image: nginxinc/nginx-unprivileged:1.29
          ports:
            - containerPort: 8080
          envFrom:
            - configMapRef:
                name: hello-config
          securityContext:
            allowPrivilegeEscalation: false
---
apiVersion: v1
kind: Service
metadata:
  name: hello
  namespace: demo
  labels:
    app.kubernetes.io/name: hello
spec:
  selector:
    app.kubernetes.io/name: hello
  ports:
    - name: http
      port: 8080
      targetPort: 8080
```

You can omit `namespace`. Zeabur fills in the current project.

</Step>
<Step>

### Check issues and creation order

The editor lists **N issues** beside the YAML. Click an issue to jump to its line. Fix these issues before reviewing changes:

- Invalid YAML or a missing `apiVersion`, `kind`, or `metadata.name`.
- A cluster-wide object, such as a Namespace.
- A `namespace` set to a different project.
- An object kind the cluster doesn't provide, such as a Certificate when cert-manager isn't installed.
- The same object defined twice.
- An object with the same name already exists. Creating objects doesn't modify existing ones. Use **Edit** to change an existing object.

**Created in this order** shows the order Zeabur uses: config files, secrets, disks, and ServiceAccounts first, then Services, workloads, and all other objects. This lets workloads read what they need when they start.

![Object editor for shop with three YAML documents and a creation order of ConfigMap, Service, and Deployment on the right](../images/shots/objects-create.avif)

</Step>
<Step>

### Review and create

Click **Review changes**, check the objects to create, and click **Create 3 objects**.

![Review screen for creating 3 objects in shop, showing the creation order, services that will start, and two notices](../images/shots/objects-create-review.avif)

</Step>
</Steps>

Kubernetes can't undo changes to multiple objects at once. If the cluster rejects an object, any objects already created remain. The screen shows **Created 1/3** and lists the objects **not attempted**. Choose **Delete the 1 object just created** to return to the previous state, or choose **Keep them**, fix the YAML, and create only the remaining objects.

## View objects

The project's **Objects** page lists all objects in the namespace by kind. Use **Filter objects** to find them by name. Objects generated by other objects have a **Generated** label and a source label such as **Created by Deployment**. Examples include ReplicaSets and replicas generated by a Deployment.

Click an object to see its status, **Conditions**, and YAML. To view a service's YAML, open the service's **Settings** and switch from **Settings** to **YAML** at the top.

Secret values appear as `(hidden)` in the YAML.

## Edit an object's YAML

<Steps>
<Step>

### Edit

Click **Edit** in the YAML view. The editor shows the current configuration in the cluster, and changes are written as entered. Leave secret values as `(hidden)` to keep them unchanged, or enter new values to change them.

</Step>
<Step>

### Review and apply

Click **Review changes**. The review screen shows which fields changed and whether the service will be interrupted. **Technical details** includes **YAML diff** and **Fields owned by**, which lists who last wrote each field, such as `kubectl` or `helm`. Confirm the changes, then apply them.

</Step>
</Steps>

Zeabur writes only the fields you changed. Before writing each field, it checks that the value in the cluster still matches the value when you started editing. If someone changed the same object while you were editing, applying fails. Reopen it and make the changes again.

Changes to cluster-maintained fields, such as `status`, `resourceVersion`, and `ownerReferences`, aren't written. Objects generated by other objects, such as replicas and ReplicaSets, can't be edited or deleted. Edit their owner instead.

If you change a field written by `kubectl apply`, the review screen warns you: **The next kubectl apply will revert … on hello**. Update your local YAML file too, or the next apply will overwrite the change.

## Delete objects

Click **Delete** in the YAML view. The review screen shows the effects of deleting the object. Confirm, then apply. Deletion can't be undone. Deleting a workload also deletes the ReplicaSets and replicas it generated.

## Do the same with kubectl

**Create** corresponds to `kubectl create` and fails if an object already exists. These commands use the `demo` project:

```sh
kubectl -n demo create -f hello.yaml
kubectl -n demo edit deployment hello
kubectl -n demo delete deployment hello
```

`kubectl create -f` creates objects in file order. Unlike Zeabur, it doesn't reorder them to put ConfigMaps and Secrets first.

Zeabur doesn't add any fields of its own when writing objects. You can continue using kubectl apply for objects managed by `kubectl apply`. Update your YAML files to match any fields you change in Zeabur.

## Verify the result

The **Objects** page lists the newly created objects. Workloads also appear in the project's service list, and **Overview** shows whether replicas are ready.

```sh
kubectl -n demo get configmap,deployment,service -l app.kubernetes.io/name=hello
kubectl -n demo get configmap hello-config
kubectl -n demo get deployment hello -o yaml
kubectl -n demo get deployment hello --show-managed-fields -o jsonpath='{.metadata.managedFields[*].manager}'
```

The first two commands confirm that the objects exist. The `-o yaml` output matches the YAML shown in Zeabur. The last command lists the programs that have written to this object, using the same data source as **Fields owned by** on the review screen.

## Troubleshooting

| Screen or result | What to do next |
| --- | --- |
| **Namespace … is cluster-wide. Zeabur only creates objects within a project.** | Create it with kubectl, or ask an administrator to do it. |
| **This cluster doesn't provide Certificate (cert-manager.io/v1).** | Install the component that provides this kind of object, or check `apiVersion` for typos. |
| **A Deployment named hello already exists. Creating objects doesn't modify existing ones.** | Use **Edit** on that object, or choose a different name. |
| **Created 1/3** | Check why the object was rejected. Choose **Delete the 1 object just created** or **Keep them**, then fix the remaining objects. |
| Editing or deleting says the object is managed by Helm, Argo CD, or Flux | Make the change in that tool's values or Git repository. |
| **Kubernetes manages this kind of object. To make changes, edit its owner.** | Another object generated this object, such as a replica. Edit its Deployment. |
| Applying says the object has changed | Someone changed it while you were editing. Reopen the YAML and make the changes again. |
