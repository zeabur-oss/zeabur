title: Adjust replicas, resources, and health checks
description: Set a service's replica count, CPU and memory, health checks, startup command, and whether containers can run as root.

When you finish this page, the service runs with the replica count, CPU, and memory you chose. Broken replicas restart on their own, and replicas that aren't ready get no traffic. All of these settings are on the service's **Settings** tab. After a change, select **Review changes** at the bottom of the page and apply it.

A replica is one running copy of the service. More replicas can handle more requests at once, and the others take over when one breaks.

## Tabs on a service page

Open a service to see these tabs at the top:

| Tab | What it's for |
| --- | --- |
| **Overview** | The service's current state, whether replicas are ready, and problems that need you. |
| **Logs** | The service's log output. |
| **Deployments** | A record of each change. Compare two versions or go back to an earlier one. |
| **Builds** | Only for services built from Git or an uploaded folder. Lists each build. |
| **Usage** | CPU, memory, and network usage. |
| **Networking** | Public domains and the private network. |
| **Variables** | Settings the service reads when it starts. |
| **Files** | Browse and edit files inside a replica. |
| **Settings** | Replicas, resources, health checks, disks, and security, which this page covers. |

For how to use the tabs, see [View logs, events, and usage, and open a terminal](./logs-terminal.mdx), [Restart, roll back, and pause services](./restart-rollback.mdx), [Add public domains and HTTPS](./domains.mdx), and [Configure environment variables](./variables.mdx).

## Before you start

- You need permission to edit the service. If Helm, Argo CD, or Flux manages the service, these fields are read-only. Make changes in the original values or Git repository.
- Changing any setting other than the replica count makes Zeabur OSS replace all replicas with the new settings. A service with only one replica may be unavailable for a few seconds during replacement.

## Compute resources

<Steps>
<Step>

### Adjust the replica count

Open the service's **Settings** → **Compute** and change **Replicas** (0 to 1000). Setting the count to 0 stops the service without deleting any configuration or data.

</Step>
<Step>

### Adjust CPU and memory

Enter **Reserved CPU**, **Maximum CPU**, **Reserved memory**, and **Maximum memory**. For example, reserve 0.25 CPU cores and 256 MiB of memory, with a memory maximum of 512 MiB.

- Reserved: The cluster sets aside this amount for each replica and uses it to pick a machine with room. Leave it blank to reserve nothing.
- Maximum: A container restarts when its memory goes over the maximum. It slows down when its CPU reaches the maximum. Leave it blank to set no maximum.

Below the fields, the form shows the CPU cores and memory of the **largest node** in the cluster. A node is one machine in the cluster. If the reserved amount is more than that, the replica fits on no machine.

![Compute resources in service settings, showing the replica count, reserved and maximum CPU and memory, and the largest node's resources below](../images/shots/service-compute.avif)

The **Size** you choose when creating a service from an image or Git sets the initial values for these fields:

| Size | CPU reserved | Memory reserved | Memory maximum |
| --- | --- | --- | --- |
| Small | 0.1 cores | 128 MiB | 256 MiB |
| Medium | 0.25 cores | 256 MiB | 512 MiB |
| Large | 0.5 cores | 512 MiB | 1 GiB |

</Step>
<Step>

### Review and apply

Select **Review changes** at the bottom of the page. The review screen shows how the replica count changes, whether the service will be interrupted, and whether the machines have room. Review the changes, then apply them.

![Review screen before changing web to 3 replicas](../images/shots/compute-review.avif)

</Step>
</Steps>

You can't change a job that runs once (a Job) under **Compute**. Use YAML instead.

Below **Compute**, there's also **Restart when its config files or secrets change**. See [Get new values into running services](./variables.mdx#let-running-services-read-the-new-values). Turning it on or off doesn't replace replicas.

## Health checks

Health checks tell the cluster whether a replica is working. Open the service's **Settings** → **Health checks** and configure each of the three checks separately:

| Check | Purpose |
| --- | --- |
| **Traffic check** | Only replicas that pass receive traffic. |
| **Restart check** | The cluster restarts a container if it keeps failing the check. |
| **Startup check** | Delays the other checks until the app starts. |

For each check, set **Check** to **None**, **HTTP GET**, **TCP**, or **Command**:

- **HTTP GET**: Enter a **Path** and **Port**, such as `/healthz` and `8080`. Responses from 200 to 399 pass.
- **TCP**: Enter a **Port**. The check passes if it can connect.
- **Command**: Enter the **Commands** to run inside the container. An exit code of 0 passes.

**Every (s)** sets how often the check runs. **Failures** sets how many consecutive failures count as a failed check. If the service declares ports, the form shows buttons such as **HTTP, port 8080**. Select one to fill in the path `/` and that port. You can save only a port the container declares.

![Health checks in service settings, with HTTP GET selected for the traffic check, the path set to /healthz, and separate restart and startup checks](../images/shots/service-health.avif)

After making changes, select **Review changes** at the bottom of the page and apply them. Scheduled jobs and jobs that run once (Jobs) have no health checks.

<Callout type="warn">
A failed restart check restarts the container. If the app takes a long time to start, configure a startup check first or increase the restart check's failure threshold. Otherwise, the cluster may keep restarting the container before the app finishes starting.
</Callout>

## Startup command

Zeabur OSS doesn't have a startup command field. To change the command a container runs at startup, open the service's **Settings**, switch from **Set up** to **YAML** at the top, and select **Edit**. Change the container's `command` (which replaces the image's `ENTRYPOINT`) and `args` (which replaces `CMD`), then review and apply:

```yaml
containers:
  - name: web
    image: nginxinc/nginx-unprivileged:1.29
    command: ["nginx"]
    args: ["-g", "daemon off;"]
```

## Security

Open the service's **Settings** → **Security** and choose what containers can do:

- **Strict**: Runs as a non-root user with no privilege escalation. Images that run as root, such as `nginx:latest`, won't start. Use a version that doesn't need root, such as `nginxinc/nginx-unprivileged`. Images built with Railpack run as user 1000 and can use Strict. In a Dockerfile, specify a non-root user with a numeric ID, such as `USER 1000`.
- **Compatible**: Allows containers to run as root, but they still can't access the host or escalate privileges.

![Security in service settings, with Compatible selected and a description stating that containers can run as root but can't access the host](../images/shots/service-security.avif)

Selecting an option opens the review screen directly. Review and apply the change to replace the replicas. When you create a service from an image, Zeabur OSS selects an option based on the image's configured user: Strict for a numeric non-root user, or Compatible otherwise.

If a service has settings beyond what Compatible permits, such as host access, this section shows **Unrestricted**. Use YAML to change those settings. If an administrator sets the project's security level (Pod Security) to `restricted`, only Strict services can start. See [Adjust the Pod Security level](./projects.mdx#change-the-pod-security-level).

## Group services in the sidebar

The project sidebar lists services by role, such as web services and databases. To list them by groups you name instead, open the service's **Settings** → **Group** and pick a group or type a new name. Leave the field empty to take the service out of its group. Then select **Review changes** and apply. Nothing restarts.

When at least one service is in a group, the sidebar lists each group under its name and the other services under **Ungrouped**.

The group is the `zeabur.com/group` label on the workload itself, not on its Pod template. To set it with kubectl or in Git, add the label to the workload's `metadata.labels`:

```sh
kubectl -n demo label deployment/web zeabur.com/group=shop
kubectl -n demo label deployment/web zeabur.com/group-
```

The second command takes the service out of its group. The `app.kubernetes.io/component` label that Helm charts set doesn't make a group.

## Verify the result

- **Compute** and **Health checks** show the current values. **Security** shows whether Strict or Compatible is selected.
- **Overview** shows whether replicas are ready.
- **Usage** charts reserved and maximum resources alongside actual usage.

## Troubleshooting

| What you see | What to do next |
| --- | --- |
| Replicas keep waiting to be scheduled after a resource change | The reserved amount exceeds the available capacity on every node. Lower the reserved amount or add nodes. |
| Replicas keep restarting, and events show `OOMKilled` | Memory usage exceeds the maximum. Increase **Maximum memory**. |
| Replicas keep restarting, and events show `Liveness probe failed` | Check the restart check's path and port, or add a startup check to give the app more time to start. |
| Replicas never become ready | The traffic check hasn't passed. Check **Logs** and confirm that the app responds on the check's port. |
| Replicas won't start after switching to Strict, and events show `container has runAsNonRoot and image will run as root` | The image runs as root. Switch back to Compatible or use an image that runs as a non-root user. |

## Do the same with kubectl

These settings are standard Deployment or StatefulSet fields. They remain in effect after you remove Zeabur OSS. The examples below use project `demo` and service `web`.

Replica count and resources:

```sh
kubectl -n demo scale deployment/web --replicas=2
kubectl -n demo set resources deployment/web -c web --requests=cpu=250m,memory=256Mi --limits=memory=512Mi
```

`set resources` changes only the values listed in the command. It keeps any values you leave out, such as an existing `cpu` maximum.

Health checks, the startup command, and security settings are all part of the Pod template:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: demo
  labels:
    app.kubernetes.io/name: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: web
  template:
    metadata:
      labels:
        app.kubernetes.io/name: web
    spec:
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: web
          image: nginxinc/nginx-unprivileged:1.29
          command: ["nginx"]
          args: ["-g", "daemon off;"]
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              memory: 512Mi
          readinessProbe:
            httpGet:
              path: /
              port: 8080
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 8080
            periodSeconds: 10
            failureThreshold: 3
          startupProbe:
            httpGet:
              path: /
              port: 8080
            failureThreshold: 30
            periodSeconds: 2
          securityContext:
            allowPrivilegeEscalation: false
            capabilities:
              drop: [ALL]
```

The example above uses **Strict** settings. For **Compatible**, remove `runAsNonRoot: true` from the Pod and `capabilities.drop: [ALL]` from the container. Keep `seccompProfile` and `allowPrivilegeEscalation: false`.

### Verify the settings

```sh
kubectl -n demo get deployment web
kubectl -n demo get deployment web -o jsonpath='{.spec.template.spec.containers[0].resources}'
kubectl -n demo describe pod -l app.kubernetes.io/name=web
```

The `READY` column in `get deployment` shows a value such as `2/2`. Matching numbers mean all replicas have passed their traffic checks. `describe pod` lists the `Readiness`, `Liveness`, and `Startup` settings. When a check fails, `Events` shows `Unhealthy`.
