Find how you installed Zeabur OSS, then follow that section. Nothing upgrades on its own. Zeabur OSS only tells you when a newer version is out.

## Let an agent upgrade for you

An agent such as Claude Code or Codex can follow this page and the upgrade notes for you. Paste this prompt, run the agent on a computer that can reach the server over SSH, and tell it the server's address:

```text
Upgrade Zeabur OSS on my server to the latest version by following https://oss.zeabur.com/docs/zeabur/upgrade/steps.md.
```

The address points to [the Markdown copy of this page](https://oss.zeabur.com/docs/zeabur/upgrade/steps.md). The agent finds how Zeabur OSS was installed, reads the upgrade notes for each version in between, and shows you what it will change. You take the snapshot and sign in afterwards with your passkey; the agent waits for you at those steps.

## See your version

The cluster page always shows `Zeabur v<version>`. When a newer version is out, a notice appears with its version and a link to the release notes. **Settings** › **About** shows the version too. In either place, **How to upgrade** opens the steps for how you installed Zeabur OSS, with the commands to copy and a link to this page.

Under `zeaburctl ui`, the page shows `zeaburctl`'s own version. For the details of the check and how to turn the notice off, see [Update check](../reference/telemetry.mdx#update-check).

## Which version

Upgrade to the version these docs describe. It is the version number in the newest heading of the [CHANGELOG](../../CHANGELOG.md), without the date, such as `0.3.0` or `0.3.0-beta.2`. A pre-release counts when the docs describe one. GitHub never marks a pre-release as Latest, so the Latest label can point to an older version.

The release tag has a `v`, such as `v0.3.0-beta.2`. Give `--version` the version without it, as `0.3.0-beta.2`.

## Before you upgrade

- Read the release notes for the version you're moving to on [GitHub Releases](https://github.com/zeabur-oss/zeabur/releases).
- Read the [upgrade notes](notes.mdx). Read one section for each version you skip, and finish what each one asks before you upgrade.
- Take a snapshot of the server or cluster. To go back to an older version, you can only restore a snapshot taken before the upgrade. See [Go back](#go-back).
- Back up project data separately with Velero. See [Back up a cluster and restore from a backup](../cluster/backups.mdx).

## Upgrade with Helm

If `kubectl -n kube-system get helmchart zeabur` finds a `HelmChart`, a K3s `HelmChart` still runs Zeabur OSS, as zeabur-installer v0.2 set it up. To move from v0.2 to v0.3, follow [Installed with zeabur-installer](notes.mdx#installed-with-zeabur-installer) in the upgrade notes instead of this section. If there is no `HelmChart`, a Helm release runs Zeabur OSS, even when the `zeabur-installer` ConfigMap is still there. Follow this section.

Replace `<version>` with the version from [Which version](#which-version):

```sh
helm upgrade zeabur oci://ghcr.io/zeabur-oss/charts/zeabur \
  --version <version> \
  --namespace zeabur --reset-then-reuse-values
kubectl -n zeabur rollout status deployment/zeabur
```

With `--reset-then-reuse-values`, Helm starts from the new chart's defaults, including the image, then applies the values you set. With `--reuse-values`, the image stays on the old version.

On a server you set up with [Zeatend](../install/one-command.mdx), run the commands on the server, as in the install. First `export KUBECONFIG=/etc/rancher/k3s/k3s.yaml`, or `/etc/rancher/rke2/rke2.yaml` on RKE2. Then run `sudo -E helm upgrade …`, and wait with `sudo k3s kubectl …` on K3s or `sudo -E /var/lib/rancher/rke2/bin/kubectl …` on RKE2.

## Upgrade with Argo CD

Change the chart version in your Argo CD Application, then sync. Argo CD generates manifests without connecting to the cluster, so create a fixed signing key beforehand and set `planKey.existingSecret`. See [Manage the chart with GitOps](../install/existing-cluster.mdx#manage-the-chart-with-gitops).

## Upgrade with Flux

Change the chart version in your Flux HelmRelease, commit it, and wait for Flux to sync.

## Upgrade with zeaburctl ui

Zeabur OSS runs on your own computer, so there is no server to upgrade. Download the new `zeaburctl` from [Release files and verification](../reference/releases.mdx), verify it, replace the old file, and run `zeaburctl ui` again.

## Upgrade Kubernetes with Zeatend

On a server you set up with Zeatend, Zeatend upgrades K3s, RKE2 or KubeSolo, apart from Zeabur OSS. Each Zeatend version installs one release that it names, so a newer Zeatend brings a newer Kubernetes.

1. On the server, download the new Zeatend as [Zeatend's README](https://github.com/zeabur-oss/zeatend#download-zeatend) shows.
2. Run `sudo zeatend plan` to see the release it moves to and the host checks. It changes nothing.
3. Run `sudo zeatend apply`.

`apply` installs the new release and restarts K3s, RKE2 or KubeSolo. The Kubernetes API stops answering for a short time, and running services keep serving. With more than one node, upgrade the servers first, one at a time, then the workers.

Kubernetes moves up one minor version at a time. When the new release is further ahead, `plan` stops before it changes anything and names the release to apply first. Set that release as `version` in `/etc/zeatend/config.yaml` and run `apply`. Repeat with each release `plan` names, then remove `version` and run `apply` once more.

### A server that zeabur-installer set up

Zeatend takes over these servers as they are. With no `/etc/zeatend/config.yaml`, it reads `/etc/zeabur-installer/config.yaml`, and it keeps off the components the installer turned off. Download Zeatend and run the same `plan` and `apply`. Zeatend doesn't change Zeabur OSS itself; to upgrade Zeabur OSS, read the [upgrade notes](notes.mdx) first.

## After you upgrade

- Everyone signs in again once the Zeabur OSS replica is replaced. The chart runs one replica, and sessions live in its memory.
- Run `zeaburctl --version`, or open the cluster page, to confirm the version.
- With Helm, Argo CD or Flux, run `kubectl -n zeabur rollout status deployment/zeabur` to wait for the new replica.

## Go back

To go back to an older version, restore a snapshot taken before the upgrade. Going back without a snapshot isn't supported.
