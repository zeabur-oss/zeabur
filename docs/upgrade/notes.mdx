This page lists each version's breaking changes and what to do before you upgrade. For the upgrade steps themselves, see [Upgrade Zeabur OSS](steps.mdx).

If you're skipping versions, start at the version you run now and read every section up to the version you're moving to. The newest version is at the top.

## v0.2 → v0.3

You don't have to do the steps below by hand. Paste the prompt in [Let an agent upgrade for you](steps.mdx#let-an-agent-upgrade-for-you), and the agent follows this section for you. It stops and waits for you when you take the snapshot and when you sign in.

zeabur-installer is gone. One `helm install` sets up Zeabur OSS on an existing cluster; on a new server, [Zeatend](../install/one-command.mdx) sets up Kubernetes first.

The chart now installs Zeabur Identity and cert-manager, and turns on the Ingress with a certificate from the ClusterIssuer `letsencrypt`. To keep the Zeabur Identity you run, upgrade with `--set identity.enabled=false`. To keep a TLS secret you make yourself, add `--set ingress.clusterIssuer=`. Upgrades never install cert-manager.

The chart now carries the `zeabur-system-hosts` admission policy. Outside namespaces labelled `zeabur.com/platform: "true"`, a new or changed Ingress rule needs a host and an HTTPRoute needs hostnames, and neither can use Zeabur OSS's or Zeabur Identity's domain. Objects that already exist keep working until their `spec` changes. To leave the policy out, set `systemHosts.enabled: false`.

Zeabur OSS now writes its own alert rules and Zeabur Proxy's access to the logs when it installs VictoriaMetrics and VictoriaLogs. The catalog components no longer carry them, and the custom resource metrics are named `kube_customresource_*`. If you installed VictoriaMetrics with Helm, Flux or Argo CD, upgrade it from Zeabur Catalog, then print Zeabur OSS's objects with `zeaburctl components export victoria-metrics victoria-logs` and apply the ones at the end of each component. If an old `zeabur-notifications` VMRule stays and the Notifications page cannot update it, delete it with `kubectl -n observability delete vmrule zeabur-notifications`, then click **Install rules** on that page.

### Installed with zeabur-installer

zeabur-installer v0.2 installed Zeabur OSS through a K3s `HelmChart`, and Zeabur Identity, its admission policy and its sign-in client as plain manifests. v0.3 installs all of them with one Helm release. These steps move what the installer made into that release without deleting it. Projects, services, databases, domains, members and passkeys stay as they are, and nobody needs a new account.

What stays the same:

- K3s, RKE2 or KubeSolo, and the file that lets Kubernetes accept Zeabur Identity's tokens. To upgrade Kubernetes later, use Zeatend, as in [A server that zeabur-installer set up](steps.mdx#a-server-that-zeabur-installer-set-up).
- The components the installer installed, such as Traefik, cert-manager, Zeabur Builder and CloudNativePG. Zeabur OSS doesn't change a component it didn't install, so they stay at their current versions.
- Zeabur Identity's Service address and signing keys, so accounts and passkeys keep working and kube-apiserver still accepts Zeabur Identity's tokens.

After the upgrade, never run `zeabur-installer apply` again. It would put back the v0.2 `HelmChart` and Zeabur Identity v0.1.

An agent can follow these steps. It stops and waits for the server's owner at these points:

- Before it changes anything: the owner reads the new values file and takes a snapshot of each server (step 3).
- When a check in step 1 finds something these steps don't cover.
- After the upgrade: the owner signs in with a passkey (step 8).
- Before it deletes anything, even the leftovers in step 9.

#### 1. Check what the installer made

Run every command on the first server, in a root shell (`sudo -i`). First point `kubectl` and `helm` at the cluster:

| Distribution | Commands |
| --- | --- |
| K3s | `export KUBECONFIG=/etc/rancher/k3s/k3s.yaml` |
| RKE2 | `export KUBECONFIG=/etc/rancher/rke2/rke2.yaml PATH=$PATH:/var/lib/rancher/rke2/bin` |
| KubeSolo | `export KUBECONFIG=/var/lib/kubesolo/pki/admin/admin.kubeconfig PATH=$PATH:/var/lib/zeabur-installer/bin` |

The server also needs Helm 4. Run the rest of the commands in `/root/zeabur-upgrade`:

```sh
umask 077
mkdir -p /root/zeabur-upgrade && cd /root/zeabur-upgrade
```

If `helm version --short` doesn't print `v4`, run the next block to install Helm 4. It downloads Helm from get.helm.sh, checks the file against the checksum published next to it, and installs it to `/usr/local/bin`. The checksum comes from the same site as the file, so it catches a broken download but doesn't prove who built it.

```sh
arch=$(uname -m | sed 's/x86_64/amd64/; s/aarch64/arm64/')
helm=$(curl -fsSL https://get.helm.sh/helm-latest-version)
curl -fsSLO "https://get.helm.sh/helm-$helm-linux-$arch.tar.gz" &&
  curl -fsSLO "https://get.helm.sh/helm-$helm-linux-$arch.tar.gz.sha256sum" &&
  sha256sum -c "helm-$helm-linux-$arch.tar.gz.sha256sum" &&
  tar -xzf "helm-$helm-linux-$arch.tar.gz" --strip-components=1 "linux-$arch/helm" &&
  install -m 0755 helm /usr/local/bin/helm &&
  helm version --short
```

`umask` holds only in the shell that ran it. Each block below that writes a file starts with `umask 077` and `cd /root/zeabur-upgrade`, so the files stay private even when each block runs in a new shell.

Then check each of these. Stop and ask the owner when a result differs from what the right column expects.

| Command | Expected |
| --- | --- |
| `kubectl -n kube-system get configmap zeabur-installer -o jsonpath='{.data.installer}'` | `0.2.0` or another `0.2.x`. For `0.1.x`, do [v0.1 → v0.2](#v01--v02) first. |
| `kubectl -n kube-system get helmchart zeabur` | One `HelmChart`. If there is none, the installer ran with `zeabur: false` and installed no Zeabur OSS: install Zeabur OSS as [Install Zeabur OSS in an existing cluster](../install/existing-cluster.mdx) shows instead. |
| `helm status zeabur -n zeabur` | `STATUS: deployed` |
| `kubectl -n zeabur-identity get deployment zeabur-identity -o jsonpath='{.spec.template.spec.containers[0].args}'` | Nothing, or only `["--invitations"]`. Other options were added by hand, and Zeabur Identity v0.3 refuses many old ones. See [its upgrade notes](https://oss.zeabur.com/docs/identity/operations/upgrade). |
| `kubectl get crd upstreamproviders.identity.zeabur.com` | `NotFound`. If it exists, someone set up GitHub or Google sign-in by hand; follow Zeabur Identity's upgrade notes for those providers first. |

Save the current values and the installer's configuration:

```sh
umask 077
cd /root/zeabur-upgrade
helm get values zeabur -n zeabur -o yaml > old-values.yaml
cp /etc/zeabur-installer/config.yaml installer-config.yaml
```

From these two files, note:

- **Access mode**: `access.mode` in `installer-config.yaml`. `domain` means certificates from Let's Encrypt for real DNS names. `local` means a CA made on the server, with the ClusterIssuer `zeabur-local-ca`.
- **Invitations**: `access.invitations: false` means Zeabur Identity doesn't accept invitation links. When the key is missing, invitations are on.
- **Which Zeabur Identity Zeabur OSS uses**: `issuer.url` in `old-values.yaml`. If it is `https://` followed by `access.identity`, Zeabur OSS uses the Zeabur Identity the installer made. If it is any other address, someone pointed Zeabur OSS at an external Zeabur Identity. Ask the owner before you go on, and write the values as step 2 says for that case.
- **Projects' own domains**: `kubectl get ingress,httproute,certificate -A > domains-before.txt`. Also pick one project domain and save what `curl -sS -o /dev/null -w '%{http_code}\n' https://<domain>/` prints. In local mode, add `--cacert /var/lib/rancher/zeabur-installer/local-ca.crt`, or `/var/lib/zeabur-installer/local-ca.crt` on KubeSolo. The upgrade doesn't touch them.
- **Databases**: `kubectl get clusters.postgresql.cnpg.io,statefulsets -A > databases-before.txt`. The upgrade doesn't touch them.

#### 2. Write the new values file

Write `values.yaml` from `old-values.yaml`. Don't use `--reuse-values` or `--reset-then-reuse-values`: they keep the installer's `image`, which pins v0.2.

Change the keys as the table shows. With an external Zeabur Identity, there are three differences: set `identity.enabled: false`, keep `issuer.url` and `issuer.clientSecret` as they are, and leave out every other `identity` key that the table and the list below it add.

| In `old-values.yaml` | In `values.yaml` |
| --- | --- |
| `image` | Leave it out, so the chart uses its own image. |
| `issuer.url` | Move it to `identity.issuer`, unchanged. |
| `issuer.clientSecret` | Leave it out. The chart makes the Secret `zeabur-client` and registers its hash in Zeabur Identity. |
| `issuer.caBundle` (local mode only) | Keep it. |
| `ingress.annotations` with `cert-manager.io/cluster-issuer: <issuer>` | Leave the annotation out. Set `ingress.clusterIssuer` and `identity.ingress.clusterIssuer` to `<issuer>`. |
| `ingress.className` | Keep it, and set `identity.ingress.className` to the same value. |
| Every other key, such as `publicUrl`, `clusterName`, `planKey`, `domains`, `ingress.enabled`, `ingress.tls`, `builds`, `proxy`, `telemetry` and `updateCheck` | Keep it as it is. |

Then add:

- `identity.admin.setupLink: false`. The administrator already exists, so the chart makes no new setup link.
- `identity.invitations: false`, only when `access.invitations` is `false`.

Use the example for your access mode as a guide, with your own addresses and names. A local-mode server ends up like this:

```yaml
publicUrl: https://zeabur.203.0.113.10.sslip.io
clusterName: vps-1
identity:
  issuer: https://login.203.0.113.10.sslip.io
  admin:
    setupLink: false
  ingress:
    className: traefik
    clusterIssuer: zeabur-local-ca
issuer:
  caBundle:
    configMap: zeabur-identity-ca
planKey:
  existingSecret: zeabur-plan-key
ingress:
  className: traefik
  clusterIssuer: zeabur-local-ca
  tls:
    secretName: zeabur-tls
domains:
  clusterIssuer: zeabur-local-ca
  suffixes: [203-0-113-10.sslip.io]
builds:
  registry: zot.zot.svc:5000
```

In domain mode, set `ingress.clusterIssuer`, `identity.ingress.clusterIssuer` and `domains.clusterIssuer` to `letsencrypt`, and leave out `issuer.caBundle`. A domain-mode server ends up like this:

```yaml
publicUrl: https://zeabur.example.com
clusterName: vps-1
identity:
  issuer: https://login.example.com
  admin:
    setupLink: false
  ingress:
    className: traefik
    clusterIssuer: letsencrypt
planKey:
  existingSecret: zeabur-plan-key
ingress:
  className: traefik
  clusterIssuer: letsencrypt
  tls:
    secretName: zeabur-tls
domains:
  clusterIssuer: letsencrypt
  suffixes: [apps.example.com]
```

Keys that the examples don't show, such as `builds`, `proxy`, `telemetry` and `updateCheck`, stay as they are in `old-values.yaml`, unless the table says to change them.

#### 3. Back up, and take a snapshot

Save what the upgrade takes over, so you can compare or put it back:

```sh
umask 077
cd /root/zeabur-upgrade
kubectl get crd -o name | grep identity.zeabur.com | xargs kubectl get -o yaml > identity-crds.yaml
kubectl -n zeabur-identity get users,credentials,grants,invitations,oauthclients,secrets,configmaps,services -o yaml > identity.yaml
kubectl -n zeabur get secrets,configmaps -o yaml > zeabur.yaml
kubectl -n kube-system get helmchart zeabur -o yaml > helmchart.yaml
kubectl -n kube-system get configmap zeabur-installer zeabur-identity-authn --ignore-not-found -o yaml > installer-record.yaml
```

These files hold secrets, such as Zeabur Identity's signing keys. Keep them on the server.

**Stop.** Show the owner `values.yaml` and the results of step 1. Ask them to take a snapshot of each server and to tell you when it is done. To go back, they restore this snapshot.

When the server can't take a snapshot itself, the owner can often take it in the provider's panel. Wait until it is done. Going back without a snapshot isn't supported. The saved files are not enough to put v0.2 back, because step 4 deletes the installer's `HelmChart` and step 5 changes Zeabur Identity's CRDs. When no snapshot is possible, tell the owner that the upgrade can't be undone. Start step 4 only after the owner confirms that every snapshot is done, or agrees in plain words to go on without one.

#### 4. Detach the installer's `HelmChart`

K3s's helm-controller owns the release through the `HelmChart` `kube-system/zeabur`. Deleting the `HelmChart` as it is uninstalls Zeabur OSS. Tell helm-controller to leave the release alone first, then remove the `HelmChart`:

```sh
kubectl -n kube-system annotate helmchart zeabur helmcharts.helm.cattle.io/unmanaged=true
kubectl -n kube-system patch helmchart zeabur --type=json -p '[{"op":"remove","path":"/metadata/finalizers"}]'
kubectl -n kube-system delete helmchart zeabur
```

Check that the release and its pods are still there before you go on:

```sh
helm status zeabur -n zeabur          # STATUS: deployed
kubectl -n zeabur get pods
```

#### 5. Update Zeabur Identity's CRDs

Helm installs a chart's CRDs only on a first install and never upgrades them. Download the chart and apply the new ones yourself. Replace `<version>` with the version you're moving to, as [Which version](steps.mdx#which-version) shows, without the `v`:

```sh
helm pull oci://ghcr.io/zeabur-oss/charts/zeabur --version <version> --untar
kubectl apply --server-side --force-conflicts -f zeabur/charts/identity/crds/
```

`--force-conflicts` is needed because the installer applied the old CRDs with its own field manager.

#### 6. Upgrade

```sh
helm upgrade zeabur ./zeabur -n zeabur -f values.yaml \
  --take-ownership --force-conflicts --wait --timeout 10m
```

- `--take-ownership` lets the release take over Zeabur Identity, the sign-in client and the admission policy that the installer made.
- `--force-conflicts` takes over fields that the installer set. Fields the chart doesn't set, such as the signing keys in Zeabur Identity's Secret, stay as they are.

If the command fails, read the error, fix `values.yaml` and run the same command again. A failed attempt leaves a failed revision, and the next attempt replaces it.

#### 7. Check the cluster

```sh
helm status zeabur -n zeabur                                   # STATUS: deployed
kubectl -n zeabur rollout status deployment/zeabur
kubectl -n zeabur-identity rollout status deployment/zeabur-identity
kubectl -n zeabur-identity get service zeabur-identity -o jsonpath='{.spec.clusterIP}'
```

The address must equal the one in `discoveryURL` in `installer-record.yaml`. If it changed, kube-apiserver can't reach Zeabur Identity and every sign-in fails: stop and ask the owner.

Then check that nothing else changed:

- `kubectl get ingress,httproute,certificate -A` lists the same names as `domains-before.txt`, and each Certificate shows `True` under `READY`.
- `kubectl get clusters.postgresql.cnpg.io,statefulsets -A` lists the same names as `databases-before.txt`, all ready.
- The `curl` from step 1 prints the same status code.
- `curl -sS <identity.issuer>/.well-known/openid-configuration` returns JSON with the same `issuer`.

#### 8. Sign in

**Stop.** Ask the owner to open Zeabur OSS, sign in with their passkey, open a project and check its services and databases. Only a person can use their passkey. Ask them to have a member sign in too, if they can.

Everyone signs in again once, because the Zeabur OSS pod was replaced.

#### 9. Clean up

Zeabur OSS no longer reads the Secret `zeabur/zeabur-oidc`, the installer's sign-in client secret, unless it uses an external Zeabur Identity. In that case `values.yaml` still names it, so keep it. Otherwise, once the owner agrees, delete it:

```sh
kubectl -n zeabur delete secret zeabur-oidc
```

Keep `/root/zeabur-upgrade` and the snapshot until everything works for a few days.

## v0.1 → v0.2

On a server installed with zeabur-installer, change the configuration file and remove the zot that v0.1 installed, then run `plan` and `apply`. If other nodes joined later, worker nodes or RKE2 servers, have each one join again after the server is upgraded.

If you installed with Helm, Argo CD or Flux, the chart values have no breaking changes. You only need to act if you added flags that v0.2 removed to the Deployment yourself. See below.

### Installed with zeabur-installer

Run the `kubectl` commands below on the server. On K3s, use `sudo k3s kubectl`. On RKE2, use `sudo /var/lib/rancher/rke2/bin/kubectl --kubeconfig /etc/rancher/rke2/rke2.yaml`.

#### 1. Change the configuration file

Edit `/etc/zeabur-installer/config.yaml` on the server and replace the three old forms below.

v0.2 has no `preset`. By default it installs the components the catalog recommends, plus Zeabur Builder, Keel and CloudNativePG. Adjust it based on your old `preset`:

| Before | After |
| --- | --- |
| `standard`, or not set | Delete the `preset` line |
| `secure` | Delete `preset` and add `enable: [runtime-security, vulnerability-scanning, intrusion-prevention]` |
| `minimal` | Delete `preset`, run `plan` to see which components it adds, and add the ones you don't want to `disable` |

Zeabur Builder is a new default component that builds from Git. If you don't need it, add `builds` to `disable`.

Input names in `inputs` and `secretFiles` are now camelCase, and the new version doesn't read the old names. If a required input uses its old name, `plan` reports it as missing. An optional one is treated as unset and takes its default. If you use any of these components, rename the old inputs:

| Component | Old name | New name |
| --- | --- | --- |
| `builds/zeabur-builder` | `cluster-ip` | `clusterIp` |
| `intrusion-prevention/crowdsec` | `bouncer-key`, `lapi-secret`, `registration-token` | `bouncerKey`, `lapiSecret`, `registrationToken` |
| `remote-access/tailscale-operator` | `oauth-client-id`, `oauth-client-secret` | `oauthClientId`, `oauthClientSecret` |
| `volume-backup/velero` | `s3-url`, `repository-password`, `backup-key`, `file-backup` | `s3Url`, `repositoryPassword`, `backupKey`, `fileBackup` |

If `enable` or `disable` lists `container-registry/zot`, delete it. zot is now part of Zeabur Builder.

#### 2. Remove the zot that v0.1 installed

v0.1's default components included a standalone zot. v0.2 doesn't replace it with Zeabur Builder's zot, so remove it yourself first. Check whether this server has it:

```sh
kubectl -n kube-system get helmchart zot \
  -o jsonpath='{.metadata.annotations.installer\.zeabur\.com/component}'
```

Only remove it if this prints `container-registry/zot`. If it prints `builds/zeabur-builder`, or there's no `zot`, go to the next step.

```sh
kubectl -n kube-system delete helmchart zot
kubectl -n zot get pods      # wait until no pods are left
kubectl delete namespace zot
```

This also deletes the images zot stored. The next `apply` installs Zeabur Builder with its own zot, and builds push their images again.

#### 3. Upgrade the server

If `profile` is `multi-node`, run these first. v0.1 gave VictoriaMetrics a 20 GiB volume on `multi-node` and v0.2 asks for 5 GiB, but a volume can't shrink, so the VictoriaMetrics operator would stop updating vmsingle. The first command tells the operator to keep the volume's size, and the second makes it try vmsingle again:

```sh
kubectl -n observability annotate pvc vmsingle-vm-victoria-metrics-k8s-stack operator.victoriametrics.com/pvc-allow-volume-expansion=false
kubectl -n observability rollout restart deployment victoria-metrics-operator
```

Download the v0.2 installer, run `plan`, review it, then run `apply`.

`plan` lists the components this upgrade adds. System Upgrade Controller is no longer a default component. `apply` doesn't remove it but stops updating it, and `plan` shows it as `not removed, no longer updated`. The installer already pins the K3s and RKE2 release, so you don't need it. To keep it, add `node-updates/system-upgrade-controller` to `enable`. Otherwise, delete it after `apply`:

```sh
kubectl delete namespace system-upgrade
kubectl delete crd plans.upgrade.cattle.io
kubectl delete clusterrolebinding system-upgrade system-upgrade-drainer
kubectl delete clusterrole system-upgrade-controller system-upgrade-controller-drainer
```

The zot you removed in step 2 also shows as `not removed, no longer updated` in `plan`. That's because the install record still lists it. It no longer shows after `apply`.

v0.2 reserves memory for the system so pods can't use it all and take the whole server down. So `apply` restarts K3s or RKE2. The Kubernetes API stops answering for about 10 seconds. Running apps keep serving. The reserved memory is taken from what pods can request, so on a server that was nearly full, pods may no longer fit and stay `Pending`. `plan` warns when the pods on a node already request more than is left. Before `apply`, delete a service on that node or lower its replicas, move a service to another node, or add a node.

#### 4. Have the other nodes join again

Nodes that joined later have a `join` section in their configuration file: worker nodes, and on RKE2, servers added after the first. If no node has one, skip this step.

In their configuration files, v0.1's `join.zot` is `join.registry` in v0.2, and zot's address has changed, so join again with a new configuration:

1. On the upgraded server, run `sudo zeabur-installer node add`. For RKE2 servers that joined later, add `--role server` so they keep their server role.
2. On each of those nodes, put the v0.2 installer in place, back up `/etc/zeabur-installer/config.yaml`, then paste what `node add` printed as root. It writes the new configuration file, then runs `plan` and `apply`.
3. Once every node is `Ready`, if any worker nodes joined, run `sudo zeabur-installer node sync` on the server, then revoke the token as the last line of the `node add` output says. Until you run `node sync`, the network policies block the rejoined nodes.

For `node add`'s options and how to revoke its token, see [Manage nodes](../cluster/nodes.mdx).

### Installed with Helm, Argo CD or Flux

Zeabur OSS and Zeabur Proxy dropped the flags that set session length and proxy limits. The values stay the same: people sign in again after 1 hour idle or 12 hours in total. The proxy times out after 30 seconds and caps requests at 16 MiB. The chart never set these flags. If you added them to the Deployment's `args` or `env` yourself, delete them before you upgrade:

- `zeabur`: `--session-idle-minutes`, `--session-max-hours`, or the `ZEABUR_SESSION_IDLE_MINUTES` and `ZEABUR_SESSION_MAX_HOURS` environment variables.
- `zeabur-proxy`: `--timeout`, `--max-bytes`, `--review-cache`, `--max-inflight`, `--max-inflight-per-person`, or the `ZEABUR_PROXY_TIMEOUT`, `ZEABUR_PROXY_MAX_BYTES`, `ZEABUR_PROXY_REVIEW_CACHE`, `ZEABUR_PROXY_MAX_INFLIGHT` and `ZEABUR_PROXY_MAX_INFLIGHT_PER_PERSON` environment variables. Other `ZEABUR_PROXY_*` variables, such as the TLS certificate and key, still work.
