---
title: Deploy from an application template
description: Choose an application template from Zeabur Catalog, enter a domain and the required values, and deploy it to a project.
---

When you finish this page, the project has a new application, such as Miniflux, with its services, databases, and public domain. Open the domain to start using it. Templates come from the [Zeabur Catalog](https://github.com/zeabur-oss/catalog) bundled with this version of Zeabur OSS. Zeabur OSS doesn't download templates from an external source during deployment.

## Before you start

- You need an existing project and permission to create services. Zeabur OSS creates the template's contents with your own permissions. Review changes lists any items you don't have permission to create.
- Install the components the template requires. For example, templates that use PostgreSQL need CloudNativePG. The template list shows **Install first…** below each template that requires components.
- If the template needs a public domain, prepare a domain that points to the cluster's entry point. For templates that require HTTPS, a cluster administrator must set a certificate issuer first. See [Add public domains and HTTPS](../configure/domains.mdx).

## Deploy a template

<Steps>
<Step>

### Choose an application

Open **Add** → **App template**. Each template describes what it's for and how much CPU and memory it needs. A message below the template warns you if the cluster doesn't have enough memory or CPU available. Enter a name at the top to filter the list.

![Application template list filtered by n8n, showing three templates with descriptions and CPU and memory requirements](../images/shots/template-list.avif)

</Step>
<Step>

### Install missing components

If a required component isn't installed, every missing component is named above the form with a **How to install** button. Click it to see the install commands for all of them at once. Follow the steps in [View and install cluster components](../cluster/components.mdx), then return to deploy the template. **Review changes** doesn't continue while components are missing.

</Step>
<Step>

### Enter a domain and field values

- **Public domain**: Defaults to a combination of the template name and project name. You can change it to your own domain.
- **Before you deploy**: Known risks and how to address them, listed by the template author. This section is collapsed by default; expand it to read the content, which is currently available only in English. Read it before deploying, for example to check who can create an admin account before the first startup.
- Other fields: Names and descriptions match the interface language. Fields marked **Optional** can be left blank.

Passwords and keys are generated in your browser and stored in the secret specified by the template, such as `miniflux-secrets` for Miniflux. After deployment, you can reveal them in **Variables** for a service that uses them.

![Miniflux deployment form with a public domain field and a note that passwords are stored in the miniflux-secrets secret](../images/shots/template-form.avif)

</Step>
<Step>

### Review and apply

Click **Review changes**, check the items to be created, then apply. **What starts** lists the template's services, databases, and domains, with peak CPU and memory requirements below. If the same template has already been deployed in this project, the review shows the items that already exist. Delete them first, or deploy to another project. Every item is created in this project.

![Miniflux deployment review listing the secrets, services, databases, and domains to create, and whether enough resources are available](../images/shots/template-review.avif)

</Step>
</Steps>

## Verify the deployment

After you apply the changes, the template's services and databases appear in the project. Open each service's **Overview**, wait for its replicas to be ready, then open the template's public domain and confirm that the application's page loads.

## Troubleshooting

- Name already exists: Templates use fixed names. If the same template has already been deployed in the project, or a secret with the same name exists, Review changes lists the conflicts. Deploy to another project.
- Field format doesn't match: The required format appears below the field. Update the value to match, then review changes again.
- Review changes says the cluster doesn't support an object type: A required component isn't installed or is still starting. Check its status on the **Components** page.

## Deploy with an agent

A coding agent such as Claude Code or Codex can deploy a template for you with `zeaburctl templates export`. Paste this prompt, with the template ID and the project:

```text
Deploy the Zeabur Catalog template <template> into the project <project> on my cluster. Follow https://oss.zeabur.com/docs/zeabur/deploy/templates.md.
Ask me which kubeconfig context to use, and pass it with --context to kubectl, `zeaburctl templates export` and `zeaburctl doctor`. Use a zeaburctl of the same version as my Zeabur OSS.
Deploy only what `zeaburctl templates export <template> --project <project>` prints. Don't choose versions or values, and don't write your own manifests, Compose files or Helm commands.
Ask me for the value of every <name> placeholder in the output. Export again with <domain> as --domain, <clusterIssuer> as --cluster-issuer and each other placeholder as --set <name>=<value>. Save that output to one file and use only that file for the template.
If zeaburctl says the cluster lacks a component, ask me which --format fits my cluster: helmchart, flux or argocd. Save what `zeaburctl components export <component> --format <format>` prints to its own file and install it first.
Before each write to the cluster, show me the output of `kubectl diff --server-side -f <file>` and wait for my go-ahead. Then run `kubectl apply --server-side -f <file>` on the same file.
When you finish, run `zeaburctl doctor --output json` and report what it says.
```

The agent needs zeaburctl and kubectl with a kubeconfig for the cluster. It writes with your permissions, and nothing reaches the cluster until you approve the diff.

## Do the same with kubectl

### Export the YAML and apply it

`zeaburctl templates export` prints the objects that deploying a template into a project writes, the same ones the web interface writes, with the same labels. It uses the templates in that zeaburctl, so use a zeaburctl of the same version as Zeabur OSS:

```sh
umask 077
zeaburctl templates export miniflux --project shop \
  --domain miniflux.example.com --cluster-issuer letsencrypt > miniflux.yaml
kubectl diff --server-side -f miniflux.yaml
kubectl apply --server-side -f miniflux.yaml
```

- The output starts with the secrets that hold the template's passwords and keys. Each run generates new values, so export once and apply that file. Applying a later export again replaces the passwords of a running application. Don't put the file in version control.
- Give each field the template asks for with `--set <name>=<value>`, such as `--set adminEmail=me@example.com`. Field names are under `inputs` in the template's `template.yaml`. A required field you don't give, a missing `--domain`, and a missing `--cluster-issuer` appear as `<name>` placeholders. Give their values with these options and export again before you apply. `--cluster-issuer` is the issuer the cluster administrator set for Zeabur OSS (`domains.clusterIssuer`).
- If the cluster lacks a component the template needs, the command says so and names the `zeaburctl components export` command that installs it. See [zeaburctl](../reference/zeaburctl.mdx#templates-export).

Delete the entire template:

```sh
kubectl -n shop delete all,ingress,pvc,secret,configmap,networkpolicy -l app.kubernetes.io/instance=miniflux
```

Operator objects, such as databases, have the same labels. Find them with `kubectl -n shop get <kind> -l app.kubernetes.io/instance=miniflux`, then delete them. Deleting volumes and databases also deletes their data.

### Check the deployed objects

Every template object, including the secrets that hold generated passwords, has three labels: `app.kubernetes.io/instance` and `templates.zeabur.com/template` contain the template ID, and `app.kubernetes.io/version` contains the application version. List the objects from this deployment:

```sh
kubectl -n shop get deploy,statefulset,svc,ingress,pvc,secret -l app.kubernetes.io/instance=miniflux
```

For templates that use a database, also confirm that the operator's objects are ready. For example, check that `kubectl -n shop get clusters.postgresql.cnpg.io -l app.kubernetes.io/instance=miniflux` shows `Cluster in healthy state` in `STATUS`. An operator is the cluster component that manages a database.

### Limit outbound connections from an application

Templates don't block traffic across the entire project. The project's NetworkPolicy `zeabur-project` determines who can connect to replicas in the project. See [Security](../reference/security.mdx). Outbound connections aren't blocked, so applications can connect to model services, webhooks, mail servers, and S3 for backups.

To restrict an application's outbound connections, add a NetworkPolicy. This example lets Umami query DNS and connect only to its database:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: umami-egress
spec:
  podSelector:
    matchLabels:
      templates.zeabur.com/template: umami
      app.kubernetes.io/name: umami
  policyTypes: [Egress]
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - {protocol: UDP, port: 53}
    - {protocol: TCP, port: 53}
  - to:
    - podSelector:
        matchLabels:
          cnpg.io/cluster: umami-db
    ports:
    - {protocol: TCP, port: 5432}
```

Apply it with `kubectl apply -n <project-namespace> -f umami-egress.yaml`. Make sure `podSelector` selects only the application's replicas, not the database's. The database needs to connect to the Kubernetes API and S3 for backups. Blocking those connections stops the database from working and causes backups to fail.
