---
title: Deploy from an application template
description: Choose an application template from Zeabur Catalog, enter a domain and the required values, and deploy it to a project.
---

In a project, select **Add** → **App template**, choose an application, enter a domain and the required values, and click **Review changes**, then apply. Templates come from the [Zeabur Catalog](https://github.com/zeabur-oss/catalog) bundled with this version of Zeabur. Zeabur doesn't download templates from an external source during deployment.

## Before you start

- You need an existing project and permission to create services. Zeabur creates template objects with your own permissions. Review changes lists any objects you don't have permission to create.
- Install the components the template requires. For example, templates that use PostgreSQL need CloudNativePG. The template list shows **Install first…** below each template that requires components.
- If the template needs a public domain, prepare a domain that points to the cluster's ingress. For templates that require HTTPS, configure a certificate issuer in Zeabur first.

## Deploy a template

<Steps>
<Step>

### Choose an application

Open **Add** → **App template**. Each template describes what it's for and how much CPU and memory it needs. A message below the template warns you if the cluster doesn't have enough memory or CPU available. Enter a name at the top to filter the list.

![Application template list filtered by n8n, showing three templates with descriptions and CPU and memory requirements](../images/shots/template-list.avif)

</Step>
<Step>

### Install missing components

If a required component isn't installed, every missing component is named above the form with a **How to install** button. Click it to see the install commands for all of them at once. Follow the steps in [Check and install cluster components](../cluster/components.mdx), then return to deploy the template. **Review changes** doesn't continue while components are missing.

</Step>
<Step>

### Enter a domain and field values

- **Public domain**: Defaults to a combination of the template name and project name. You can change it to your own domain.
- **Before you deploy**: Known risks and how to address them, listed by the template author. This section is collapsed by default; expand it to read the content, which is currently available only in English. Read it before deploying, for example to check who can create an admin account before the first startup.
- Other fields: Names and descriptions match the interface language. Fields marked **Optional** can be left blank.

Passwords and keys are generated in your browser and stored in the secret specified by the template, such as `miniflux-secrets` for Miniflux. After deployment, you can reveal them in **Variables** for a service that uses them.

![Miniflux deployment form with a public domain field and a note that passwords are stored in the miniflux-secrets secret](../images/shots/template-form.avif)

</Step>
<Step>

### Review and apply

Click **Review changes**, check the objects to be created, then apply. **What starts** lists the template's services, databases, and domains, with peak CPU and memory requirements below. If the same template has already been deployed in this project, the review shows the objects that already exist. Delete them first, or deploy to another project. All template objects are created in this project's namespace.

![Miniflux deployment review listing the secrets, services, databases, and domains to create, and whether enough resources are available](../images/shots/template-review.avif)

</Step>
</Steps>

## Verify the deployment

After you apply the changes, the template's services and databases appear in the project. Open each service's **Overview**, wait for its replicas to be ready, then open the template's public domain and confirm that the application's page loads.

Every template object, including the generated password secrets, has three labels: `app.kubernetes.io/instance` and `templates.zeabur.com/template` contain the template ID, and `app.kubernetes.io/version` contains the application version. Use kubectl to list the objects from this deployment:

```sh
kubectl -n shop get deploy,statefulset,svc,ingress,pvc,secret -l app.kubernetes.io/instance=miniflux
```

For templates that use a database, also confirm that the operator's objects are ready. For example, check that `kubectl -n shop get clusters.postgresql.cnpg.io -l app.kubernetes.io/instance=miniflux` shows `Cluster in healthy state` in `STATUS`.

## Do the same with kubectl

Zeabur uses its bundled [Zeabur Catalog](https://github.com/zeabur-oss/catalog) to render templates as YAML. This happens inside Zeabur and has no corresponding cluster object, but you can use Catalog's `catalog` command to generate the same YAML and apply it with kubectl.

First, find the Catalog version Zeabur uses: open **About** in **Settings**. The **Zeabur Catalog** row shows its commit. Check out that commit in the Catalog source, enter `nix develop`, then run:

```sh
umask 077
go run ./tools/cmd/catalog template inputs -namespace shop miniflux > secrets.json
go run ./tools/cmd/catalog template render -namespace shop \
  -domain miniflux.example.com -cluster-issuer letsencrypt miniflux > plan.yaml
kubectl -n shop apply -f secrets.json
kubectl -n shop apply -f plan.yaml
```

- `template inputs` generates the passwords and keys the template needs. Each run generates new values, so run it only once and reuse the same secrets for upgrades. Don't put `secrets.json` in version control.
- If the template has fields to fill in, write the values as a JSON object, such as `{"storageRegion":"us-east-1", ...}` for Dify, and pass it with `-values inputs.json`. Field names are listed under `inputs` in the template's `template.yaml`.
- Install the components listed in the template's `requires` first.

Delete the entire template:

```sh
kubectl -n shop delete all,ingress,pvc,secret,configmap,networkpolicy -l app.kubernetes.io/instance=miniflux
```

Operator objects, such as databases, have the same labels. Find them with `kubectl -n shop get <kind> -l app.kubernetes.io/instance=miniflux`, then delete them. Deleting volumes and databases also deletes their data.

## Connection rules

Templates don't block traffic across the entire project. The project's `zeabur-project` determines who can connect to replicas in the project. See [Security](../reference/security.mdx). Outbound connections aren't blocked, so applications can connect to model services, webhooks, mail servers, and S3 for backups.

To restrict an application's outbound connections, add a NetworkPolicy. This example lets Umami query DNS and connect only to its database:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: umami-egress
spec:
  podSelector:
    matchLabels:
      templates.zeabur.com/template: umami
      app.kubernetes.io/name: umami
  policyTypes: [Egress]
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - {protocol: UDP, port: 53}
    - {protocol: TCP, port: 53}
  - to:
    - podSelector:
        matchLabels:
          cnpg.io/cluster: umami-db
    ports:
    - {protocol: TCP, port: 5432}
```

Apply it with `kubectl apply -n <project-namespace> -f umami-egress.yaml`. Make sure `podSelector` selects only the application's replicas, not the database's. The database needs to connect to the Kubernetes API and S3 for backups. Blocking those connections stops the database from working and causes backups to fail.

## Common failures

- Name already exists: Templates use fixed object names. If the same template has already been deployed in the project, or a secret with the same name exists, Review changes lists the conflicts. Deploy to another project.
- Field format doesn't match: The required format appears below the field. Update the value to match, then review changes again.
- Review changes says the cluster doesn't support an object type: A required component isn't installed or is still starting. Check its status on the **Components** page.
