把已部署的 Namespace 開成專案，就能查看服務；修改前先檢查差異，確認後用自己的 Kubernetes 權限套用。服務設定保留在叢集物件裡，之後仍可交給原本的工具管理。

## 用既有工具部署的服務

用 `kubectl`、Helm、Argo CD 或 Flux 部署的工作負載本來就在 Kubernetes 裡。開啟 Zeabur 的**專案**，從**其他 Namespace**進入對應的 Namespace，就能依自己的權限查看裡面的服務。

Zeabur 會依工作負載與物件的關係整理資訊：Deployment 等工作負載對應服務，Service 提供私有位址，Ingress 或 HTTPRoute 提供公開網域，Pod 的參照指出環境變數與磁碟區從哪裡來。按**使用這個 Namespace**只加上專案標籤，原有物件不會搬動。

如果服務由 Helm、Argo CD 或 Flux 管理，直接改 Deployment，那個工具下次同步時就會改回去。Zeabur 會標出管理工具，拒絕編輯或刪除這類物件，請你到 Helm values 或 Git repository 修改。重新啟動不改設定，仍然可以使用。

同一份 ConfigMap 或機密可能給多個服務使用。改共用的設定前，先看還有哪些服務會受影響；詳見[環境變數](../configure/variables.mdx)。

## 檢查完變更，叢集又有了更新

修改副本數或環境變數後，按**檢查變更**會列出要寫入的內容與前後差異。按下套用之前，叢集裡什麼都不會變。

如果這段時間有人用 `kubectl` 改了同一個物件，Zeabur 會拒絕套用，請你重新檢查。重新檢查會從物件目前的狀態算出差異，你的舊值不會蓋掉另一個人的修改。

檢查過的變更 10 分鐘內有效，超過時間會看到**這份變更已過期**，按**重新檢查**。變更只能由檢查它的人、在同一台 Zeabur 伺服器上套用；中途換了帳號或群組，也要重新檢查。

一次套用多個物件時，Zeabur 依序寫入。中途有一個遭拒，前面已建立的物件會留在叢集；畫面會列出哪些已寫入，依此決定清除或重新檢查。

## 看得到專案，操作卻遭拒

同一個專案，**檢視者**能看狀態與事件，但讀不到機密和日誌；**開發者**還能部署、修改設定、讀日誌與使用終端機。所以檢視者看得到服務名稱，打開日誌卻會遭拒。

Zeabur 每次呼叫 kube-apiserver 都帶著登入者的 token，由 Kubernetes RBAC 決定能讀寫什麼。chart 建立的 Zeabur ServiceAccount 沒有綁定任何 Role 或 ClusterRole，Pod 也不掛載它的 token（`automountServiceAccountToken: false`），所以 Zeabur 沒有自己的權限可以代替成員操作。

讀取遭拒時，畫面會說是權限不足，不會顯示成物件不存在。管理員可到[成員](../cluster/members.mdx)調整角色。若安裝啟用提升權限，符合條件的管理員可選擇**暫時使用管理員權限**，再次驗證通行密鑰後重試。

管理員權限有效期間，所有請求都用提升後的權限；時間到就回到日常權限，不會自動續期。有效時間由 Zeabur Identity 的設定決定。角色範圍與終端機的安全邊界見[權限參考](../reference/permissions.mdx)和[安全性](../reference/security.mdx)。

## 移除 Zeabur，服務會怎樣

只移除 Zeabur 的 Helm release，應用程式的 Deployment、Service、Ingress、環境變數與磁碟區仍在各自的 Namespace。Kubernetes 和已安裝的 controller 繼續處理它們，應用程式流量經原本的入口進入服務。

移除後，Zeabur 的管理介面、工作階段與由 chart 安裝的成員角色會消失。由成員角色取得的權限要另行接手；保留 Zeabur Identity 時，其他用戶端仍可使用它登入。

資料庫依賴的 operator、網域依賴的 Ingress controller、憑證與儲存元件都要留下。如果連 RKE2 或這些元件一起移除，就會影響依賴它們的服務。執行前依[移除 Zeabur](../leave/uninstall.mdx)核對清單，先準備其他管理與登入方式。
