---
title: Register a shared S3 backup destination
description: Register S3 storage for database, K8up, and Velero backups, and understand how copying and rotating keys affects backups.
---

Open **Cluster** → **Backups**, then click **Add destination** under **S3 destinations** at the top. Register a destination once, then select it in database, volume, and cluster backup forms instead of entering the endpoint and keys each time.

You don't need Velero installed to register a destination. A destination is only an option in backup forms. You set schedules and retention periods in each backup form.

## Get an S3 bucket

If you don't have one yet, Cloudflare R2 and Backblaze B2 both offer S3-compatible storage. Create a private bucket. Backups then live outside the cluster and survive losing it.

### Cloudflare R2

1. In the Cloudflare dashboard, open **R2 object storage**, click **Create bucket**, and give it a name, for example `zeabur-backups`.
2. Create an API token with **Object Read & Write** permission, limited to this bucket.
3. Copy the **Access Key ID** and **Secret Access Key**. The secret access key is shown only once.
4. The endpoint is `https://<account ID>.r2.cloudflarestorage.com`. Enter `auto` as the region.

### Backblaze B2

1. Sign in to Backblaze, open **Buckets**, click **Create a Bucket**, and keep it **Private**.
2. The bucket's details list its **Endpoint**, for example `https://s3.us-west-004.backblazeb2.com`. The region is the `us-west-004` part.
3. Open **Application Keys**, click **Add a New Application Key**, limit it to this bucket, and choose **Read and Write**.
4. Copy the `keyID` (the access key ID) and the `applicationKey` (the secret access key). The `applicationKey` is shown only once.

## Before you begin

- Have an S3-compatible bucket and its endpoint, region, access key ID, and secret access key ready.
- To register or edit a destination, you need permission to write config files and secrets in the `zeabur-s3-destinations` namespace. Admin accounts have this permission.
- To select a destination in a backup form, you need permission to read secrets in `zeabur-s3-destinations` and create secrets in the backup's namespace.

Everyone who's signed in can see destination names and locations, but the Zeabur Chart doesn't grant anyone permission to read the secrets stored there. Members without this permission can only select **Enter manually** in backup forms and enter their own keys.

## Register a destination

<Steps>
<Step>

### Enter the location and keys

Under **Cluster** → **Backups** → **S3 destinations**, click **Add destination** and fill in:

| Field | What to enter |
| --- | --- |
| **Name** | Up to 63 characters using only lowercase letters, numbers, and hyphens. Must start and end with a letter or number, for example, `r2-backups`. |
| **Endpoint** | Required. An S3 address starting with `https://` or `http://`. Required for AWS S3, too. |
| **Bucket** | An existing bucket with a name of 3 to 63 lowercase letters, numbers, periods, or hyphens. |
| **Folder** | Optional. Backups go under this path. Can't contain spaces or `..`. |
| **Region** | Enter a region if the storage provider requires one. |
| **Access key ID**, **Secret access key** | Both are required when adding a destination. |

![Add S3 destination form with a Backblaze B2 endpoint, bucket, and keys entered](../images/shots/s3-destination-add.avif)

</Step>
<Step>

### Review and save

Click **Review changes**, check the config file and secret to be written (keys aren't shown), then apply the changes.

After you apply the changes, **S3 destinations** lists the name, bucket, folder, and endpoint. The list doesn't check the connection. To verify the endpoint and keys, select the destination in a backup form and run a backup.

</Step>
</Steps>

## Use a destination for three backup types

| Data to back up | Where to configure it |
| --- | --- |
| Database | Open the database in a project → **Backups**. See [Database backups](../deploy/databases.mdx). |
| A service's volume files | Open the service's **Settings** → **Backup** below **Storage**. Uses K8up. See [Volumes](../configure/volumes.mdx). |
| Cluster objects and volume files | Open **Cluster** → **Backups** → **Where backups go**. Uses Velero. See [Cluster backups](./backups.mdx). |

New backup forms select the first registered destination in the **S3 destination** menu by default. You can select another destination or **Enter manually**. Selecting a destination fills in the endpoint, bucket, region, and folder, and hides the key fields. Some backups add a subfolder under the destination's folder, so check the final folder before you apply the changes.

When you apply the changes, Zeabur copies the destination's keys into a separate secret for the backup. Database and K8up secrets go in the project's namespace; Velero secrets go in Velero's namespace. Backups then read only this copy, so they keep running even if you remove the destination or Zeabur.

## Change keys

Click **Edit** in the destination's row. You can't change the name. Leave both key fields blank to keep the current keys, or fill in both to replace them, then click **Review changes**.

The review lists each key copy that Zeabur also updates, for example **Update copied keys shop-db-backups-s3 in shop**. The database, K8up, and Velero copies all receive the new keys when you apply the changes.

![Review before saving a destination, listing the shop key copy that will also be updated](../images/shots/s3-destination-keys.avif)

The review also lists copies that can't be updated and explains why. These copies keep using the old keys:

- You don't have permission to edit the copy. A member with permission can save the destination again to update it with the new keys.
- The copy doesn't identify its key fields.
- You don't have permission to list secrets across all namespaces, so Zeabur can't find copies elsewhere.

<Callout type="warn">
Before revoking the old keys with the storage provider, confirm that the review lists no copies that will keep using the old keys, and wait for the next backup to succeed. Otherwise those backups start failing.
</Callout>

## Do the same with kubectl

A destination consists of two objects with the same name in the `zeabur-s3-destinations` namespace: a ConfigMap for the endpoint, bucket, region, and folder, and a Secret for the keys. Zeabur lists the destination only when both have the label `zeabur.com/s3-destination: <name>`. Omit `region` and `prefix` if they have no values.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: r2-backups
  namespace: zeabur-s3-destinations
  labels:
    zeabur.com/s3-destination: r2-backups
data:
  endpoint: https://s3.example.com
  bucket: team-backups
  region: auto
  prefix: zeabur
---
apiVersion: v1
kind: Secret
metadata:
  name: r2-backups
  namespace: zeabur-s3-destinations
  labels:
    zeabur.com/s3-destination: r2-backups
type: Opaque
stringData:
  AWS_ACCESS_KEY_ID: AKIAEXAMPLE
  AWS_SECRET_ACCESS_KEY: example-secret-key
```

After you select a destination in a backup form, the key copy written to the project looks like this. The label records its source. The `zeabur.com/s3-destination-keys` annotation identifies the two keys that hold the access key ID and secret access key. The key names vary by backup type. This example is a Secret for PostgreSQL backups:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: shop-db-backups-s3
  namespace: shop
  labels:
    zeabur.com/s3-destination: r2-backups
  annotations:
    zeabur.com/s3-destination-keys: ACCESS_KEY_ID,ACCESS_SECRET_KEY
type: Opaque
stringData:
  ACCESS_KEY_ID: AKIAEXAMPLE
  ACCESS_SECRET_KEY: example-secret-key
```

To change keys manually, update the destination's Secret first. Then find each copy and update the keys named in its annotation:

```sh
kubectl get secret -A -l zeabur.com/s3-destination=r2-backups \
  -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,KEYS:.metadata.annotations.zeabur\.com/s3-destination-keys
```

To remove the destination, delete these two objects. Copies aren't affected:

```sh
kubectl -n zeabur-s3-destinations delete configmap,secret r2-backups
```

## Verify the result

- **Cluster** → **Backups** → **S3 destinations** lists the name, bucket, folder, and endpoint.
- `kubectl -n zeabur-s3-destinations get configmap,secret -l zeabur.com/s3-destination` lists one ConfigMap and one Secret for each destination.
- After you apply the backup configuration, the `kubectl get secret -A -l zeabur.com/s3-destination=<name>` command above also lists a copy in the backup's namespace.

## Common failures

- The menu is stuck on **Enter manually** and you can't change it: You don't have permission to read secrets in `zeabur-s3-destinations`. Ask an administrator to grant access, or enter the keys manually.
- The backup form has no **S3 destination** menu: No one has registered a destination yet. Anyone with permission to add a destination sees a prompt linking to this section.
- The endpoint field can't be blank: Registering a destination requires a full S3 address, including for AWS S3.
- The destination saved, but the backup failed: Open the backup page that uses it and check the error message for that backup or storage location.
- You changed the destination's keys, but backups still use the old ones: That copy wasn't updated. Ask a member with permission to save the destination again.

## Remove a destination

Click **Remove** in the destination's row, review the config file and secret to delete, then confirm. The destination disappears from the list and the menus in backup forms.

Copied keys, backup schedules, and files in the bucket remain. To remove an entire set of backups, first stop the schedules and delete the key copies everywhere they're used. Then delete the backup files with the storage provider. Revoke the keys with the storage provider only after confirming that no backups still use them.
