When you finish this page, your teammate is listed on **Members**, signs in to Zeabur with their own passkey, and can use only the projects you gave them. A passkey lives on their phone or computer. They unlock it with a fingerprint, their face, or the screen lock, so there is no password to remember.

## Before you begin

- You're signed in to Zeabur with an admin account.
- Zeabur Identity is installed in the cluster and handles sign-in to Zeabur. It must run with `--invitations` for setup links to work.
- The chart's `memberRoles.enabled` setting is on, which is the default. When it's off, an invitation can only choose whether to give **Admin** rights.

## Invite a member

<Steps>
<Step>

### Enter the account

Open **Members** and click **Invite**. Enter a **Username**. **Display name** is optional.

A username can contain only lowercase letters, numbers, `-`, and `.`, up to 63 characters. If you enter an existing member, the link adds another passkey to their account and leaves their permissions as they are.

To add someone to one project, you can also start from that project: open its **Settings**, and under **Members** click **Invite** next to **Invite someone to this project**. That project is already selected, with the Developer role.

</Step>
<Step>

### Choose their projects

Under **Access**, select **Chosen projects**, select the projects, and choose a role for each. A project you select starts as **Viewer**.

| Role | What they can do |
| --- | --- |
| **Developer** | Deploy, change variables, restart services, read logs, open terminals, and read secret values. |
| **Viewer** | View status and events. They can't read logs, make changes, open terminals, or read secret values. |

A person can have different roles in different projects. Someone with no projects selected can still sign in, but sees only nodes and project names.

![Invite member dialog with Chosen projects selected, blog set to Viewer, and shop set to Developer](../images/shots/members-invite.avif)

Selecting **Admin** gives the person full control over the cluster, including all projects, nodes, and members. Admins can sign in only with passkeys, not GitHub or Google. See [Admin accounts and regular accounts](../reference/permissions.mdx#admin-accounts-and-regular-accounts).

The list shows projects only. If the cluster has other namespaces, click **Also show N namespaces that aren't projects** below it. A namespace is how Kubernetes groups things, and each project is one namespace.

</Step>
<Step>

### Review the change

Click **Review changes**. The dialog lists the account to add and the permissions in each project. If it looks right, click **Invite erin** (`erin` is the username).

![Invitation review dialog showing the new account and project permissions](../images/shots/members-invite-review.avif)

</Step>
<Step>

### Send them the link

Copy the setup link and send it through a channel only the recipient can read.

![Setup link and expiration time shown after creating an invitation](../images/shots/members-invite-link.avif)

The link expires in 7 days and works once. The full link is shown only this time.

</Step>
<Step>

### Check that they can sign in

The person opens the link and adds a passkey. Back on **Members**, their **Passkeys** column shows a number. Then ask them to sign in and open a project you gave them.

![Members page listing each member's role, number of passkeys, and last sign-in](../images/shots/members-list.avif)

</Step>
</Steps>

<Callout type="warn">
Whoever opens a setup link first can add a passkey to the account and sign in. If you sent the link to the wrong person or it leaked, click **Revoke** under **Pending setup links**, then create a new link.
</Callout>

## Change permissions

On the member's row, click **⋯** and select **Change access**. Adjust their projects and roles, click **Review changes**, then click **Save access**.

The change takes effect right away. A terminal the person already has open stays open until they close it.

When you make a member **Admin**, they can sign in only with passkeys. Their sessions signed in through GitHub or Google end. Removing **Admin** turns the account back into a regular one.

## Add a device, or deal with a lost one

To add a backup device for a member, click **⋯** on their row and select **New setup link**. This link expires in 24 hours and works once. Their passkeys and sessions stay.

If a device is lost or stolen, click **⋯** and select **Reset after a lost device**. Select the option to also remove their passkeys, linked accounts, and sessions, then click **Reset and create link**. No one can sign in to the account until the person opens the new link.

![Reset after a lost device dialog, with the option to remove passkeys, linked accounts, and sessions selected](../images/shots/members-reset.avif)

## Remove a member

First, revoke unused links under **Pending setup links**. Then click **⋯** on the member's row, select **Remove member**, and confirm.

This deletes their passkeys, linked accounts, sessions, setup links, and the permissions Zeabur gave them. Projects and services stay.

## If something goes wrong

| What you see | What to do |
| --- | --- |
| **Zeabur Identity isn't installed** | Ask a cluster administrator to install Zeabur Identity, or start Zeabur with the namespace where Zeabur Identity runs. |
| Zeabur doesn't know the Zeabur Identity URL | Start Zeabur with `--issuer-url`. |
| Zeabur Identity isn't accepting setup links | Run Zeabur Identity with `--invitations`. |
| **Zeabur was installed without the member roles** | Upgrade the chart with `memberRoles.enabled=true`, or make the member an admin. [Permissions](../reference/permissions.mdx) has the full table. |
| You can't change your own permissions, reset your account, or remove yourself | Ask another admin. You can add a backup passkey yourself from the account page. |
| The changes have expired | Click **Review changes** again. |
| The person signs in but sees no projects | On **Members**, check that their row lists projects and roles. If not, add them with **Change access**. |

## Do the same with kubectl

A member is a Zeabur Identity `User` in the `zeabur-identity` namespace. Permissions use standard role bindings, all named `zeabur-member-<username>`: one ClusterRoleBinding binds to `zeabur-member` so the person can sign in and see nodes and project names. Each assigned project also has a RoleBinding that binds to `zeabur-project-developer` or `zeabur-project-viewer`. Kubernetes sees the username as `zeabur:<username>`.

The following gives `erin` a regular account with the Developer role in `shop`:

```yaml
apiVersion: identity.zeabur.com/v1alpha1
kind: User
metadata:
  name: erin
  namespace: zeabur-identity
  labels:
    app.kubernetes.io/managed-by: zeabur
spec:
  username: erin
  displayName: Erin Lin
  groups: []
  accountType: Regular
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: zeabur-member-erin
  labels:
    app.kubernetes.io/managed-by: zeabur
    zeabur.com/member: erin
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: zeabur-member
subjects:
  - apiGroup: rbac.authorization.k8s.io
    kind: User
    name: zeabur:erin
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: zeabur-member-erin
  namespace: shop
  labels:
    app.kubernetes.io/managed-by: zeabur
    zeabur.com/member: erin
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: zeabur-project-developer
subjects:
  - apiGroup: rbac.authorization.k8s.io
    kind: User
    name: zeabur:erin
```

To grant admin rights, change `accountType` to `Admin`. No additional role bindings are needed. Don't add `admins` to `groups`; that group comes only from the account type.

After applying the configuration, generate a setup link with `zeabur-identityctl invite` and send it to the person:

```sh
zeabur-identityctl invite --username erin
```

To change permissions, change the RoleBinding's `roleRef` (`roleRef` is immutable, so you must delete and recreate the binding), or create the same RoleBinding in other projects. To remove a member, first delete their role bindings, then their setup links, passkeys, and sessions, and finally their `User`:

```sh
kubectl delete clusterrolebinding,rolebinding -A -l zeabur.com/member=erin
kubectl -n zeabur-identity delete zbinvite,zbcred,zbgrant -l identity.zeabur.com/user=erin
kubectl -n zeabur-identity delete zbuser erin
```

For other options, such as granting permissions through groups or disabling accounts, see [Managing users](https://oss.zeabur.com/docs/identity/managing-users) in the Zeabur Identity docs.

To check with kubectl:

- `kubectl get clusterrolebinding,rolebinding -A -l zeabur.com/member=erin` lists one ClusterRoleBinding and one RoleBinding for each project.
- After signing in, the person runs `kubectl auth whoami` on their computer. The username is `zeabur:erin`.
- An admin can run `kubectl auth can-i --as zeabur:erin -n shop create deployments`. It prints `yes` for a Developer and `no` for a Viewer.

Removing a member leaves role bindings that Zeabur didn't create but that name `zeabur:<username>`. An admin reviews those separately.
