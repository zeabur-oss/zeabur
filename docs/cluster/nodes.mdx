Go to **Cluster** → **Overview** → **Nodes** to check each host's status. To run services on another host, see [Add a node](#add-a-node). Before taking a host down for maintenance, select **Stop scheduling** from the node's action menu. Use kubectl's `drain` when you also need to move replicas off the node.

![Node list in the cluster overview](../images/shots/cluster-nodes.avif)

## Before you begin

- `zeabur-installer node add` works on K3s and RKE2 clusters that Zeabur Installer created. On K3s you can add workers only. On RKE2 you can add workers and servers, and three servers keep the control plane running when one goes down. For other clusters, use the tool you originally installed them with.
- Prepare a new VM with root access and the same `zeabur-installer` binary used to install the first server.
- Keep all nodes with the same hosting provider in the same region. Different availability zones within that region are fine. Across providers or regions, latency slows down etcd, the Kubernetes API, and storage.
- Stopping and resuming scheduling requires permission to modify Node objects. Run `drain` and `delete node` in the kubectl terminal with your own permissions. Opening a node terminal requires an admin account.

Open these firewall ports between nodes:

| Direction | K3s | RKE2 |
| --- | --- | --- |
| To servers | TCP 6443 | TCP 9345, 6443 |
| Between all nodes | TCP 10250, UDP 4789 (Calico VXLAN) | TCP 10250, 9099, UDP 8472 (Canal VXLAN) |
| Between servers | None | TCP 2379–2381 |

Allow the UDP port only between cluster nodes. Don't expose it to the internet. The installer's connection check can't test UDP. If the port is blocked, replicas on different nodes can't reach each other.

## Add a node

Node-joining commands are part of `zeabur-installer`. For all options, see [Installer commands](../reference/installer.mdx#node-add-and-node-sync).

<Steps>
<Step>

### Generate the join configuration on an existing server

Sign in to an existing server as root and run:

```sh
sudo zeabur-installer node add --ttl 1h
```

The command prints what to run on the new VM: the configuration to write to `/etc/zeabur-installer/config.yaml`, followed by `plan` and `apply`. Treat the token in the output like a password. Don't post it publicly.

Worker nodes join with an expiring bootstrap token. `--ttl` defaults to 1 hour, with a maximum of 24 hours. On RKE2, include `--role server` to add a server (control plane). This uses the cluster's server token, which doesn't expire. K3s refuses `--role server` because it runs one server with SQLite. If the new VM can't reach the server's private address, use `--address` to specify an address it can reach.

If the cluster runs Longhorn or a zot mirror, the output automatically includes the corresponding configuration. If the config file still has `profile: single-node`, the output reminds you to change it to `multi-node` and run `apply` again.

</Step>
<Step>

### Run on the new VM

Copy the `zeabur-installer` binary used to install the first server to the new VM. As root, paste the output from the previous step. It writes the config file, then runs:

```sh
zeabur-installer plan
zeabur-installer apply
```

`plan` only lists network checks and warnings. It doesn't change anything. Resolve any warnings before continuing. `apply` installs the K3s agent or RKE2 and waits for the node to be ready before exiting.

</Step>
<Step>

### Verify on the server

```sh
sudo zeabur-installer node sync
# K3s
sudo k3s kubectl get nodes -o wide
# RKE2
sudo /var/lib/rancher/rke2/bin/kubectl --kubeconfig /etc/rancher/rke2/rke2.yaml get nodes -o wide
```

`node sync` adds the new node's addresses to the baseline network policies created by Installer. Newly joined servers sync automatically. After a worker node joins, you must run this command manually on a server. Until then, network policies block traffic from the new node. Once the new node shows `Ready`, revoke the worker node's token. Replace `<ID>` with the ID from the last line of the `node add` output:

```sh
# K3s
sudo k3s kubectl -n kube-system delete secret bootstrap-token-<ID>
# RKE2
sudo /var/lib/rancher/rke2/bin/kubectl --kubeconfig /etc/rancher/rke2/rke2.yaml \
  -n kube-system delete secret bootstrap-token-<ID>
```

This doesn't affect nodes that have already joined. The token can no longer be used to join the cluster.

</Step>
</Steps>

On RKE2, etcd needs a majority of servers to operate. To keep running with one server down, you need at least three servers. With only two, taking either server down stops the entire cluster. A K3s cluster has one server; when it goes down, the control plane stops until it returns.

## Take a node down for maintenance

### Reboot only

Select **Stop scheduling** from the node menu. The node row shows that scheduling has stopped, and no new replicas are scheduled on the node. Existing replicas stay where they are. If you're only rebooting, this is enough. You don't need to run `drain`.

You can also click **Open kubectl terminal** next to the heading on Zeabur's **Cluster** page and run:

```sh
kubectl cordon <node>
```

Replace `<node>` with the node name. Resume scheduling after the reboot.

### Move replicas before maintenance

Click **Open kubectl terminal** next to the heading on Zeabur's **Cluster** page. First, list the replicas on the node and the disks they use:

```sh
kubectl get pods -A --field-selector spec.nodeName=<node> -o custom-columns=NS:.metadata.namespace,POD:.metadata.name,PVC:.spec.volumes[*].persistentVolumeClaim.claimName
```

Check the disks in the list to identify which use `local-path` volumes on this node. The data in these volumes exists only on this node. It won't move to another node with the replica.

After checking, run:

```sh
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data
```

`drain` stops scheduling on the node and evicts replicas so their controllers can recreate them on other nodes. Replicas managed by DaemonSet stay where they are. Keep the following in mind:

- `drain` respects PodDisruptionBudget. If eviction is blocked, it keeps retrying until eviction is allowed.
- `drain` stops when it encounters a replica that isn't managed by a controller. These replicas won't restart automatically after deletion. Add `--force` to the end of the command only after confirming they're safe to delete.
- `--delete-emptydir-data` clears the `emptyDir` scratch data of evicted replicas.
- Replicas using this node's `local-path` volumes are also evicted. Recreated replicas can't use these volumes on other nodes and remain `Pending` until the original node returns. `drain` doesn't delete the data. For these replicas, the result is the same as taking the node down directly: they must wait for it to return.

If Zeabur itself runs on this node, the page disconnects for about a minute during `drain`. Refresh the page and sign in again. The kubectl terminal also disconnects; reopen it.

Wait for `drain` to finish before taking the node down for maintenance.

## Resume scheduling

Once maintenance is complete and the node is running again, select **Resume scheduling** from the node menu.

You can also click **Open kubectl terminal** next to the heading on Zeabur's **Cluster** page and run:

```sh
kubectl uncordon <node>
```

New replicas can now be scheduled on the node.

## Remove a node

**Don't remove the cluster's only node or its last control plane node.**

First, click **Open kubectl terminal** next to the heading on Zeabur's **Cluster** page and check the number of control plane nodes:

```sh
kubectl get nodes -l node-role.kubernetes.io/control-plane
```

If only one control plane node remains, don't delete it. If removal leaves fewer than three server nodes, losing one more will stop the control plane.

Data in `local-path` volumes exists only on this VM. After you remove the node, replicas using these volumes have nowhere to start. Follow the steps in “Take a node down for maintenance” to check replicas and volumes, then run `drain`. Delete the node only after it finishes:

```sh
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data
kubectl delete node <node>
```

Next, sign in to the removed VM and run these as `root`, using the uninstall script for the cluster's distribution:

```sh
/usr/local/bin/k3s-agent-uninstall.sh   # K3s
/usr/local/bin/rke2-uninstall.sh        # RKE2
zeabur-installer uninstall --purge
```

**After deleting the Kubernetes node, you must also complete the uninstall on the VM.** Until you do, the VM rejoins the cluster whenever `k3s-agent` or RKE2 restarts.

Volumes under `/var/lib/zeabur/storage` remain on the VM. Delete them manually only after confirming you no longer need the data.

Finally, return to the server where you run Zeabur Installer and run:

```sh
sudo zeabur-installer node sync
```

This removes the deleted node's addresses from the baseline network policies.

## Open a node terminal

A **Node terminal** opens a shell with full root access on the host. Sign in with an admin account and click **Node terminal** in the node row. Review the terminal replica that will be created and the time limit, then click **Open terminal**.

<Callout type="warn">
The node terminal can modify every file, process, and network interface on the host. Actions in this terminal bypass Zeabur and Kubernetes permission checks and can't be undone.
</Callout>

The node records an event with who opened the terminal and when. If the screen shows **Others could enter this terminal**, role bindings allow people other than cluster administrators to create replicas in the terminal's namespace. Remove the listed role bindings, then check again.

When you close the terminal, Zeabur removes the terminal replica. Terminal replicas are kept for at most 30 minutes. If one remains, click **Remove terminal replica** in the terminal replica list below the node, review the change, and confirm.

## Common failures

- Can't reach the server when joining: Check that the new VM can reach the server address printed by `node add` on TCP 6443 (K3s) or TCP 9345 and 6443 (RKE2), along with the other ports in the table above.
- The new node is ready, but services on different nodes can't reach each other: Check UDP 4789 (K3s) or 8472 (RKE2) and whether network policies allow traffic from the new node.
- `drain` is stuck: It's waiting for PodDisruptionBudget to allow eviction or has stopped at a replica that isn't managed by a controller. Run `kubectl get pdb -A` to see which budget is blocking eviction, resolve it, and run the command again.
- A replica is `Pending` on the new node: It uses a `local-path` volume on the old node and must wait for that node to return.
- A terminal replica **Can't start**: Check its events. A failed image download is a common cause.
