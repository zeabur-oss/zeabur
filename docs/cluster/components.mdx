title: View and install cluster components
description: Check which components are installed, their status, and what's missing, then install them from the page or with zeaburctl.
---

Open **Cluster** → **Components**. **Installed** lists detected components, and **Catalog** lists components in Zeabur Catalog. On K3s and RKE2, a cluster administrator installs and removes components here. On other clusters, or to keep components in a GitOps repository, print their manifests with `zeaburctl components export` and apply them yourself.

![Installed components and the catalog on the cluster components page](../images/shots/cluster-components.avif)

## Before you begin

To detect installed components, the components page needs permission to read CRDs and IngressClasses across the cluster and workloads in every namespace.

## Check what's in the cluster

**Installed** lists detected components, their versions, and their installation source (K3s, HelmChart, or Helm). It also marks each version as the Zeabur Catalog **Tested version** or **Newer than tested**. Components that aren't running are marked **Failing**.

In **Catalog**, filter by **Installed** or **Recommended**, or use **Search components** to find components by name or purpose.

If a feature such as backups or notifications already works, but its component card still shows **Install**, the components page hasn't detected it. It was likely installed under a different name or with another method. Find the existing deployment before installing another copy.

## Install from the page

Only someone allowed to do everything in the cluster (`cluster-admin`) can install here: Zeabur hands each chart to the cluster's helm-controller, which installs it with full rights. The cluster must run helm-controller, as K3s and RKE2 do.

<Steps>
<Step>

### Review the steps

Click **Install** on a component card. The dialog lists each step and the objects it writes; click an object to see its YAML. When the component needs another one the cluster lacks, that one comes first. Nothing is written yet.

</Step>
<Step>

### Install

Click **Install**. Zeabur writes one step at a time with your account, and starts the next step once the one before it is ready. Keep the dialog open until every step and health check shows **Ready**; if you close it, click **Install** again to go on from where it stopped. When a health check takes longer than expected, the dialog says what to check.

</Step>
</Steps>

If the dialog says the component is already installed and not by Zeabur, Zeabur leaves it alone. Upgrade or remove it with the tool that installed it.

## Install with zeaburctl

<Steps>
<Step>

### View the command

When the **Add** menu, a template, a build setting or database backups need a missing component, **How to install** opens a dialog with the command to run. It lists every component that action is missing, so you can copy the command as is.

</Step>
<Step>

### Print the manifests and apply them

Use `zeaburctl components export` to print a component's manifest, or to print the Helm command that installs it:

```sh
zeaburctl components export velero > velero.yaml
zeaburctl components export velero --format helm
```

To install several at once, list all their IDs, for example `zeaburctl components export zeabur-builder keel`. The output puts them one after another.

By default, the command prints a K3s/RKE2 `HelmChart`, which the cluster's built-in helm-controller installs. For other clusters, use `--format` to choose `helm`, `flux`, or `argocd`. Required component values appear as `<name>` placeholders. Replace them with actual values, then apply the manifest with `kubectl apply -f` or commit it to a GitOps repository. For command details, see [zeaburctl](../reference/zeaburctl.mdx#components-export).

</Step>
<Step>

### Check the installation

Return to **Cluster** → **Components**. The component and its version should appear under **Installed**. Then check the feature that uses it. For example, check **Cluster** → **Backups** for Velero or **Cluster** → **Notifications** for VictoriaMetrics.

</Step>
</Steps>

### Replace built-in K3s/RKE2 components

If the exported manifest starts with instructions to disable a built-in version, follow the steps for your cluster's distribution on every server before applying it:

- K3s: Add the listed components to `disable` in `/etc/rancher/k3s/config.yaml`, then restart `k3s`.
- RKE2: For metrics-server, add `rke2-metrics-server` to `disable` in `/etc/rancher/rke2/config.yaml`. For Traefik, set `ingress-controller: none` in the same file. Then restart `rke2-server`.

<Callout type="warn">
Disabling the built-in Traefik deletes its CRDs and all IngressRoute and Middleware objects. Ingress traffic stops until the replacement component starts. Disabling the built-in metrics-server makes the metrics API unavailable until the new version starts. Schedule the switch for a time when an interruption is acceptable.
</Callout>

## Remove components

To remove a component Zeabur installed, click **Remove** on its card, check the steps, then click **Remove**. Zeabur deletes its objects in the reverse order; deleting a chart makes helm-controller uninstall it. The dialog lists what stays, such as CRDs and keys. Zeabur refuses while another installed component needs it, or while objects of its custom resources are still in use outside its own namespace, and names them.

Remove a component Zeabur didn't install through the same files or tools you used to install it, such as `kubectl delete -f`, `helm uninstall`, Flux, or Argo CD.

Before you remove one, check that nothing still uses it. For example, custom resources may still exist, Longhorn volumes may remain, or replicas may still pull images from zot. Removing a component that stores data, such as Longhorn, also deletes that data, so back it up first.

After removal, the component's namespace and volumes remain. Some charts also delete CRDs and all their objects; other CRDs remain. Delete what remains by hand once you're sure you no longer need it.

## Where the catalog comes from

Zeabur downloads Zeabur Catalog from `https://oss-catalog.zeabur.com/v1/` and checks for a new release every 10 minutes. It keeps the last release it downloaded in the ConfigMap `zeabur-catalog` in its namespace, so it stays available after a restart or while the catalog is down. The components page shows the release and when it was downloaded.

If Zeabur can't download the catalog and has no saved copy, the page says why and offers **Try again**. Installed components and every service keep working; only installing a component needs the catalog.

### Use a mirror

For a cluster without internet access, serve a copy of the catalog over HTTPS:

1. Download `api-v1.tar.gz` from a [Zeabur Catalog release](https://github.com/zeabur-oss/catalog/releases) and unpack it. It holds a `v1` folder.
2. Serve the folder that holds `v1` with any web server, over HTTPS with a certificate the cluster trusts. For a private CA, see [Trust a private CA](../install/existing-cluster.mdx#trust-a-private-ca).
3. Point Zeabur at it:

   ```sh
   helm upgrade zeabur oci://ghcr.io/zeabur-oss/charts/zeabur \
     --version <version> \
     --namespace zeabur --reset-then-reuse-values \
     --set catalog.url=https://catalog.example.internal/v1/
   ```

The URL must start with `https://`. The catalog only says which charts and images to install; helm-controller and the nodes still pull those from their registries, so mirror them too.

## Common failures

- The components page reports insufficient permissions: Give the cluster administrator the list of missing permissions shown on the page.
- A step shows **Failed**: Its message says why. For a chart, also check the logs of the `helm-install-<name>` Job in `kube-system`.
- The component still doesn't appear under **Installed** after installation: Check the logs for the `helm-install-<name>` Job in `kube-system` and whether the component's workloads have started.
