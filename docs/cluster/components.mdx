title: View and install cluster components

Open **Cluster** → **Components**. **Installed** lists detected components, and **Catalog** lists components in Zeabur Catalog. On K3s and RKE2, a cluster administrator installs and removes components here. On other clusters, or to keep components in a GitOps repository, print their manifests with `zeaburctl components export` and apply them yourself.

![Installed components and the catalog on the cluster components page](../images/shots/cluster-components.avif)

A card shows how much memory the component uses, from Zeabur Catalog's measurement of its pods on a fresh cluster. For a component that does work, such as builds, the figure includes one unit of that work: Zeabur Builder's figure is for one build. Zeabur OSS doesn't check whether the cluster has that much free. Compare the figure with the free memory on **Cluster** → **Nodes**.

## Before you begin

To detect installed components, the components page needs permission to read CRDs and IngressClasses across the cluster and workloads in every namespace.

## Check what's in the cluster

**Installed** lists detected components, their versions, and their installation source (K3s, HelmChart, or Helm). It also marks each version as the Zeabur Catalog **Tested version** or **Newer than tested**. Components that aren't running are marked **Failing**.

In **Catalog**, filter by **Installed** or **Recommended**, or use **Search components** to find components by name or purpose.

If a feature such as backups or notifications already works, but its component card still shows **Install**, the components page hasn't detected it. It was likely installed under a different name or with another method. Find the existing deployment before installing another copy.

## Install from the page

Only someone allowed to do everything in the cluster (`cluster-admin`) can install here: Zeabur OSS hands each chart to the cluster's helm-controller, which installs it with full rights. The cluster must run helm-controller, as K3s and RKE2 do.

If you manage the cluster with Flux or Argo CD, install the component through it instead. The install dialog shows the `zeaburctl components export` commands that print the component's manifests for Flux or Argo CD. Run one and commit its output to the repository the cluster reads, as [Install with zeaburctl](#install-with-zeaburctl) describes.

<Steps>
<Step>

### Review the steps

Click **Install** on a component card. The dialog lists each step and the objects it writes; click an object to see its YAML. When the component needs another one the cluster lacks, that one comes first. Nothing is written yet.

</Step>
<Step>

### Install

Click **Install**. Zeabur OSS writes one step at a time with your account, and starts the next step once the one before it is ready. The browser tab drives the install, so keep Zeabur OSS open in it until every step and health check shows **Ready**. You can click **Hide** and use other pages meanwhile: a line at the bottom of the page shows the step, and clicking it opens the dialog again. Closing or reloading the tab asks first, because it stops the install between two steps.

An install that stopped shows **Incomplete** on its card and on **Cluster** → **Backups**. Any cluster administrator can click **Manage** on the card to go on from where it stopped; enter the component's values again if it asks for them. When a health check takes longer than expected, the dialog says what to check.

</Step>
</Steps>

If the dialog says the component is already installed and not by Zeabur OSS, Zeabur OSS leaves it alone. Upgrade or remove it with the tool that installed it.

## Install with zeaburctl

<Steps>
<Step>

### View the command

When the **Add** menu, a template, a build setting or database backups need a missing component, **How to install** opens a dialog with the command to run. It lists every component that action is missing, so you can copy the command as is.

</Step>
<Step>

### Print the manifests and apply them

Use `zeaburctl components export` to print a component's manifest, or to print the Helm command that installs it:

```sh
zeaburctl components export velero > velero.yaml
zeaburctl components export velero --format helm
```

To install several at once, list all their IDs, for example `zeaburctl components export zeabur-builder keel`. The output puts them one after another.

By default, the command prints a K3s/RKE2 `HelmChart`, which the cluster's built-in helm-controller installs. For other clusters, use `--format` to choose `helm`, `flux`, or `argocd`. Required component values appear as `<name>` placeholders. Replace them with actual values, then apply the manifest with `kubectl apply -f` or commit it to a GitOps repository. For command details, see [zeaburctl](../reference/zeaburctl.mdx#components-export).

</Step>
<Step>

### Check the installation

Return to **Cluster** → **Components**. The component and its version should appear under **Installed**. Then check the feature that uses it. For example, check **Cluster** → **Backups** for Velero or **Cluster** → **Notifications** for VictoriaMetrics.

</Step>
</Steps>

### Replace built-in K3s/RKE2 components

If the exported manifest starts with instructions to disable a built-in version, follow the steps for your cluster's distribution on every server before applying it:

- K3s: Add the listed components to `disable` in `/etc/rancher/k3s/config.yaml`, then restart `k3s`.
- RKE2: For metrics-server, add `rke2-metrics-server` to `disable` in `/etc/rancher/rke2/config.yaml`. For Traefik, set `ingress-controller: none` in the same file. Then restart `rke2-server`.

<Callout type="warn">
Disabling the built-in Traefik deletes its CRDs and all IngressRoute and Middleware objects. Ingress traffic stops until the replacement component starts. Disabling the built-in metrics-server makes the metrics API unavailable until the new version starts. Schedule the switch for a time when an interruption is acceptable.
</Callout>

## Install with an agent

A coding agent such as Claude Code or Codex can install components for you with `zeaburctl components export`. Put the component IDs in this prompt and paste it:

```text
Install the Zeabur Catalog components <ids> on my cluster. Follow https://oss.zeabur.com/docs/zeabur/cluster/components.md.
Ask me which kubeconfig context to use, and use it in every kubectl, helm and zeaburctl doctor command (--context, or --kube-context for helm). Use a zeaburctl of the same version as my Zeabur OSS.
Ask me which format fits my cluster: flux or argocd when Flux or Argo CD manages it, else helmchart on K3s and RKE2, else helm.
Install only what `zeaburctl components export <ids> --format <format>` prints. Don't choose chart versions, change values or run helm commands of your own.
Ask me for the value of every <name> placeholder in the output, and put my answer in its place.
Before each write to the cluster, show me what changes and wait for my go-ahead: the output of `kubectl diff --server-side -f <file>` for a manifest, the exact printed commands for the helm format.
Each component's output ends with "Zeabur's objects for <id>". Apply those only after that component is installed and its pods are ready.
When you finish, run `zeaburctl doctor --output json` and report what it says.
```

The agent asks you for the context, the format and each placeholder, and shows you each change before it applies it. On a cluster that Flux or Argo CD manages, you can have it write the files into the repository Flux or Argo CD syncs from instead.

## Change settings of built-in components

K3s and RKE2 install some components themselves, such as Traefik. **Installed** shows K3s or RKE2 as their source, and their cards have no **Install** or **Manage** button, because Zeabur OSS changes only components it installed. Don't edit their manifest files in the server's manifests directory: K3s rewrites them every time it starts.

When the distribution installs a component as a Helm chart, its card names its `HelmChart`, for example `traefik` on K3s and `rke2-traefik` on RKE2. To change the chart's values, write a `HelmChartConfig` with the same name in `kube-system`. helm-controller passes its `valuesContent` to Helm as an extra values file and upgrades the chart. On K3s, metrics-server is plain manifests, not a chart, so its card names no chart and a `HelmChartConfig` doesn't change it.

For example, to make Traefik on K3s trust `X-Forwarded-*` headers on its `web` entry point from a load balancer in `10.0.0.0/8`, save this on a server as `/var/lib/rancher/k3s/server/manifests/traefik-config.yaml`:

```yaml
apiVersion: helm.cattle.io/v1
kind: HelmChartConfig
metadata:
  name: traefik
  namespace: kube-system
spec:
  valuesContent: |-
    ports:
      web:
        forwardedHeaders:
          trustedIPs:
            - 10.0.0.0/8
```

Replace `10.0.0.0/8` with your load balancer's addresses. On RKE2, set `metadata.name` to `rke2-traefik` and save the file as `/var/lib/rancher/rke2/server/manifests/rke2-traefik-config.yaml`. The chart's values are in its own documentation; RKE2's charts are in the [RKE2 charts repository](https://github.com/rancher/rke2-charts/tree/main/charts).

To undo it, delete the file, then delete the object (`rke2-traefik` on RKE2). Deleting the file alone leaves the object in the cluster:

```sh
kubectl delete helmchartconfig traefik -n kube-system
```

helm-controller then upgrades the chart again with the distribution's values.

## Remove components

To remove a component Zeabur OSS installed, click **Manage** on its card. When every step and health check is ready, the dialog removes; while an install is unfinished, for example when a health check fails, the dialog shows **Remove** next to **Install**. Check the steps, then click **Remove**. Zeabur OSS deletes its objects in the reverse order; deleting a chart makes helm-controller uninstall it. The dialog lists what stays, such as CRDs and keys. Zeabur OSS refuses while another installed component needs it, or while objects of its custom resources are still in use, and names them. Objects in use are ones Zeabur OSS wrote for another component, and others outside the component's own namespace.

Remove a component Zeabur OSS didn't install through the same files or tools you used to install it, such as `kubectl delete -f`, `helm uninstall`, Flux, or Argo CD.

Before you remove one, check that nothing still uses it. For example, custom resources may still exist, Longhorn volumes may remain, or replicas may still pull images from zot. Removing a component that stores data, such as Longhorn, also deletes that data, so back it up first.

After removal, the component's namespace and volumes remain. Some charts also delete CRDs and all their objects; other CRDs remain. Delete what remains by hand once you're sure you no longer need it.

## Where the catalog comes from

Zeabur OSS downloads Zeabur Catalog from `https://oss-catalog.zeabur.com/v1/`, and again once its copy is more than 10 minutes old. It keeps the last release it downloaded in the ConfigMap `zeabur-catalog` in its namespace, so it stays available after a restart or while the catalog is down. The components page shows the release and when it was downloaded.

If Zeabur OSS can't download the catalog and has no saved copy, the page says why and offers **Try again**. Installed components and every service keep working; only installing a component needs the catalog.

### Use a mirror

For a cluster without internet access, serve a copy of the catalog over HTTPS:

1. Download `api-v1.tar.gz` from a [Zeabur Catalog release](https://github.com/zeabur-oss/catalog/releases) and unpack it. It holds a `v1` folder.
2. Serve the folder that holds `v1` with any web server, over HTTPS with a certificate the cluster trusts. For a private CA, see [Trust a private CA](../install/existing-cluster.mdx#trust-a-private-ca).
3. Point Zeabur OSS at it:

   ```sh
   helm upgrade zeabur oci://ghcr.io/zeabur-oss/charts/zeabur \
     --version <version> \
     --namespace zeabur --reset-then-reuse-values \
     --set catalog.url=https://catalog.example.internal/v1/
   ```

The URL must start with `https://`. The catalog only says which charts and images to install; helm-controller and the nodes still pull those from their registries, so mirror them too.

[Template updates](../reference/telemetry.mdx#template-updates) read the same address.

## Common failures

- The components page reports insufficient permissions: Give the cluster administrator the list of missing permissions shown on the page.
- A step shows **Failed**: Its message says why. For a chart, also check the logs of the `helm-install-<name>` Job in `kube-system`.
- The component still doesn't appear under **Installed** after installation: Check the logs for the `helm-install-<name>` Job in `kube-system` and whether the component's workloads have started.
