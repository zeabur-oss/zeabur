---
title: Deploy private repositories with a GitHub App
description: Create a GitHub App for the cluster and grant it to projects, so members can pick a GitHub repository and deploy without setting up a deploy key.
---

After you set up the cluster's GitHub App, project members can pick a GitHub repository when they add a service. Private repositories don't need a separate deploy key or token. Create the App in **Cluster** → **GitHub**, install it on the GitHub account or organization that holds the repositories, then grant it to projects. You can also select **Connect GitHub** from **Deploy from Git** in a project and follow the on-screen steps.

## Before you start

- Zeabur Builder is installed in the cluster, so the `builder-system` namespace exists. If it doesn't, Zeabur says Zeabur Builder isn't installed.
- You can write secrets and config files in `builder-system`. Usually only a cluster administrator can.
- You can create an App on GitHub. To create it under an organization, you must be an owner of that organization.

## Create and install the App

<Steps>
<Step>

### Enter the App name

Go to **Cluster** → **GitHub**, select **Create GitHub App**, and fill in:

| Field | What to enter |
| --- | --- |
| **Name on GitHub** | The default is "Zeabur" plus the cluster name, at most 34 characters. It can't match another App's name on GitHub. |
| **Organization** | Leave this empty to create the App under your own account. |
| **Webhook URL** | Starts with `https://`. Fill this in only when Zeabur Builder has a webhook receiver enabled. If you leave it empty, Zeabur Builder checks GitHub once a minute for new commits. |

![The Create GitHub App form, with Name on GitHub, Organization, and Webhook URL, and Continue on GitHub](../images/shots/github-app-create.avif)

</Step>
<Step>

### Create it on GitHub and save it back to Zeabur

Select **Continue on GitHub** and confirm on GitHub. The App is private. It can only read repository contents and write commit statuses. If you set a webhook URL, it also receives push events.

GitHub sends you back to Zeabur. Review the secret to save (the private key isn't shown), then select **Save the GitHub App**. Finish this step within one hour of selecting **Create GitHub App**.

If the cluster already has an App, the new one replaces it. Services built with the old App pick up new commits again only after you grant the new App to their projects.

</Step>
<Step>

### Install it on the account that holds the repositories

Select **Install on GitHub**. On GitHub, choose the account or organization, then choose **All repositories** or specific repositories. Back in Zeabur, **Installed on** lists it.

![The cluster's GitHub tab, with installed accounts acme and bob, each showing the projects it's granted to](../images/shots/github-app-installed.avif)

</Step>
<Step>

### Grant it to projects

On the account row, select **Choose projects** and check the projects to grant. Members of those projects can deploy repositories under this account that the App can read. Select **Review changes**, then **Apply**.

Selecting **Connect GitHub** from **Deploy from Git** in a project follows the same steps to grant the account to that project.

Projects you uncheck can no longer build from this account's repositories.

![The project list with shop checked, then Review changes and Apply](../images/shots/github-app-grant.avif)

</Step>
</Steps>

## Pick a repository in the project

In a granted project, add a service, choose **GitHub** as the source, and find the repository with **Search repositories**. Access shows "Read through the cluster's GitHub App. Nothing else to set up." The other steps are the same as [Build and deploy a service from Git](../deploy/git.mdx).

The list contains the repositories the App could read when you granted it to the project, and the page shows the update time. When a repository is added on GitHub, the list updates only after you apply again from **Choose projects**.

## Do the same with kubectl

Zeabur Builder reads the App's credentials from the Secret `github-app` in `builder-system`. These values are all on the App's settings page on GitHub. Generate the private key there and download it. For GitHub Enterprise Server, add an `api-url` key with its API URL. The annotation only lets Zeabur link to the App's page.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: github-app
  namespace: builder-system
  annotations:
    builder.zeabur.com/github-app: https://github.com/apps/zeabur-example
type: Opaque
stringData:
  app-id: "123456"
  client-id: Iv23liEXAMPLE
  private-key: |
    -----BEGIN RSA PRIVATE KEY-----
    (the private key downloaded from GitHub)
    -----END RSA PRIVATE KEY-----
  webhook-secret: example-webhook-secret
```

The ConfigMap `github-app-installations` in the same namespace specifies which projects can use each installation. The key is the installation ID (the number at the end of the GitHub installation page URL). The value is a comma-separated list of project names. `*` means every project:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: github-app-installations
  namespace: builder-system
data:
  "87654321": shop, blog
```

Zeabur also writes a config file `zeabur-github-app` (label `zeabur.com/github-app: "true"`) in each granted project. It records the repositories the App could read at that time, so members without permission to read `builder-system` can still pick a repository. Zeabur Builder doesn't read it. You can omit it when you set this up with kubectl. The list on screen is then empty, and you enter the repository URL yourself.

A service's Build sets the installation with `spec.source.githubApp.installationId`:

```yaml
apiVersion: builder.zeabur.com/v1alpha1
kind: Build
metadata:
  name: web
  namespace: shop
  labels:
    app.kubernetes.io/name: web
spec:
  builderRef: railpack
  source:
    git:
      url: https://github.com/example/web.git
      ref: HEAD
    githubApp:
      installationId: 87654321
  output:
    image: registry.example.com/shop/web
  notify:
    - type: keel
      url: http://keel.keel.svc.cluster.local:9300/v1/webhooks/native
```

## Check the result

- The **GitHub App** section shows the App name and **Open on GitHub**. **Installed on** lists the accounts and the projects they're granted to.
- `kubectl -n builder-system get secret github-app` and `kubectl -n builder-system get configmap github-app-installations -o yaml` both find the objects, and the config file contains your installation ID.
- For a service deployed from a private repository, the first build on the **Builds** tab succeeds. `kubectl -n shop get build web` shows its status too.

## Troubleshooting

| Situation | What to do |
| --- | --- |
| The page says Zeabur Builder isn't installed | Install Zeabur Builder first. See [View and install cluster components](./components.mdx). |
| You can't select **Create GitHub App** | You don't have permission to write a secret in `builder-system`. Ask a cluster administrator. |
| Back in Zeabur, the page says GitHub didn't send back a code | Create the App again from the same page. |
| **Installed on** can't be read | Zeabur can't reach GitHub, or the App's private key is wrong. Generate a new private key on GitHub and update `private-key` in the secret. |
| The repository doesn't appear in the project | The App installation doesn't include this repository, or the list is stale. Change the installation's repositories on GitHub, then apply again from **Choose projects**. |
| A build starts a minute after the push | No webhook is set, so Zeabur Builder checks once a minute. |

## Remove

Uninstall or delete the App on GitHub, then delete the configuration on the cluster:

```sh
kubectl -n builder-system delete secret github-app
kubectl -n builder-system delete configmap github-app-installations
kubectl delete configmap -A -l zeabur.com/github-app=true
```

Services built with the App remain. They run the image from the last build and don't build new commits. To keep building, switch them to a deploy key or an access token. See [Build and deploy a service from Git](../deploy/git.mdx).
