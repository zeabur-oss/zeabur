Put domains, component choices, and host settings in YAML, then run `zeabur-installer --config config.yaml plan` to preview the installation. The default file path is `/etc/zeabur-installer/config.yaml`. Field names are camelCase. The installer stops on misspelled or unknown fields.

The web interface saves its choices to this same file. For installation through the web interface, see [Install Zeabur on a server](../get-started/quickstart.mdx). For command-line installation, see [Install with a configuration file and commands](../get-started/advanced-install.mdx). For command options, see [Installer commands](./installer.mdx).

## Configuration for creating a cluster

This example uses your own domains. Both DNS names must point to the server, and port `80` must be reachable from the internet so Let's Encrypt can complete HTTP-01 validation.

```yaml title="/etc/zeabur-installer/config.yaml"
preset: minimal
profile: single-node
access:
  mode: domain
  identity: login.example.com
  zeabur: zeabur.example.com
  invitations: true
zeabur: true
host:
  requireEncryptedDisk: true
```

### Top-level fields

| Field | Default | Purpose |
|---|---|---|
| `use` | `team` | `team` is for teams. Set `personal` for personal use; see [Configuration for personal use](#configuration-for-personal-use) for supported fields |
| `distribution` | `k3s` | `k3s` or `rke2`. See [`distribution` and versions](#distribution-and-versions) |
| `access` | Required | Domains and certificate mode for the sign-in service and Zeabur |
| `preset` | `standard` | `minimal`, `standard`, or `secure` |
| `profile` | `single-node` | `single-node` or `multi-node`; selects the Catalog's component settings for that profile |
| `enable` | `[]` | Capabilities or full component IDs to add |
| `disable` | `[]` | Capabilities or full component IDs to exclude |
| `allowDataLoss` | `[]` | Component IDs whose removal you're allowing to delete their data, such as `replicated-storage/longhorn` |
| `zeabur` | `true` | Install Zeabur Identity and Zeabur. `false` installs only K3s/RKE2 and the selected components |
| `inputs` | `{}` | Non-secret input values grouped by component ID |
| `secretFiles` | `{}` | Secret file paths grouped by component ID |
| `k3sVersion`, `rke2Version` | Versions pinned by the installer | Override the K3s or RKE2 version |
| `host` | Empty | Extra names for the API certificate and disk encryption requirements |
| `sources` | Empty | Optional overrides for the pinned Catalog, images, and chart using your own versions |

`zeabur: false` only determines what this installation installs. It doesn't remove an existing Zeabur installation. To remove it, use [`uninstall`](./installer.mdx#uninstall).

### `access`

| Field | Default and rules |
|---|---|
| `mode` | Required. `domain` gets certificates from Let's Encrypt through cert-manager (HTTP-01). `local` creates a private CA on the server and is only suitable for test machines |
| `identity` | Required. Zeabur Identity's hostname. Its issuer is `https://<identity>` |
| `zeabur` | Required. Zeabur's hostname. It must differ from `identity` |
| `invitations` | `true`. Whether to accept setup links generated on Zeabur's **Members** page. Turn this off when members are managed only through version control |
| `suffixes` | Defaults to `<address>.sslip.io` when the server has a public address, such as `203-0-113-7.sslip.io`; otherwise, none. New services' URLs are suggested under these app domains, using the first one by default, such as `[apps.example.com]`. Each domain needs a wildcard record, `*.apps.example.com`, pointing to the server; see [Set up DNS records](../configure/dns.mdx). Set `[]` to stop suggesting URLs |

Hostnames must not include `https://`, a port, or a path. Use only lowercase letters, numbers, hyphens, and dots, with at least two labels. Each label can have at most 63 characters and can't start or end with a hyphen. The full hostname can have at most 253 characters.

Both the browser and the server must be able to resolve these two names. Replicas resolve names through DNS and can't see entries in the host's `/etc/hosts`. In `local` mode, the CA certificate is at `/var/lib/rancher/zeabur-installer/local-ca.crt`. Import it into the trust store on the user's computer so the browser trusts both URLs.

### Component selection

- `minimal`: ingress, certificates, and metrics-server—the components Zeabur needs to be reachable and show resource usage.
- `standard`: everything the Catalog recommends for this profile, plus `builds` (Zeabur Builder and zot), `image-updates` (Keel), and `databases/cloudnative-pg`, so you can deploy from images or Git and create PostgreSQL databases right after installation. Zeabur Builder builds in a privileged buildkitd, so a build that escapes its sandbox reaches the node; add `builds` to `disable` if you don't need it.
- `secure`: `standard` plus runtime detection, vulnerability scanning, and intrusion prevention.

`enable` accepts capabilities, such as `runtime-security`, or full component IDs, such as `volume-backup/velero`. A component's dependencies are added with it. If `disable` excludes a component that another component needs, `plan` names both and stops. The `plan` output lists the final components, their installation order, and the reasons for exclusions.

A component removed from the list is removed by the next `apply`. If removing a component also deletes its data, add it to `allowDataLoss` first. See [Remove a component](./installer.mdx#remove-components).

```yaml
inputs:
  volume-backup/velero:
    bucket: backups
    s3-url: https://s3.example.com
```

The Catalog defines each component's inputs and their types. If a required value is missing, `plan` names the field to add.

The installer fills in `kube-api-cidr` for External Secrets (the subnet containing the node address) and `cluster-ip` for Zeabur Builder (zot's fixed address). A value in `inputs` overrides it.

Velero also accepts the installer's own `region` input, the bucket's region. It defaults to `us-east-1`; Cloudflare R2 needs `auto`. The web interface asks for the access key ID and secret access key separately and writes the `credentials` file from them.

### `secretFiles`

Specify secret inputs as file paths, and set the files' permissions to `0600`:

```yaml
secretFiles:
  volume-backup/velero:
    credentials: /root/secrets/velero-credentials
```

```sh
sudo chmod 0600 /root/secrets/velero-credentials
```

Use the format the component's input requires for the file contents. The installer uses the file to create the secret the component needs. Keep secret values in files, not in `inputs`. If a secret the Catalog marks `generate: random` has no file specified, the first `apply` generates it, and later runs reuse it.

### Storage classes

The installer always creates `local-path`, which stores data on the node at `/var/lib/zeabur/storage`. When Longhorn is installed, the Catalog's settings for the profile determine the default: `multi-node` uses `longhorn`, and `single-node` keeps `local-path`. `plan` lists the default class and the other classes.

- `local-path` volumes stay on their original node. Changing the default class doesn't move existing data.
- When Longhorn becomes the default, the installer changes its previously default `local-path` to a non-default class.
- If the cluster already has another default class, the installer keeps it. If this installation would make Longhorn the default, `apply` stops. Remove the default annotation from the existing class, then run it again.

When Longhorn is selected, `apply` installs the iSCSI initiator and NFS client on this host, loads `iscsi_tcp`, and starts `iscsid`. Every node running Longhorn needs these. See [Add nodes](../cluster/nodes.mdx).

### `distribution` and versions

Leave `distribution` out to install K3s. Set `rke2` for a server with 8 GiB of memory or more, or to run the control plane on three servers later.

| Field | Default and purpose |
|---|---|
| `distribution` | `k3s`. K3s uses less memory and runs one server, to which you can add workers. `rke2` lets you add workers and servers; three servers keep the control plane running when one goes down |
| `k3sVersion` | The version pinned by the installer. Set this to use another K3s release, such as `v1.37.1+k3s1`. Only with `distribution: k3s` |
| `rke2Version` | The version pinned by the installer. Set this to use another RKE2 release, such as `v1.37.1+rke2r1`. Only with `distribution: rke2` |

Setting the version field of the other distribution stops the installer, for example: `rke2Version applies to distribution: rke2; this one is k3s (set k3sVersion)`.

Downloads for the default version are checked against digests compiled into the installer. Downloads for another version can only be checked against that release's own checksum list. `plan` marks the version as unsupported, and it may not match the Kubernetes versions the Catalog has tested.

### `host`

| Field | Default and purpose |
|---|---|
| `host.tlsSan` | `[]`. Extra DNS names or IP addresses for the Kubernetes API server's certificate. Servers only |
| `host.requireEncryptedDisk` | `false`. When `true`, `apply` stops if the root directory or data directory isn't on an encrypted device |

### `sources`

Release builds of the installer don't need `sources`. They pin versions of Zeabur Catalog, Zeabur Identity, and Zeabur, download them to `/var/lib/rancher/zeabur-installer/downloads`, and check them against SHA-256 hashes compiled into the installer.

Use `sources` to install your own builds, usually for development and testing. Specify only the fields you want to override; the rest keep their pinned versions. A development build of the installer that you compile yourself doesn't pin any versions, so you must specify `catalog`, `identityImage`, `identityctl`, `zeaburImage`, and `zeaburChart`. `plan` lists any that are missing. Replace the paths with the files you've prepared:

```yaml
sources:
  catalog: /root/releases/catalog/index.json
  identityImage: registry.example.com/identity@sha256:<digest>
  identityctl: /root/releases/zeabur-identityctl
  zeaburImage: registry.example.com/zeabur@sha256:<digest>
  zeaburChart: /root/releases/zeabur-chart
```

| Field | Accepted value |
|---|---|
| `catalog` | A local `index.json` |
| `imageArchives` | An array of paths to `docker save` archives, imported when K3s or RKE2 starts |
| `identityImage` | Zeabur Identity's image reference |
| `identityctl` | A local `zeabur-identityctl` binary |
| `zeaburImage` | Zeabur's image reference |
| `zeaburChart` | A Helm chart directory or a packaged `.tgz` |

An archive removed from `imageArchives` is also removed from the K3s or RKE2 import directory on the next `apply`. This list contains archives already on the host. It has nothing to do with private registry access settings.

## Configuration for personal use

With `use: personal` at the top level, the installer installs KubeSolo and components, without the Zeabur dashboard or Zeabur Identity. For instructions and limitations, see [Personal use: Install on a small machine](../get-started/personal.mdx).

```yaml title="/etc/zeabur-installer/config.yaml"
use: personal
enable: [builds]
host:
  tlsSan: [solo.example.com]
```

Only the fields in the table below can appear alongside it. `preset`, `profile`, `access`, `zeabur`, `distribution`, `k3sVersion`, `rke2Version`, and `join` aren't accepted.

| Field | Default and purpose |
|---|---|
| `enable` | `[]`. Ingress and certificates come by default. You can add only `builds` (Zeabur Builder, installed with zot, requires at least 1800 MiB of memory) or component IDs under these capabilities |
| `disable` | `[]`. Capabilities or full component IDs to exclude |
| `allowDataLoss` | `[]`. Same as in the configuration for creating a cluster |
| `inputs` | `{}`. Same as in the configuration for creating a cluster, grouped by component ID |
| `secretFiles` | `{}`. Same as in the configuration for creating a cluster. Files must have permissions `0600` |
| `host.tlsSan` | `[]`. Add an address or domain here if your computer uses it to reach the API |
| `host.requireEncryptedDisk` | `false`. When `true`, `apply` stops if `/var/lib/kubesolo` isn't on an encrypted device |
| `sources.catalog` | Optional. A local Catalog `index.json` to replace the pinned version |

Components use KubeSolo's built-in `local-path` storage class, which stores data under `/var/lib/kubesolo`. KubeSolo, helm-controller, and kubectl are pinned by the installer; no field changes their versions.

## Configuration for joining an existing cluster

A top-level `join` tells the installer to treat this machine as a new node joining an existing cluster and install only K3s or RKE2. Only `distribution`, the version field of that distribution (`k3sVersion` or `rke2Version`), `host`, and `sources.imageArchives` can appear alongside it. Fields for creating a cluster, such as `preset` and `access`, aren't accepted.

Run `zeabur-installer node add` on an existing server to get the complete YAML, then save it on the new host. It includes the token and server settings, so you don't need to assemble them yourself.

| Field | Default and rules |
|---|---|
| `distribution` | `k3s`. The cluster's distribution, as `node add` prints it |
| `join.server` | Required. A server's address: port `6443` on K3s, such as `https://10.0.0.5:6443`, or `9345` on RKE2 |
| `join.role` | `worker`. `server` works on RKE2 only |
| `join.token` | Use either this or `tokenFile`. If you put the token directly in the configuration file, the file must have permissions `0600` |
| `join.tokenFile` | Use either this or `token`. A token file with permissions `0600` |
| `join.serverConfig` | Required for `server`; not accepted for workers. Copy `disable` and `identity` exactly as printed by `node add --role server` |
| `join.longhorn` | `false`. When `true`, installs the host packages Longhorn needs before K3s or RKE2 starts |

Workers don't accept `host.tlsSan`. `distribution` and the version must match the cluster. A worker bootstrap token can't be used to join a server; use the configuration generated by `node add --role server`.

## Troubleshoot configuration issues

- unknown field: Check field capitalization, and remove misspelled keys or keys at the wrong level.
- Invalid hostname: Remove `https://` and the path, and use different names for `identity` and `zeabur`.
- Missing required input: Add the values for the components and fields listed by `plan`, then run `plan` again.
- `join.role: server` on K3s: K3s runs one server with SQLite and takes workers only. For a control plane that keeps running when a server goes down, install RKE2 (`distribution: rke2`) on three servers.
- Incorrect token file permissions: Run `chmod 0600` on the new host. Don't commit configuration files containing tokens to a Git repository.

Run `plan` after editing the configuration file. To remove the product and clean up host files, see [Uninstall Zeabur](../leave/uninstall.mdx).
