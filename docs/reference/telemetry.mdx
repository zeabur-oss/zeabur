title: Experience program
description: What Zeabur OSS, `zeaburctl ui` and Zeabur Desktop send when you join the experience program, what they never send, how Zeabur OSS and zeaburctl check for a newer version, how Zeabur OSS fetches newer templates, and how to turn each off.
---

The experience program sends the version, how many people use Zeabur OSS each day, which features they use, whether `zeaburctl ui` could connect to a cluster, and whether saving changes worked, so we know how many installations are in use and what to fix first. Zeabur OSS installed with Helm and `zeaburctl ui` join by default. Each says so, with how to turn it off: `helm install` and `helm upgrade` when they finish, `zeaburctl ui` each time it starts. Zeabur Desktop follows the setting of `zeaburctl ui`.

## What is sent

Zeabur OSS sends one event each time someone signs in or saves changes, and one the first time each feature below is used with the same values in a UTC day. Each event carries a random installation ID, the properties below and nothing else. With Helm, the chart makes the ID once with `uuidv4` and keeps it in the ConfigMap `zeabur-installation-id`, so upgrades keep it; you can set your own with `telemetry.installationId`. Nothing about your machine goes into it. The data is kept for 13 months.

| Event | Sent by | When |
|---|---|---|
| `signed_in` | Zeabur OSS | Each time someone signs in to Zeabur OSS's web interface |
| `feature_used` | Zeabur OSS, `zeaburctl ui`, Zeabur Desktop | After a call that uses one of the features below succeeds. Zeabur OSS sends it once per UTC day for each feature and set of values; `zeaburctl ui` and Zeabur Desktop send it each time |
| `cluster_connected` | `zeaburctl ui`, Zeabur Desktop | It connected to a cluster with your kubeconfig, or could not |
| `app_change_submitted` | Zeabur OSS | Someone saved changes in Zeabur OSS's web interface or API and got an answer; one event for each save, whatever it changes |

| Property | Events | Values |
|---|---|---|
| `zeabur_version` | `signed_in`, `feature_used` | Zeabur OSS's version, such as `0.1.1` |
| `day` | `feature_used` | The UTC date, such as `2026-10-30` |
| `person` | `signed_in`, `app_change_submitted` | 32 hexadecimal digits that tell people apart within one installation and one day |
| `zeabur_version` | `cluster_connected` | The version of `zeaburctl` or Zeabur Desktop, such as `0.1.1` |
| `zeabur_version` | `app_change_submitted` | Zeabur OSS's version |
| `mode` | `signed_in`, `feature_used`, `cluster_connected`, `app_change_submitted` | `in-cluster` for Zeabur OSS in a cluster, `local` for `zeaburctl ui` and Zeabur Desktop |
| `client` | `cluster_connected`, and `feature_used` when `mode` is `local` | The program that sent it: `desktop` for Zeabur Desktop, `zeaburctl` for `zeaburctl ui`. It lets us count how many people use Zeabur Desktop. |
| `result` | `cluster_connected` | `connected`, `unreachable`, `credential_refused`, `no_read_right` or `other` |
| `result` | `app_change_submitted` | `accepted`, or why not, by the HTTP status you got: `forbidden` (403), `invalid` (422), `conflict` (409), `unreachable` (502, 503 or 504) or `other` |

| `component` | `feature_used` with `component_installed` | The component's ID in Zeabur Catalog, such as `logs/victoria-logs` |
| `policy` | `feature_used` with `auto_update_enabled` | Which new images it takes: `same_tag`, `patch`, `minor` or `major` |
| `kind` | `feature_used` with `database_created`, `domain_added`, `access_limited` or `data_restored` | The database or object storage: `postgresql`, `mongodb`, `mysql`, `mariadb`, `dragonfly` or `object-storage`. The domain: `generated` when the name ends in a suffix Zeabur OSS offers for new services, `custom` otherwise. The limit: `ip_allow`, `basic_auth` or `maintenance`. The restore: `volume` or `project` |
| `$process_person_profile` | all | Always `false`: no person profile is made |
| `$geoip_disable` | all | Always `true`: no location is looked up |

The event doesn't say who the person is. `person` is a keyed hash of the user name and the day. The key is derived from Zeabur OSS's plan key, which stays in the cluster's Secret and is never sent, so we can't work out the user name from it. The same person gets the same `person` all day, even after Zeabur OSS restarts, and a different one the next day, so their days can't be linked.

`feature_used` has no `person`. From Zeabur OSS it says that something was used today, not by whom or how often. From `zeaburctl ui` and Zeabur Desktop it is sent each time, under the random ID of that computer, so the events show how often it is used there. Nothing is sent from your browser: Zeabur OSS's server, or the local service of `zeaburctl ui` or Zeabur Desktop on your computer, sends it after the call succeeds.

`zeaburctl ui` and Zeabur Desktop have no installation ID, so they share a random one, made the first time one of them is about to send an event, never when the program is off. The ID is kept in a file named `local-id` in the `zeabur` folder of the configuration directory: `$XDG_CONFIG_HOME` or `~/.config` on Linux, `~/Library/Application Support` on macOS, `%APPDATA%` on Windows. Only you can read it, and nothing about your machine, kubeconfig, token or user name goes into it.

Events go to PostHog through `oss-nori.zeabur.com` over HTTPS. They wait in a queue in memory and go out in batches, in the background, so sending never delays Zeabur OSS, the link of `zeaburctl ui` or a window of Zeabur Desktop. A request that gets no answer, a rate limit or a server error is tried up to three more times; one that PostHog refuses is not. When Zeabur OSS, `zeaburctl ui` or Zeabur Desktop stops, it waits a few seconds for the queue; events still waiting after that are lost, as nothing is kept on disk. PostHog doesn't keep IP addresses.

## What is never sent

Domains, host names, IP addresses, Git URLs, image or service names, project names, namespace or resource names, emails, user names, logs, credentials, kubeconfigs, cluster addresses, error messages, and the contents of your cluster.

## Turn it off

Any one of these is enough, and `DO_NOT_TRACK` wins over all the others.

- Set `DO_NOT_TRACK=1` in the environment of Zeabur OSS, `zeaburctl ui` or Zeabur Desktop. Any value but empty or `0` counts.
- With Helm, set `telemetry.enabled=false`, as the command below does.
- For `zeaburctl ui`, run `zeaburctl telemetry disable`, which writes `telemetry: false` to `config.yaml` in the same `zeabur` folder as `local-id`, or set `ZEABUR_TELEMETRY=off`. If `config.yaml` can't be read, `zeaburctl ui` sends nothing. `zeaburctl telemetry status` shows which setting is in effect. Zeabur Desktop reads the same `config.yaml` and `ZEABUR_TELEMETRY` when it starts.

To delete the ID of `zeaburctl ui`, run `zeaburctl telemetry reset`. It makes a new one the next time it is about to send an event.

To leave with Helm:

```sh
helm upgrade <release> oci://ghcr.io/zeabur-oss/charts/zeabur --reset-then-reuse-values \
  --set telemetry.enabled=false
```

If a tool such as Argo CD renders the chart with `helm template`, the chart can't read the ConfigMap it made before and makes a new ID on each render. Set `telemetry.installationId` to a UUID of your own, such as the output of `uuidgen | tr 'A-Z' 'a-z'`.

## See what would be sent

Set `ZEABUR_TELEMETRY=debug` and Zeabur OSS prints the exact request body instead of sending it. The line is in its log:

```sh
kubectl -n zeabur set env deployment/zeabur ZEABUR_TELEMETRY=debug
kubectl -n zeabur logs deployment/zeabur | grep telemetry
```

`ZEABUR_TELEMETRY=off` turns it off like `DO_NOT_TRACK` does.

## Update check

Zeabur OSS and `zeaburctl` tell you when a newer version is out and how to upgrade. Nothing upgrades on its own. This check is separate from the experience program and on by default.

**What is checked.** Both read `https://api.github.com/repos/zeabur-oss/zeabur/releases` and leave out drafts. They leave out pre-releases too, unless you run one. If the newest of the rest is newer than yours, you see its version, a link to its release notes and how to upgrade. If any newer release that is not a pre-release has a `### Security` section in its notes, you see that your version has known security problems, with links to those releases.

**Where it runs.**

- The cluster page always shows `Zeabur v<version>`. The Zeabur OSS server asks GitHub at most once an hour, however many people open Zeabur OSS, and the page reads its answer each time it opens and every hour while it stays open. The server keeps the last answer: if GitHub can't be reached, that answer stays and the server tries again a minute later, or after GitHub's reset when GitHub refuses. Browsers make no request to GitHub. **Settings** › **About** shows the version too, and **How to upgrade** opens the steps for how Zeabur OSS was installed, with Helm, Argo CD or Flux. See [Upgrade Zeabur OSS](../upgrade/steps.mdx). Under `zeaburctl ui`, the page shows `zeaburctl`'s own version and how to update it.
- `zeaburctl` checks each time a command runs. The check runs beside the command. When the command ends, `zeaburctl` waits at most a second more for the answer. When a newer version is out, it prints one line to stderr. It keeps nothing on disk. It doesn't check when stderr isn't a terminal or when `CI` is set.
- Without a token, GitHub answers 60 requests an hour from one IP address, shared by everyone behind it. When that's used up, `zeaburctl` says so instead. Set `GH_TOKEN` or `GITHUB_TOKEN` to a GitHub token, the same variables `gh` reads, and `zeaburctl` sends it so the requests count against your own limit. A fine-grained token with no permissions is enough.

**What is sent.** A plain request to GitHub with no ID or cookie, and no token unless you set one for `zeaburctl`. GitHub sees the IP address it comes from. The Zeabur OSS server sends `zeabur` as its user agent, and `zeaburctl` sends `zeaburctl/<version>`.

**Turn it off.** Any one of these is enough. Once it is off, the Zeabur OSS server makes no request to GitHub.

- With Helm, set `updateCheck.enabled=false`. The cluster page then only shows the version.
- Set `DO_NOT_TRACK=1` in Zeabur OSS's environment, or in yours for `zeaburctl`. It turns off the experience program too.
- Set `NO_UPDATE_NOTIFIER` to any value in your environment for `zeaburctl`, including `zeaburctl ui`. It turns off only the update check.

## Template updates

Zeabur OSS offers newer templates without an upgrade. It reads Zeabur Catalog's API and offers the templates there in place of the ones it was built with. Components, and how Zeabur OSS finds them in your cluster, stay as they were built. Services you already deployed from a template don't change. This is separate from the experience program and the update check, and on by default.

**What is fetched.** From `https://oss-catalog.zeabur.com/v1/`: `catalog.json`, which lists each template with a digest of its files, and `templates/<id>.json` for each template whose digest isn't the one Zeabur OSS offers now.

**What Zeabur OSS trusts.** The address it fetches from: `https://oss-catalog.zeabur.com/v1/`, whose HTTPS certificate it checks, or the mirror you set. The files carry no signature, so whoever controls that address decides which templates Zeabur OSS offers. Zeabur OSS then checks each template on its own: it must read, it must be the revision `catalog.json` lists, and the components it needs must be ones this Zeabur OSS knows. A template that fails isn't offered; the one offered before stays, if there is one, and Zeabur OSS asks for it again at the next fetch. When a fetch fails, nothing changes.

**When it runs.** When someone opens the template list, at most once every 6 hours, or 10 minutes after a failure. The Zeabur OSS server fetches; browsers don't. The templates are kept in memory only: after a restart, Zeabur OSS offers the ones it was built with until the next fetch. `zeaburctl ui` doesn't fetch. If a template changes after you open its form, or after you plan it, Zeabur OSS refuses the change; open the form again.

**What is sent.** Plain requests with no ID or cookie. The Zeabur OSS server sends `zeabur` as its user agent. GitHub Pages, which serves `oss-catalog.zeabur.com`, sees the IP address they come from. Nothing about your cluster or its people is sent, so `DO_NOT_TRACK` doesn't turn this off.

**Use a mirror.** For a cluster without internet access, serve a Zeabur Catalog release and set `catalog.url` to it, as [Use a mirror](../cluster/components.mdx#use-a-mirror) describes. Templates come from the same address as components. Zeabur OSS trusts the mirror as it trusts `oss-catalog.zeabur.com`. To trust a release rather than a server, verify its signature before you copy it, as Zeabur Catalog's [Releases and the API](https://oss.zeabur.com/docs/catalog/reference/releases/#verify-and-read-a-release) describes.

**Turn it off.** Any one of these is enough. Once it's off, Zeabur OSS offers only the templates it was built with and makes no request for them.

- With Helm, set `templateFetch.enabled=false`.
- Set `ZEABUR_TEMPLATE_FETCH=false` in Zeabur OSS's environment.
