---
title: Experience program
description: What Zeabur and its installer send when you join the experience program, what they never send, and how to turn it off.
---

The experience program sends the version and how many people use Zeabur each day, so we know how many installations are in use and what to fix first. It's off unless you join: the installer's checkbox is checked by default and asks you at install time; with Helm you turn it on yourself.

## What is sent

Zeabur sends one event about once an hour, and the installer sends one event when an install starts, finishes or fails. Each event carries a random installation ID, the properties below and nothing else. The ID is made once by the installer, or by you with `uuidgen`, and comes from nothing about your machine. The data is kept for 13 months.

| Event | Sent by | When |
|---|---|---|
| `zeabur_day` | Zeabur | About once an hour while at least one person has used Zeabur that day |
| `install_started` | Installer | `apply` begins |
| `install_finished` | Installer | `apply` ends well |
| `install_failed` | Installer | `apply` stops |

| Property | Events | Values |
|---|---|---|
| `zeabur_version` | `zeabur_day` | Zeabur's version, such as `0.1.1` |
| `day` | `zeabur_day` | The UTC date, such as `2026-10-30` |
| `people` | `zeabur_day` | How many different people made an API request that day so far. Zeabur counts them in memory by a hash it keeps only until it restarts; it never sends a name or the hash |
| `mode` | `zeabur_day` | `in-cluster` |
| `installer_version` | the installer's events | The installer's version |
| `profile` | the installer's events | `single-node`, `multi-node` or `personal` |
| `distribution` | the installer's events | `k3s`, `rke2` or `kube-solo` |
| `step` | `install_failed` | Where it stopped: `plan`, `preflight`, `node-prep`, `cluster`, `cluster-setup`, `components`, `identity`, `zeabur` or `record` |
| `error` | `install_failed` | `config`, `plan`, `io`, `command`, `download`, `digest`, `parse` or `other`; never a message |
| `$process_person_profile` | all | Always `false`: no person profile is made |
| `$geoip_disable` | all | Always `true`: no location is looked up |

Events go to PostHog (`us.i.posthog.com`) over HTTPS, one try with a short timeout. If it fails, nothing happens and nothing is retried. IP addresses aren't kept.

## What is never sent

Domains, host names, IP addresses, Git URLs, image or service names, project names, emails, user names, logs, and the contents of your cluster.

## Turn it off

Any one of these is enough, and `DO_NOT_TRACK` wins over all the others.

- **Anywhere:** set `DO_NOT_TRACK=1` in the environment of the installer or of Zeabur. Any value but empty or `0` counts.
- **Installer:** uncheck the box in the web interface, run `zeabur-installer --no-telemetry apply`, or set `telemetry: false` in `/etc/zeabur-installer/config.yaml`.
- **Helm:** set `telemetry.enabled=false` (the default), or leave `telemetry.installationId` out. The chart refuses `telemetry.enabled=true` without an ID.

To join with Helm, make an ID and pass it in:

```sh
uuidgen | tr 'A-Z' 'a-z'
helm upgrade <release> <chart> --reuse-values \
  --set telemetry.enabled=true \
  --set telemetry.installationId=<installation-id>
```

The installer keeps its ID in `/etc/zeabur-installer/installation-id` (mode `0600`) and gives it to Zeabur's chart.

## See what would be sent

Set `ZEABUR_TELEMETRY=debug` and Zeabur or the installer prints the exact request body instead of sending it. For Zeabur, the line is in its log:

```sh
kubectl -n zeabur set env deployment/zeabur ZEABUR_TELEMETRY=debug
kubectl -n zeabur logs deployment/zeabur | grep telemetry
```

`ZEABUR_TELEMETRY=off` turns it off like `DO_NOT_TRACK` does.
