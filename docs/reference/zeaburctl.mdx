---
title: zeaburctl
description: Open Zeabur OSS with the current kubeconfig, upload a folder, check a cluster, or export what installs a component or deploys a template.
---

If you have a kubeconfig that can connect to the cluster, run `zeaburctl ui` to open Zeabur OSS locally. Reads, **Review changes**, and confirmed changes all use that context's permissions. You don't need to install a Zeabur OSS server in the cluster first.

With [Homebrew](https://brew.sh) on a Mac with Apple silicon or on Linux, install it and update it later with `brew upgrade`:

```sh
brew tap zeabur-oss/tap
brew install zeabur-oss/tap/zeaburctl
```

To try the newest pre-release, install `zeaburctl-beta` instead. It installs the same `zeaburctl` command, so uninstall `zeaburctl` first:

```sh
brew install zeabur-oss/tap/zeaburctl-beta
```

Or download the binary for your operating system and processor from [Releases and verification](./releases.mdx). When a newer version is out, `zeaburctl` prints one line about it, at most once a day. See [Update check](./telemetry.mdx#update-check) for what it sends and how to turn it off.

## Commands

```sh
zeaburctl --version
zeaburctl ui
zeaburctl ui --context production --no-browser
zeaburctl doctor --context production --output json
zeaburctl up ./site --project shop --service site
zeaburctl connect orders --project shop
zeaburctl connect shop/api:8080
zeaburctl components export cert-manager
zeaburctl templates export miniflux --project shop --domain rss.example.com
```

`ui`, `doctor`, `up`, `connect`, and `templates export` each accept `--context`. If omitted, they use the current context in kubeconfig. The commands don't modify kubeconfig.

| Command | Result | What it changes |
|---|---|---|
| `ui` | Opens Zeabur OSS in a local browser | Installs no components in the cluster. Changes applied in the interface go directly to the cluster |
| `doctor` | Checks the cluster version, components, and Zeabur Identity settings | Reads only; doesn't change settings |
| `up` | Uploads a folder to a service created from a folder and starts a build | Updates the service's Build and pushes the folder to the registry |
| `connect` | Forwards a local port to a database or service and prints how to reach it | Changes nothing in the cluster |
| `components export` | Prints manifests or Helm commands to install Zeabur Catalog components | Doesn't connect to the cluster or change anything |
| `templates export` | Prints the objects that deploying a Zeabur Catalog template into a project writes | Reads the cluster only to check the components the template needs; changes nothing |
| `telemetry status` | Shows whether `zeaburctl ui` sends events, and which setting decides it | Doesn't connect to the cluster or change anything |
| `telemetry disable`, `telemetry enable` | Leaves or joins the experience program | Writes `telemetry: false` or `true` to `config.yaml` on this computer |
| `telemetry reset` | Deletes the random ID that `zeaburctl ui` keeps for the experience program | Doesn't connect to the cluster or change anything |

## `ui`

| Option | Default and purpose |
|---|---|
| `--context <name>` | The current context in kubeconfig |
| `--no-browser` | Doesn't open a browser automatically; still prints the link |
| `--metrics-service <namespace/name:port>` | Specifies a Kubernetes Service that supports the Prometheus HTTP API. You can also use the `ZEABUR_METRICS_SERVICE` environment variable |

For example, to read usage history from an existing Prometheus installation:

```sh
zeaburctl ui --context production \
  --metrics-service monitoring/prometheus:9090
```

By default, Zeabur OSS reads from the VictoriaMetrics installation in Zeabur Catalog: `observability/vmsingle-vm-victoria-metrics-k8s-stack:8428`. Zeabur OSS reads through the Kubernetes API's Service proxy, so you also need `get services/proxy` permission for this Service. Live CPU and memory usage comes from metrics-server.

`zeaburctl ui` listens only on `127.0.0.1`, on a port assigned by the operating system. The link printed in the terminal includes a one-time token. Opening it for the first time exchanges the token for a browser session. The same link won't work again.

Press `Ctrl-C` to close the local interface. Applied changes stay in the cluster; unapplied drafts aren't written to it. When you run `zeaburctl ui` again, open the newly printed link.

## `doctor`

```sh
zeaburctl doctor
zeaburctl doctor --context production --output json
```

| Option | Values |
|---|---|
| `--context <name>` | Specifies a kubeconfig context |
| `--output <format>` | `text` (default) or `json` |

The JSON output has a top-level `checks` array. Each item has `name`, `status`, `findings`, and `fix` fields. `status` is `ok`, `warning`, `critical`, `skipped`, or `error`. If the command can't read something, it lists the missing permissions.

| Exit code | Meaning |
|---|---|
| `0` | No issues need attention; some checks may be `skipped` |
| `1` | There are warnings |
| `2` | There are critical issues, or the command arguments are incorrect |
| `3` | The command can't connect to the cluster, or checks can't run |

When results differ, critical issues take precedence over warnings, which take precedence over checks that couldn't run. `skipped` doesn't affect the exit code. Monitoring tools need to read `checks` separately to find out which checks were skipped.

On a cluster without the Zeabur OSS dashboard, `zeaburctl doctor` skips the Zeabur Identity checks, because only the dashboard needs Zeabur Identity. A cluster you only open with `zeaburctl ui` has no dashboard. doctor looks for a Deployment labeled `app.kubernetes.io/name=zeabur` in the projects you can see. If it can't read the namespaces or a project's Deployments, it runs the checks anyway.

Whether kube-apiserver trusts the Zeabur Identity issuer is defined in the control plane's `AuthenticationConfiguration` file. RBAC can't read this file, so `zeaburctl doctor` marks this check as skipped. To check it, read that file on the control plane host.

## `up`

```sh
zeaburctl up [folder] [--project <project>] [--service <service>]
```

Uploads a folder to the cluster and starts a build. If you omit the folder, the command uses the current folder. If the service doesn't exist, the command creates it. The project must already exist; the command doesn't create projects.

The command acts with your kubeconfig through the Kubernetes API, the same way `zeaburctl ui` does. It uses the same API and change plans as the web interface, so you don't need to know the registry address. Your credentials go nowhere else, and the command can't do anything your kubeconfig can't. A kubeconfig made from an API token with **Developer** in the project is enough; see [Connect from your computer or CI](../deploy/from-outside.mdx).

### What it needs

- Zeabur Builder installed in the cluster. If it's missing, the command stops before uploading. Deploy an image instead.
- The `zeabur-info` config file in the `kube-public` namespace, which the Zeabur OSS chart creates. The command reads the registry's address from it. Anyone signed in to the cluster can read it. Without it, the command can't create new services and doesn't forward a port.
- Access to the registry. If the registry is inside the cluster, such as `zot.zot.svc:5000`, the command forwards a port through the Kubernetes API, like `kubectl port-forward`. This needs `get services`, `list endpointslices`, and `create pods/portforward` in the registry's namespace. A Developer in any project has them; see [Images in the build registry](./permissions.mdx#images-in-the-build-registry). The command trusts the registry's certificate through the CA that Zeabur Builder publishes for everyone signed in.

### Choose a project and service

If you omit `--project`, the command uses the namespace of the kubeconfig context and prints which project that is. An API token's kubeconfig sets one when the token has a role in only one project. When the context sets none, the command prompts you to choose a project from a list in a terminal. If you omit `--service`, it asks for a service name, defaulting to the folder name.

If the service doesn't exist, the command asks for confirmation before creating it. Add `--yes` to skip this confirmation.

In scripts or CI, the command doesn't prompt. You must name the service with `--service`, and the project with `--project` unless the context sets a namespace. If the service doesn't exist, the command creates it without requiring `--yes`.

A new service has the same contents as one created with **Upload a folder** in the web interface, including a Build and Deployment. If you pass `--port`, the command also creates a Kubernetes Service and sets the `PORT` environment variable. Without a port, the service doesn't accept connections. The default build method is `railpack`; use `--method dockerfile` to use a Dockerfile instead.

If the service already exists, the command keeps its build settings. If the service builds from Git, the command rejects the upload without changing anything.

### Packaging and uploading

Packaging follows the same rules as [web uploads](../deploy/upload.mdx). It skips files excluded by `.gitignore` and `.dockerignore`, as well as `.git`. The limits are 256 MiB compressed and 1 GiB extracted.

The command sends a `tar.gz` archive. It keeps executable permissions, and symbolic links that point inside the uploaded folder.

The upload has three steps, in order:

1. Request an upload token from the Build. This is a change plan that the command applies directly.
2. Push the archive to the registry from your computer.
3. Write the digest to the Build to start the build. This is also a change plan that the command applies directly.

These are the same change plans the web interface uses. Running the command confirms that you want to apply them; the command doesn't ask again. When creating a new service, the service creation plan already includes the upload token request.

### Options

| Option | Default and purpose |
|---|---|
| `--project <project>` | The existing project for the service. Defaults to the namespace of the kubeconfig context. Without one, prompts you to choose from a list in a terminal, and is required in scripts and CI |
| `--service <service>` | The service name. If omitted in a terminal, prompts for a name, defaulting to the folder name. Required in scripts and CI |
| `--context <name>` | Defaults to the current context in kubeconfig |
| `--method railpack\|dockerfile` | The build method for a new service. Defaults to `railpack` |
| `--port <port>` | The port where a new service accepts connections. Configures both the Kubernetes Service and the `PORT` environment variable. If omitted, the service doesn't accept connections |
| `--yes` | Skips confirmation before creating a new service in a terminal |

## `connect`

```sh
zeaburctl connect [<project>/]<name>[:<port>] [--project <project>] [--port <port>] [--context <name>]
```

Forwards a port on `127.0.0.1` to a database or service through kube-apiserver, like `kubectl port-forward`. The command keeps running until you press Ctrl-C.

The project is the one before `/` in the target, else `--project`, else the namespace of the kubeconfig context. If the target and `--project` name different projects, the command stops. `zeaburctl connect orders --project shop` and `zeaburctl connect shop/orders` reach the same database.

`<name>` is looked up among the project's databases first. For a database, the command prints a connection string; it works for every engine. Otherwise `<name>` is a service, and the command prints the local address, such as `127.0.0.1:52341`. A service is reached through the ports of its Kubernetes Services. If there is more than one, add the one you want, as in `shop/api:8080`; without it the command lists the ports and stops.

You need `create pods/portforward` in the project, and for a database also `list` on its resources; Developers have both. If you can't read the database's secret, the connection string has `PASSWORD` in place of the password. For MongoDB the string connects to one instance directly, since the other instances' addresses only work inside the cluster. With more than one instance, that instance may not be the primary, and then the database refuses writes; the command says so before it prints the string.

| Option | Default and purpose |
|---|---|
| `--project` | The namespace of the kubeconfig context |
| `--port` | A free port. Set it to keep the same local port between runs |
| `--context` | The current kubeconfig context |

## `components export`

```sh
zeaburctl components export <id>... [--format helmchart|helm|flux|argocd] [--profile single-node|multi-node]
```

Prints installation manifests or commands for Catalog components for clusters. You can name several components; their output comes one after another. The output comes from zeaburctl's built-in Catalog, with pinned versions and configuration values. The command doesn't connect to the cluster, so it doesn't need `--context`.

| Option | Default and purpose |
|---|---|
| `--format` | `helmchart`: a K3s/RKE2 `HelmChart`, installed by helm-controller. `helm`: a `helm upgrade --install` command. `flux`: a Flux source and `HelmRelease`. `argocd`: an Argo CD `Application` |
| `--profile` | `single-node`. Use `multi-node` for the Catalog's multi-node configuration values |

Values you need to supply appear as `<name>` placeholders. Replace them with actual values first. If a component needs host access, the output first sets its namespace to `privileged`. If K3s or RKE2 includes the same component, the start of the output explains how to disable the built-in version first.

```sh
zeaburctl components export velero > velero.yaml
kubectl apply -f velero.yaml
```

You can also commit the file to a GitOps repository for Flux or Argo CD to apply. Make later changes and removals in this file.

## `templates export`

```sh
zeaburctl templates export <id> --project <project> [--domain <domain>] [--cluster-issuer <issuer>] [--set <name>=<value>]... [--context <name>]
```

Prints, as YAML for `kubectl diff --server-side` and `kubectl apply --server-side`, the objects that deploying a template into the project writes. They are the same objects the web interface writes, with the same labels and `metadata.namespace` set to the project. The templates come from zeaburctl's built-in Catalog.

| Option | Purpose |
|---|---|
| `--project` | The project to deploy into. Required |
| `--domain` | The domain, for a template that routes one |
| `--cluster-issuer` | The `ClusterIssuer` set for Zeabur OSS (`domains.clusterIssuer`), for a template that asks for certificates |
| `--set <name>=<value>` | The value of one field. Repeat it for each field |
| `--context` | The kubeconfig context for the component check. Defaults to the current one |

- The output starts with a secret for the template's passwords and keys. Each run generates new values, so save one export and apply that file.
- A required field you don't give, a missing domain, and a missing issuer appear as `<name>` placeholders. Give their values with the options above and export again before you apply.
- An unknown template ID, a value that doesn't match its field's format, and a value for a generated field stop the command.
- If the cluster lacks a component the template needs, the command says so on stderr and names the `zeaburctl components export` command that installs it. If the cluster can't be reached, it says the components weren't checked and prints the objects anyway.

To have a coding agent deploy a template this way, use the prompt in [Deploy with an agent](../deploy/templates.mdx#deploy-with-an-agent).

## `telemetry status`

```sh
zeaburctl telemetry status
```

Shows whether `zeaburctl ui` sends events, then what decides it: `config.yaml`, `DO_NOT_TRACK`, `ZEABUR_TELEMETRY`, and whether the random ID exists.

## `telemetry disable` and `telemetry enable`

```sh
zeaburctl telemetry disable
```

`disable` writes `telemetry: false` to `config.yaml`, so `zeaburctl ui` sends nothing. `enable` writes `telemetry: true`. The other lines of the file stay. Neither deletes the random ID; `telemetry reset` does. If `config.yaml` can't be read, both stop and change nothing.

## `telemetry reset`

```sh
zeaburctl telemetry reset
```

Deletes the `local-id` file that `zeaburctl ui` makes when you join the experience program. It makes a new one the next time it is about to send an event. See [Experience program](./telemetry.mdx) for where the file is and what is sent.

## Connection and permission issues

- Context not found or unable to connect to the Kubernetes API: Check the kubeconfig context, API address, and network connection, then retry with the same `--context`.
- The browser shows `This link was already used or is not valid.`: Run `zeaburctl ui` again and open the full, newly printed link.
- Some lists won't load: Request permissions for the verbs, resources, and namespaces listed on screen. To switch contexts, stop the command and run it again with a new `--context`.
- No usage history: Check the metrics store address, Service port, and `services/proxy` permissions. Usage history starts when the metrics store begins collecting data; earlier periods are empty.

For permission scope and terminal security boundaries, see [Permissions](./permissions.mdx) and [Security](./security.mdx).
