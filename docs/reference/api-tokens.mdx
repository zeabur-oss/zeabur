---
title: API tokens
description: Let scripts and CI call the Kubernetes API with roles in projects, using a token that expires.
---

An API token lets a script or CI job work with the cluster without anyone's sign-in. Admins create tokens on the **Members** page and give each one roles in projects, the same way they give a member access. A token calls kube-apiserver directly, the same way kubectl does, and Kubernetes RBAC decides what it can do. Every token expires.

## Before you begin

- You're an admin. Only admins can create, renew, change, and delete API tokens. See [Permissions](./permissions.mdx).
- The machine that uses the token can reach kube-apiserver on TCP 6443.

## Create a token

1. Open **Members** and, under **API tokens**, click **Create token**.
2. Name it after what uses it, such as `github-actions`.
3. Pick **Developer** or **Viewer** in each project it needs and how long it lasts, then click **Review**.
4. Check the changes and apply them.
5. Copy the token. Zeabur shows it only once. The dialog also shows a kubeconfig and the cluster's CA certificate.

The list shows each token's roles, who created it, and when it expires. If the cluster limits token lifetimes with `--service-account-max-token-expiration`, kube-apiserver cuts the token short, and the list shows the real expiry.

## Connect

A request needs three things: the API address, the CA certificate, and the token.

**Address**: kube-apiserver listens on TCP 6443 on each server node, for example `https://203.0.113.10:6443`. The `server` line in the kubeconfig you use with kubectl has the same address. If you reach the API through a domain or another address, add it to [`host.tlsSan`](./installer-configuration.mdx) so the certificate covers it.

**CA certificate**: The dialog shows it after you create or renew a token. A token with a role in a project can also read it from the project's `kube-root-ca.crt` config file:

```sh
kubectl -n shop get configmap kube-root-ca.crt -o jsonpath='{.data.ca\.crt}' > ca.crt
```

**kubeconfig**: Copy the kubeconfig from the dialog, fill in `server`, and save it, for example as `ci.yaml`. The CA certificate is already in `certificate-authority-data`. When the token has a role in only one project, the kubeconfig starts in that project. Otherwise, add `-n <project>` to each command.

```sh
export KUBECONFIG=$PWD/ci.yaml
kubectl auth whoami
```

`kubectl auth whoami` shows `system:serviceaccount:zeabur-api-tokens:github-actions`. That's the name kube-apiserver logs for the token's requests.

For curl, set the address and token once:

```sh
APISERVER=https://203.0.113.10:6443
TOKEN='<token>'
```

## What a token can do

A token has only the roles you give it in projects, plus `zeabur-member`, which lets it read node and namespace names. A **Viewer** token can see the status of a project's services. A **Developer** token can also:

- Change a service's image and replicas, and restart it.
- Read and edit secrets, and set variables.
- Read logs and run commands in a replica with `kubectl exec`.
- Build again.

A token can't:

- Create or delete projects, or touch a project it has no role in.
- Change nodes, cluster components, or cluster backups.
- Read or change anything in `zeabur-api-tokens`, so it can't request more tokens.

There's no admin token. Admin accounts sign in only with passkeys, and a token with full rights would get around that. For work across the cluster, such as creating projects, installing components, managing nodes, or cluster backups, use your own kubeconfig as an admin. See [Admin accounts and regular accounts](./permissions.mdx#admin-accounts-and-regular-accounts).

## Common tasks

The examples use the project `shop` and the service `web`. A service built from an image or Git is a Deployment, and its container has the same name as the service. A **Viewer** token can only list services. The other tasks need **Developer**.

| Task | Method and path |
|---|---|
| List services | `GET /apis/apps/v1/namespaces/shop/deployments` |
| Read logs | `GET /api/v1/namespaces/shop/pods/<replica>/log` |
| Restart | `PATCH /apis/apps/v1/namespaces/shop/deployments/web` |
| Change the image | `PATCH /apis/apps/v1/namespaces/shop/deployments/web` |
| Set a variable | `PATCH /apis/apps/v1/namespaces/shop/deployments/web` |
| Build again | `PATCH /apis/builder.zeabur.com/v1alpha1/namespaces/shop/builds/web` |
| Change replicas | `PATCH /apis/apps/v1/namespaces/shop/deployments/web/scale` |

### List services

```sh
kubectl get deployments -l app.kubernetes.io/name
```

```sh
curl --cacert ca.crt -H "Authorization: Bearer $TOKEN" \
  "$APISERVER/apis/apps/v1/namespaces/shop/deployments?labelSelector=app.kubernetes.io/name"
```

Databases and services with volumes may be StatefulSets. List them at `/apis/apps/v1/namespaces/shop/statefulsets`.

### Read logs

```sh
kubectl logs -l app.kubernetes.io/name=web --tail=100
```

curl reads one replica at a time. Find the replica names, then read one:

```sh
curl --cacert ca.crt -H "Authorization: Bearer $TOKEN" \
  "$APISERVER/api/v1/namespaces/shop/pods?labelSelector=app.kubernetes.io/name%3Dweb"
curl --cacert ca.crt -H "Authorization: Bearer $TOKEN" \
  "$APISERVER/api/v1/namespaces/shop/pods/<replica>/log?container=web&tailLines=100"
```

### Restart

Like **Restart** in Zeabur, this sets the pod template annotation `kubectl.kubernetes.io/restartedAt` to the current time.

```sh
kubectl rollout restart deployment/web
```

```sh
curl --cacert ca.crt -H "Authorization: Bearer $TOKEN" -X PATCH \
  -H "Content-Type: application/strategic-merge-patch+json" \
  -d "{\"spec\":{\"template\":{\"metadata\":{\"annotations\":{\"kubectl.kubernetes.io/restartedAt\":\"$(date -u +%Y-%m-%dT%H:%M:%SZ)\"}}}}}" \
  "$APISERVER/apis/apps/v1/namespaces/shop/deployments/web"
```

### Change the image

For a service built from Git, build again instead. Keel sets the image when the build finishes.

```sh
kubectl set image deployment/web web=ghcr.io/acme/web:1.5
```

```sh
curl --cacert ca.crt -H "Authorization: Bearer $TOKEN" -X PATCH \
  -H "Content-Type: application/strategic-merge-patch+json" \
  -d '{"spec":{"template":{"spec":{"containers":[{"name":"web","image":"ghcr.io/acme/web:1.5"}]}}}}' \
  "$APISERVER/apis/apps/v1/namespaces/shop/deployments/web"
```

### Set a variable

This changes a variable under **Set directly** on the service's **Variables** tab. New replicas start with the new value.

```sh
kubectl set env deployment/web -c web LOG_LEVEL=debug
```

```sh
curl --cacert ca.crt -H "Authorization: Bearer $TOKEN" -X PATCH \
  -H "Content-Type: application/strategic-merge-patch+json" \
  -d '{"spec":{"template":{"spec":{"containers":[{"name":"web","env":[{"name":"LOG_LEVEL","value":"debug"}]}]}}}}' \
  "$APISERVER/apis/apps/v1/namespaces/shop/deployments/web"
```

### Build again

Like **Build again** in Zeabur, this sets the `builder.zeabur.com/rebuild` annotation on the Build. Zeabur Builder builds the branch's latest commit.

```sh
kubectl annotate build web --overwrite builder.zeabur.com/rebuild="$(date -u +%Y-%m-%dT%H:%M:%SZ)"
```

```sh
curl --cacert ca.crt -H "Authorization: Bearer $TOKEN" -X PATCH \
  -H "Content-Type: application/merge-patch+json" \
  -d "{\"metadata\":{\"annotations\":{\"builder.zeabur.com/rebuild\":\"$(date -u +%Y-%m-%dT%H:%M:%SZ)\"}}}" \
  "$APISERVER/apis/builder.zeabur.com/v1alpha1/namespaces/shop/builds/web"
```

### Change replicas

```sh
kubectl scale deployment/web --replicas=2
```

```sh
curl --cacert ca.crt -H "Authorization: Bearer $TOKEN" -X PATCH \
  -H "Content-Type: application/merge-patch+json" \
  -d '{"spec":{"replicas":2}}' \
  "$APISERVER/apis/apps/v1/namespaces/shop/deployments/web/scale"
```

## Renew, change, and delete

Choose **More** → **Renew** next to a token to get a new token with the same name and access. Tokens issued before keep working until they expire.

Choose **More** → **Change access** to give the token roles in other projects. The change applies to every token issued for it.

To stop a token at once, choose **More** → **Delete**. Every token issued for it stops working, and requests get `401 Unauthorized`.

A token doesn't belong to the person who created it. It keeps working after they leave, until it expires or an admin deletes it.

## What Zeabur creates

Zeabur writes these objects with the admin's own permissions:

| Object | Contents |
|---|---|
| `ServiceAccount <name>` in the `zeabur-api-tokens` namespace | Labels `zeabur.com/api-token: <name>` and `app.kubernetes.io/managed-by: zeabur`. Annotations record who created it and when the latest token expires |
| `RoleBinding zeabur-api-token-<name>` in each project | Binds `zeabur-project-developer` or `zeabur-project-viewer` to the ServiceAccount |
| `ClusterRoleBinding zeabur-api-token-<name>` | Binds `zeabur-member`, like a member's |

The token itself comes from a TokenRequest for the ServiceAccount. Zeabur doesn't store it in a secret or anywhere else. Deleting the token deletes its bindings and the ServiceAccount.

The chart creates the `zeabur-api-tokens` namespace, and nothing else runs there. Only admins have permissions in it, so nobody else can request a token or run a pod as one. See [API tokens and RBAC](./permissions.mdx#api-tokens-and-rbac).
