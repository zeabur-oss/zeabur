Run `plan` first to see what the configuration will create, then run `apply` as root. If installation stops, fix the cause and run `apply` again with the same configuration. Each step checks what's already there and changes only what's missing or different.

To install with the web interface, see [Install Zeabur on a server](../get-started/quickstart.mdx). To use a configuration file and commands, see [Install with a configuration file and commands](../get-started/advanced-install.mdx). For YAML fields, see [Installer configuration](./installer-configuration.mdx). If you already have a Kubernetes cluster, follow [Install Zeabur in an existing cluster](../get-started/install.mdx).

## Common options

```sh
zeabur-installer --version
zeabur-installer --help
zeabur-installer --config /etc/zeabur-installer/config.yaml plan
```

Every subcommand accepts `--config` (`-c`), which defaults to `/etc/zeabur-installer/config.yaml`.

## `plan`

```sh
sudo zeabur-installer --config /etc/zeabur-installer/config.yaml plan
sudo zeabur-installer --config /etc/zeabur-installer/config.yaml plan --json
```

`plan` reads the configuration, Catalog, and host information, then lists the Kubernetes distribution (K3s or RKE2), components, namespaces, host files, storage classes, memory estimates, and warnings. It then runs the same host checks as `apply` without changing the host. If a check fails, it reports that `apply` will stop. Add `--json` to output JSON without running the host checks.

Without a configuration file, `plan` generates `sslip.io` names from the host's address and the default components so you can preview the result. It uses `domain` certificate mode (Let's Encrypt) when the host has a public address, and `local` when it has only private, CGNAT, or link-local addresses. `apply` always requires a configuration file.

`apply` recalculates the installation from the configuration when it runs. If you change the YAML after running `plan`, `apply` installs the new configuration.

## `apply`

```sh
sudo zeabur-installer --config /etc/zeabur-installer/config.yaml apply
sudo zeabur-installer doctor
```

Requires Linux, systemd, and root access. The installer first checks the host, ports, disk, and clock synchronization. A failed check stops the run before anything is written. An unsynchronized clock only produces a warning. The installer also warns when the kernel reserves memory for crash dumps (kdump) and prints a command to turn it off. A K3s server needs `80`, `443`, `6443`, and `10250`, and an RKE2 server also needs `9345`. A worker needs only `80`, `443`, and `10250`. ServiceLB uses `80` and `443` on every node.

To create a cluster, the installer runs these steps in order:

1. Prepares host packages for the selected components, such as the iSCSI and NFS clients Longhorn needs.
2. Writes the K3s or RKE2 configuration, kernel parameters required by CIS, and audit policy. The audit log keeps only request metadata and records every request for a secret. See [Secret encryption and access logs](./security.mdx#secret-encryption-and-access-logs).
3. Downloads K3s or RKE2 to `/var/lib/rancher/zeabur-installer/downloads`, verifies it against the SHA-256 pinned by the installer, starts `k3s` or `rke2-server`, and waits for the API and node to be ready.
4. Creates the components' namespaces, baseline NetworkPolicies, and storage classes. The default CIS policy in `kube-system` blocks outside traffic to ServiceLB. Requests that arrive at a node without Traefik then can't reach Traefik, so the installer adds `kube-system/zeabur-installer-servicelb` to allow outside traffic into ServiceLB replicas only.
5. Installs components in Catalog order and waits for them to be ready. It downloads each chart and manifest file first and stops if its SHA-256 doesn't match the Catalog. Before each chart, it applies the CRDs in the chart's `crds/` folder with server-side apply, so CRDs follow the chart on upgrade (Helm applies them only on first install). It never deletes CRDs.
6. With `zeabur: true`, adds the `zeabur-system-hosts` admission policy first so projects can't use Zeabur's and Zeabur Identity's domains. See [Zeabur's and Zeabur Identity's domains](./security.mdx#domains-for-zeabur-and-zeabur-identity). It then installs Zeabur Identity, configures the API server to trust it, registers the OAuth client, and installs Zeabur. cert-manager automatically renews the certificate the API server uses to connect to Zeabur Identity. See [Zeabur Identity's internal certificate](./security.mdx#zeabur-identitys-internal-certificate).
7. On the first install, prints a one-time setup link for the first admin, valid for 24 hours, and writes the installation record to the `kube-system/zeabur-installer` config file.

When installation finishes, the installer prints the Zeabur and Zeabur Identity URLs. Open the setup link and add a passkey to sign in to Zeabur and view the cluster. In `local` mode, first configure the browser to trust the CA the installer generated.

`apply` restores installer-managed files to the content it generates. Put your own settings in `/etc/rancher/k3s/config.yaml.d/90-local.yaml` (K3s) or `/etc/rancher/rke2/config.yaml.d/90-local.yaml` (RKE2) instead of changing the installer's `config.yaml`.

## `gui`

Run on the server:

```sh
sudo zeabur-installer gui
```

Create an SSH tunnel from your computer:

```sh
ssh -L 8085:127.0.0.1:8085 root@server.example.com
```

Open the full link printed by the server. The GUI listens on `127.0.0.1:8085` by default. Use `--listen <address:port>` to change the address. The GUI writes the same configuration file and runs the same `apply` when you start installation. For screenshots of each step, see [Install Zeabur on a server](../get-started/quickstart.mdx).

<Callout type="warn">
The GUI modifies this host as root. Keep it listening on loopback and access it through an SSH tunnel. If you bind it to an external address, it sends the sign-in token and installation configuration over unencrypted HTTP.
</Callout>

After installation, press `Ctrl-C` to close the GUI. K3s/RKE2 and the installed services keep running.

## `doctor`

```sh
sudo zeabur-installer doctor
```

On the server that created the cluster, `doctor` checks the K3s or RKE2 unit, API, components in the installation record and their health checks, default storage class, Zeabur and Zeabur Identity Deployments, Zeabur Identity's internal certificate, node addresses, baseline network policies, secret encryption, and encryption of `/var/lib/rancher`. It checks against the last `apply` record. If you change the YAML, run `apply` again for those changes to count.

Each component's health checks come from the Catalog release that `apply` used. When a check fails, `doctor` prints the Catalog's advice and the `kubectl wait` command it ran. Run that command yourself to check again.

On a node that joined an existing cluster, it checks the local `k3s-agent` or RKE2 unit, whether the node is ready, connectivity and latency to the server, and disk encryption. On a server, it also compares Zeabur Identity's authentication configuration.

| Exit code | Meaning |
|---|---|
| `0` | Checks passed |
| `1` | Warnings found |
| `2` | Faults found |
| `3` | Checks couldn't run, for example, because the command wasn't run as root |

Invalid command-line arguments also return `2`. To check from your computer through the Kubernetes API, use [`zeaburctl doctor`](./zeaburctl.mdx#doctor). Its exit codes have the same meanings.

## `node add` and `node sync`

Run on an existing server:

```sh
sudo zeabur-installer node add
sudo zeabur-installer node add --role worker --ttl 30m
sudo zeabur-installer node add --role server --address 10.0.0.5
```

| Option | Default and purpose |
|---|---|
| `--role` | Defaults to `worker`. `server` works on RKE2 only; K3s takes workers only |
| `--address` | Defaults to this node's `InternalIP`; the new host uses this address to reach this server |
| `--ttl` | Worker token lifetime. Defaults to `1h`; accepts values such as `30m` and `1h`, up to `24h` |

`node add` prints the join YAML and commands for the new VM. The new VM must use the same hosting provider and region as this server. It can be in a different availability zone. Workers use an expiring bootstrap token. Servers use the cluster's server token, which doesn't expire; `--ttl` has no effect on it. Treat the output like a password and set its permissions to `0600` when saving it on the new host.

After the new host applies the join configuration, run this on an existing server:

```sh
sudo zeabur-installer node sync
```

`node sync` updates the installer's baseline network policies to allow traffic from every current node: the first address in each node's replica network range. A joining server runs the sync itself. After a worker joins, you must run `node sync` once on a server. Until then, the network policies block traffic from the new node. `node add` also prints a reminder for this step. For network and storage requirements, see [Add nodes](../cluster/nodes.mdx).

## Remove components

Only the installer installs and removes components. To remove one, uncheck it under **Components** in `gui`, or remove it from `enable` in the configuration file. For a component installed by default, add it to `disable` instead. Then run `apply`. A personal install works the same way.

`plan` lists the components to remove under "Removed", along with what stays and which CRDs it will delete. Once the cluster is running, `apply` removes components before creating namespaces, storage classes, and other components. It removes a component after any components that depend on it. For each component, `apply` deletes the `HelmChart` objects in `kube-system` that carry the label `app.kubernetes.io/managed-by: zeabur-installer` and the annotation `installer.zeabur.com/component: <capability>/<id>`, then waits for helm-controller's `helm-delete-<chart>` Job to finish uninstalling the chart.

The installer removes only what it installed. A component installed by Helm, Flux, or Argo CD has no such annotation and stays. A component the Catalog no longer lists stays too; `plan` warns and gives the `kubectl delete` command.

Uninstalling deletes the CRDs that the chart puts in its templates, along with every object of those CRDs in the cluster. Helm marks these CRDs with the annotations `meta.helm.sh/release-name` and `meta.helm.sh/release-namespace`. Before removing anything, the installer reads these annotations from the cluster so `plan`, `gui`, and `apply` can list the CRDs it will delete. CRDs in the chart's `crds/` folder have no such annotations and stay. CRDs with the annotation `helm.sh/resource-policy: keep` also stay.

`apply` changes nothing while a component is still in use and lists what uses it:

| Component | In use when |
|---|---|
| A component with custom resources | Objects of the CRDs the Catalog lists for it, or of CRDs the uninstall will delete, exist outside the namespaces of components being removed together. For CRDs the uninstall will delete, cluster-scoped objects count too |
| Longhorn | A PersistentVolume with the driver `driver.longhorn.io` still exists |
| Zeabur Builder | A replica outside zot's namespace uses an image from `zot.zot.svc:5000` |

Delete or move those first. Trivy Operator's reports are its own output, so they don't count.

When uninstalling will delete a component's stored data, you must also add its component ID to `allowDataLoss` (`gui` asks with a checkbox under **Review**). For Longhorn, `apply` then sets its `deleting-confirmation-flag` to `true`; otherwise, Longhorn refuses to uninstall. This also deletes every volume's replicas.

Once you're sure nothing needs the remaining resources, you can delete them manually:

- The component's namespace, including its secrets and workload disks (PersistentVolumeClaims): `kubectl delete namespace <namespace>`. Back up the disks first.
- CRDs the uninstall didn't delete (those not listed under "Deletes these CRDs"): find them with `kubectl get crd -o name | grep <group>`, then use `kubectl delete`. This deletes every object of those CRDs in the cluster.
- Manifests the installer applied for the component, such as Gateway API CRDs or cert-manager issuers: `plan` lists their names. Delete them with `kubectl delete`.
- Other leftovers the Catalog lists, such as Longhorn's `longhorn-static` storage class: `kubectl delete storageclass longhorn-static`.

These steps don't depend on Zeabur's finalizer and still work after Zeabur is removed.

## `uninstall`

```sh
sudo zeabur-installer uninstall zeabur
```

Removes only Zeabur. K3s/RKE2, Zeabur Identity, Catalog components, and applications stay. `uninstall zeabur` also deletes the RoleBindings and ClusterRoleBindings Zeabur created for members.

`uninstall identity` also removes Zeabur Identity and clears the API server's trust configuration for it. Before running it, set up another sign-in method as described in [Remove Zeabur](../leave/uninstall.mdx). If the cluster has multiple servers, run `sudo zeabur-installer apply` once on each other server so it stops trusting Zeabur Identity's tokens. The command lists these servers.

On a joined node, `uninstall` only prints the commands to run in order: drain, delete the Node, run the K3s or RKE2 uninstall script, and sync the network policies. See [Add and maintain nodes](../cluster/nodes.mdx#remove-a-node) for these steps.

After K3s or RKE2 is removed, `uninstall --purge` deletes the installer's download cache, local CA copy, and configuration. Volumes stay. You can't combine `--purge` with `zeabur` or `identity`. To keep the cluster, don't run the K3s or RKE2 uninstall script or `--purge`.

### A personal install

With `use: personal` in the configuration, `uninstall` deletes nothing and only prints the commands to remove KubeSolo. See [Personal use: Install on a small machine](../get-started/personal.mdx#uninstall). `node add` and `node sync` aren't available because KubeSolo has only one node.

## If installation stops

- Host check failed: free the ports or fix the disk as directed in the output, then run `plan` and `apply` again.
- Kubernetes didn't start: on K3s, check `sudo journalctl -u k3s`, or `k3s-agent` on a worker. On RKE2, check `sudo journalctl -u rke2-server`, or `rke2-agent` on a worker.
- A component is stuck installing through Helm: `doctor` points to the `helm-install-<name>` Job in `kube-system`. Check its logs.
- A new node is ready but can't reach some system services: run `node sync` on a server first, then check `doctor`'s network policy results.

To undo an installation, follow the [removal steps](../leave/uninstall.mdx) to remove only Zeabur or clean up the entire test machine. Deleting an application's namespace doesn't remove Zeabur; it only deletes the application.
