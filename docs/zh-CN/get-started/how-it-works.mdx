Zeabur 没有自己的数据库。你在 Zeabur 看到的项目、服务、域名，都直接从 Kubernetes 读取。你在 Zeabur 做的修改，也直接写回 Kubernetes 对象。下面四个场景说明这在日常操作中意味着什么。

## 已经用 Helm 部署的服务

假设 `shop` 这个 Namespace 是同事半年前用 Helm 安装的。打开 Zeabur 的**项目**，在**其他 Namespace** 中找到 `shop`，点进去，服务、域名、环境变量都已经在里面，不需要导入。

要把这个 Namespace 作为项目管理，点击**使用这个 Namespace**。Zeabur 只会给 Namespace 添加一个标签，不会移动里面的任何内容。

接下来，你可能想直接在 Zeabur 调高副本数。Zeabur 会阻止这次修改，提示这个服务由 Helm 管理：即使这次修改成功，下次 `helm upgrade` 也会覆盖回去。要修改副本数，就去改 Helm values。重启不会改动配置，所以仍然可以操作。Argo CD 和 Flux 管理的服务也一样。

## 检查完，同事又改了一次

你把副本数从 2 改成 3，点击**检查变更**，页面列出将要写入集群的差异。这时集群还没有任何变化。

你去倒杯水时，同事用 `kubectl` 更换了同一个 Deployment 的镜像。你回来点击应用，Zeabur 会拒绝这次操作，提示你重新检查。重新计算的差异以同事修改后的版本为准，你不会意外把同事换上的镜像改回旧版本。

检查过的变更放置太久也会过期。看到**这份变更已过期**时，点击**重新检查**即可。

## 看得到服务，打开日志却遭到拒绝

新同事在 `shop` 中的角色是**查看者**，能看到服务和状态，点击**日志**却提示权限不足。

这是因为 Zeabur 每次读写集群，都使用登录者自己的身份，能做什么由 Kubernetes RBAC 决定。**查看者**角色不能读取日志和机密变量，所以 Zeabur 也读不到。Zeabur 自身没有任何集群权限，无法替任何人读取权限范围以外的内容。

要让新同事查看日志，管理员可以到[成员](../cluster/members.mdx)页面，把角色改成**开发者**。管理员使用管理员账号登录，本来就有整个集群的权限，不会遇到这种情况。各个角色能做什么，见[权限](../reference/permissions.mdx)。

## 有一天决定不用 Zeabur

服务本来就是 Kubernetes 对象，所以移除 Zeabur 后，Deployment、Service、Ingress、环境变量和卷都还在原来的 Namespace 中，网站照常响应。

消失的是 Zeabur 的管理界面，以及 Zeabur 安装的成员角色。原本依靠这些角色登录集群的同事，需要先通过其他方式获取权限。数据库 operator、Ingress controller、cert-manager 这些组件也要保留，服务仍然依赖这些组件。

完整的移除步骤和需要保留的组件清单，见[移除 Zeabur](../leave/uninstall.mdx)。
