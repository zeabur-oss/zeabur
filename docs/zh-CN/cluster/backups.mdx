打开**集群** → **备份**，先配置**备份存放位置**，再配置**定时**。点击**立即备份**运行一次，等**备份记录**显示**成功**，就确定备份能用了。

集群备份由 Velero 执行，把选定 Namespace 的 Kubernetes 对象和卷里的文件存到 S3 兼容存储。PostgreSQL、MongoDB 这类数据库有自己的备份，在各数据库的**备份**标签页配置，见[部署数据库](../deploy/databases.mdx)。只想备份单个服务的卷，可以用 [K8up 卷备份](../configure/volumes.mdx)。

页面上的**各类数据的备份**表列出哪类数据由什么备份：

| 数据 | 备份方式 | 配置位置 |
| --- | --- | --- |
| PostgreSQL、MongoDB | 数据库备份到 S3，不需要 K8up 或 Velero。 | 各数据库的**备份**标签页 |
| 卷 | K8up | 服务的**设置** → **备份** |
| 整个项目 | Velero | **集群** → **备份** |

## 开始之前

- 集群已安装 Velero。界面显示**备份需要 Velero** 时，点击**安装 Velero**，按照[安装组件](./components.mdx)装好。
- 准备 S3 兼容的存储桶、端点和密钥，或先在同一页上方的 **S3 目的地**添加，见 [S3 目的地](./s3-destinations.mdx)。
- 你能在 Velero 的 Namespace 读取和创建备份位置、定时、备份、还原和 Secret。Zeabur Chart 的成员角色没有 Velero 的权限，通常要用管理员账号操作。

<Callout type="warn">
备份要存放在集群以外的存储，例如 Cloudflare R2、Backblaze B2 或 AWS S3。如果存放在同一个集群里，集群丢失时备份也会一起消失。端点看起来在集群里时，表单会提醒。
</Callout>

## 配置存放位置

<Steps>
<Step>

### 选择存储桶

在**备份存放位置**点击**设置**或**编辑**。已添加 S3 目的地时，**S3 目的地**菜单默认选中第一个，表单会填入这个目的地的位置和密钥。要自己填写，改选**手动输入**。

手动输入时填写**存储桶**、**访问密钥 ID** 和**私密访问密钥**。使用 AWS S3 时**端点**留空，R2、B2 或 MinIO 填写各自的 S3 地址。**区域**留空时是 `us-east-1`。**文件夹**可选，可以让这些备份和其他文件分开。

![备份存放位置的表单，选了 S3 目的地 r2-backups 并填入端点和存储桶](../images/shots/backup-location-form.avif)

编辑已有配置时，两个密钥都留空就沿用当前密钥。要换就两个一起填。

</Step>
<Step>

### 检查并等待连接结果

点击**检查变更**，确认存储桶、端点，以及要新增或修改的备份位置和存储密钥，再应用。

回到**备份存放位置**，等**状态**从**尚未检查**变成**可访问**。显示**无法访问**时，先核对存储桶、端点和密钥，再配置定时。

![备份存放位置显示存储桶、端点和可访问状态](../images/shots/backup-location.avif)

</Step>
</Steps>

## 配置定时并运行一次备份

1. 在**定时**选择每天执行的**时间**（UTC 整点）和**保留天数**。新定时默认每天 03:00（UTC）、保留 7 天。保留天数可填 1 到 365。
2. 在**范围**选择**整个集群**，或选择**选定的项目**并至少勾选一个项目。**整个集群**也包括之后新增的项目和 Namespace。

   ![定时表单，每天 03:00（UTC）、保留 7 天、范围是整个集群](../images/shots/backup-schedule-form.avif)

3. 点击**检查变更**，确认执行时间和范围后应用。Zeabur 会创建或修改名为 `zeabur` 的 Velero Schedule，并开启卷文件备份。
4. 点击**立即备份**，检查后应用。这次备份按刚配置的范围和保留天数执行，不用等定时。
5. 在**备份记录**找到这条，等状态从**运行中**变成**成功**，再看记录列出的条目数和**保留到**的日期。

   ![备份记录列出每次备份的状态、条目数和保留期限](../images/shots/backup-list.avif)

在 Zeabur 以外创建的定时会标为**在 Zeabur 以外配置**，要回到原来创建的地方修改。

## 从备份还原

还原分三步：先还原项目，检查服务和数据，最后接回域名。原项目还在时，备份会另存为一个新项目，原项目照常运行。原项目已经删除时，备份用原来的名称还原。两种还原都不带域名，等你确认项目没问题，再把域名接回来。

<Steps>
<Step>

### 选择项目并检查

1. 在**备份记录**找到要使用的备份，点击该行的还原按钮。按钮名称随备份里的项目而变：
   - **从备份创建新项目**：备份选定的项目都还在。
   - **还原已删除的项目**：备份选定的项目都已经删除。
   - **还原项目**：备份整个集群，或选定的项目有些还在、有些已删除。
2. 在**要还原的项目**选择一个项目。选项是这份备份选定的项目；备份整个集群时，选项是当前的项目，加上备份里已经删除的项目，后面标 **（已删除）**。Zeabur 要下载备份才知道有哪些已删除的项目，表单会先显示“正在找备份里已删除的项目…”。
   - 原项目还在：**新项目名称**会填入一个新名称，可以改。
   - 原项目已经删除：界面会说明使用原来的名称还原。

   ![还原表单，选了备份里的项目，并填入新项目名称](../images/shots/backup-restore.avif)

   ![还原表单，选了已删除的项目 wiki，说明会用原来的名称还原](../images/shots/backup-restore-deleted.avif)

3. 点击**检查变更**，确认内容。清单来自备份本身，与当前项目无关：
   - 备份里的域名不会一起还原。Ingress、HTTPRoute 和 cert-manager 的证书都不还原，域名在最后一步接回，证书到时重新申请。
   - 另存为新项目时，备份里的定时任务会先暂停，避免同一件事在两个项目各运行一次。用原名称还原时，定时任务照常执行。
   - 另存为新项目时，界面会列出备份里的服务和机密变量。写着 `<服务>.<原项目>.svc` 的值仍然连到原项目，还原后用**改写地址**改掉。
   - 另存为新项目时，界面会显示节点资源够不够两个项目同时运行。自动部署和 Git webhook 仍然送到原项目。

   ![检查界面，列出新项目、要改写的服务地址和节点资源](../images/shots/backup-restore-plan.avif)

   原项目还在时点击**从备份创建新项目**，已经删除时点击**还原**。

4. 应用后 Velero 马上开始。到**还原记录**查看这条的状态、来源备份、错误和警告数。

</Step>
<Step>

### 检查项目

还原完成后，这条记录下方会出现**打开项目**和**接回域名**，另存为新项目时还有**改写地址**。

1. 点击**打开项目**，确认服务的副本都已就绪、卷已挂载且数据正确。用数据库自己备份的数据，按[该数据库的还原步骤](../deploy/databases.mdx)处理。
2. 另存为新项目时，点击**改写地址**，把指向原项目的服务地址改成新项目。
3. 确认新项目没有问题后，到每个[定时任务](../deploy/cron-jobs.mdx)点击**恢复**。

Velero 会跳过已经存在的同名对象。另存为新项目后，原项目会继续保留，不需要时自己删除。

</Step>
<Step>

### 接回域名

点击**接回域名**。Zeabur 从备份读出这个项目的域名，再检查集群里有没有其他项目正在使用。

- 没有其他项目在用：应用后 Velero 只还原这些路由，**还原记录**会多一条“域名接回”。cert-manager 会重新申请证书。

  ![接回域名的检查界面，会从备份把 blog.example.com 接回 blog](../images/shots/backup-attach.avif)

- 原项目还在用：这次不能应用。界面会指出哪个项目在用，例如原项目是 `blog` 时，点击**从 blog 移动域名**，把域名从 `blog` 移到新项目。

</Step>
</Steps>

### 用 kubectl 做同样的事

把备份 `zeabur-20261020030000` 里的 `blog` 另存为 `blog-restored`：先创建暂停定时任务的 ConfigMap（Velero 的 resource modifier），再创建 Restore，两个都在 `velero` Namespace。ConfigMap 的 `namespaces` 填写备份里原来的 `blog`。

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: blog-restored
  namespace: velero
data:
  cronjobs.yaml: |
    version: v1
    resourceModifierRules:
    - conditions:
        groupResource: cronjobs.batch
        namespaces:
        - blog
      patches:
      - operation: add
        path: /spec/suspend
        value: "true"
---
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: blog-restored
  namespace: velero
spec:
  backupName: zeabur-20261020030000
  includedNamespaces:
  - blog
  namespaceMapping:
    blog: blog-restored
  excludedResources:
  - ingresses.networking.k8s.io
  - httproutes.gateway.networking.k8s.io
  - certificates.cert-manager.io
  - certificaterequests.cert-manager.io
  - orders.acme.cert-manager.io
  - challenges.acme.cert-manager.io
  resourceModifier:
    kind: ConfigMap
    name: blog-restored
```

用原名称还原时，去掉 `namespaceMapping` 和 `resourceModifier`，也不用创建 ConfigMap。Zeabur 创建的 ConfigMap 会把 Restore 设为所有者，删除 Restore 时一起删除；自己创建的要在还原完成后用 `kubectl -n velero delete configmap blog-restored` 删掉。

确认项目后，用 `kubectl get ingress -A` 确认没有其他项目在用同一个域名，再创建只还原路由的 Restore：

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: blog-restored-domains
  namespace: velero
spec:
  backupName: zeabur-20261020030000
  includedNamespaces:
  - blog
  namespaceMapping:
    blog: blog-restored
  includedResources:
  - ingresses.networking.k8s.io
  - httproutes.gateway.networking.k8s.io
```

恢复定时任务：

```sh
kubectl -n blog-restored patch cronjob <名称> -p '{"spec":{"suspend":false}}'
```

## 备份的加密

Velero 把 Kubernetes 对象原样放进备份，Secret 也在里面，值只是任何人都能解码的 base64。从 Zeabur Catalog 安装 Velero 时，会在 `velero` Namespace 生成两把随机密钥：

| Secret 与字段 | 用途 |
|---|---|
| `velero-repo-credentials` 的 `repository-password` | Kopia 在上传前用这个密码加密卷里的文件。 |
| `velero-backup-key` 的 `key`（32 个字符） | 存放位置配置 `customerKeyEncryptionSecret: velero-backup-key/key`，存储服务用这把密钥加密每个对象，包括对象清单和 Secret（SSE-C）。 |

在**集群** → **备份**新增存放位置时，Zeabur 也会配置 `customerKeyEncryptionSecret`。`velero-backup-key` 不存在就创建一把，已经有的不会更换。已有的存放位置保持原样，之前没有用密钥的备份仍然读得到。

SSE-C 每次请求都把密钥交给存储服务，由存储服务加密后再保存，所以端点要用 HTTPS。SeaweedFS、AWS S3、Cloudflare R2 和 Backblaze B2 支持 SSE-C，MinIO 只在 HTTPS 下接受。不支持的存储服务会拒绝上传，备份就会失败。

### 把密钥另存到集群外

<Callout type="warn">
这两把密钥也在自己加密的备份里。集群坏掉后少了密钥，谁都读不了备份。安装 Velero 后，先存一份到密码管理工具或外部机密库。
</Callout>

```sh
kubectl -n velero get secret velero-repo-credentials velero-backup-key -o yaml > velero-keys.yaml
```

还原到新集群时，先创建这两个 Secret，再安装 Velero，指向同一个存储桶。

### 确认存储服务真的要求密钥

第一次备份完成后，只用存储桶的访问密钥、不带 SSE-C 密钥，下载 `backups/<备份名称>/velero-backup.json`。存储服务应该拒绝，例如 SeaweedFS 返回 `InvalidArgument`，要求提供 customer key。如果下载得到内容，就说明这个存储服务没有加密。

### 之前就安装了 Velero

如果 Velero 不是从 Catalog 安装的，集群里可能没有 `velero-repo-credentials`。这时 Velero 会自己用公开的默认密码 `static-passw0rd` 创建这个 Secret，而 Kopia 存储库会一直沿用创建时的密码。这种集群要把存放位置的**文件夹**换成新的，让 Kopia 用新密码创建存储库。加入 SSE-C 之前的备份没有加密，到期删除后就不留明文。

### 其他备份

[卷备份](../configure/volumes.mdx)使用 restic，上传前用 Zeabur 生成的 `<claim>-backup` Secret 里的 `RESTIC_PASSWORD`（24 个随机字符）加密。CloudNativePG 的数据库备份只压缩、不加密，存储桶里读得到数据行（没有 Secret 的值）。数据库备份要放在有服务器端加密的存储桶，访问密钥只给集群使用。

## 常见失败

- **无法访问**：核对存储桶、端点、区域和密钥，并查看位置下方 Velero 的消息。
- 连接成功但备份失败，存储服务拒绝上传：确认存储服务支持 SSE-C，端点也用 HTTPS，见[备份的加密](#备份的加密)。
- 没有**立即备份**：要先有 Zeabur 创建的定时，而定时要先有存放位置。
- 还原按钮（**从备份创建新项目**、**还原已删除的项目**或**还原项目**）无法使用：你不能在 Velero 的 Namespace 创建 Restore。还原时 Velero 用自己的权限写入对象，所以只有管理员能还原，见[权限](../reference/permissions.mdx)。请管理员用管理员账号还原。
- **部分失败**：有些对象或卷文件没有复制到，其余的已经保存。用 `velero backup describe <backup> --details` 查看失败的条目，处理后再备份一次。
- 界面提示备份途中 Velero 重启：下一次会按定时执行，也可以点击**立即备份**补一次。
- **卷**显示**只备份对象，不复制卷里的文件**：这是在 Zeabur 以外创建的定时，要到原来的配置开启 `defaultVolumesToFsBackup`。
- 变更已过期：重新**检查变更**。

## 暂停与清除

在**定时**点击**暂停**，检查后应用，之后就不会再备份。点击**恢复**恢复。已有的备份和存放位置都会保留，备份按各自的**保留到**日期到期。

Zeabur 没有删除备份或定时的操作。要马上删掉，用 `velero backup delete` 或 `velero schedule delete`。移除 [S3 目的地](./s3-destinations.mdx)只会删掉目的地本身，已经复制到 Velero 的密钥、定时和 S3 里的备份都会留下。
