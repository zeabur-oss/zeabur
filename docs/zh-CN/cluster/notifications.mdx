打开 **集群** → **通知**，点击 **添加渠道**，选择接收位置和事件。应用后点击 **发送测试**，到 Slack、邮箱或其他接收位置确认是否收到通知。

集群的渠道接收节点、Falco 运行时安全事件和系统 Namespace 的告警。单个项目的构建、部署或数据库事件，需要在该项目的 **设置** → **通知** 中另行添加渠道。

## 开始之前

- 集群已安装指标组件（VictoriaMetrics）。如果页面显示 **通知需要先安装告警功能**，点击 **安装指标组件**，安装完成后再返回。
- 准备好接收服务的 Webhook 地址、令牌或 SMTP 配置。
- 添加渠道需要在通知所在的 Namespace 中创建 `VMAlertmanagerConfig` 和机密变量的权限。发送测试还需要创建 Job 的权限。管理员账号具备这些权限。

## 添加并测试渠道

<Steps>
<Step>

### 选择接收位置

在 **集群** → **通知** 中点击 **添加渠道**。**名称** 最多 30 个字符，只能使用小写字母、数字和连字符，且必须以字母开头。

在 **发送到** 中选择类型，填写对应配置：

| 类型 | 需要准备 |
| --- | --- |
| **Slack**、**Discord** | **Webhook 地址**。 |
| **Telegram** | **Bot 令牌**、数字格式的 **聊天 ID**。 |
| **电子邮件** | **收件人**、**发件人**，以及包含端口的 **SMTP 服务器**，例如 `smtp.example.com:587`。SMTP 服务器必须支持 TLS，**SMTP 用户名** 和 **SMTP 密码** 为选填项。 |
| **Webhook** | **网址**，**Bearer 令牌** 为选填项。 |
| **ntfy** | **主题**。**服务器** 留空时使用 `ntfy.sh`，**访问令牌** 为选填项。 |

</Step>
<Step>

### 选择事件并应用

在 **事件** 中至少勾选一项，例如 **节点未就绪** 或 **运行时安全（Falco）**。

点击 **检查变更**，确认要创建的渠道和用于存储地址、令牌的机密变量（不会显示内容），再点击 **添加渠道**。

![添加通知渠道窗口，已填写 Slack 的 Webhook 地址并勾选三种事件](../images/shots/notify-channel-add.avif)

</Step>
<Step>

### 发送一次测试

等渠道不再显示 **等待中**，在渠道所在行点击 **发送测试**，检查要创建的测试 Job，再点击 **发送测试**。

测试会创建一个运行时间不超过两分钟的 Job。告警规则检测到它后，会向该渠道发送一条测试告警。页面显示已发送后，大约一两分钟内，到接收位置确认是否收到消息。

![渠道所在行显示接收位置和事件，旁边有编辑和发送测试按钮](../images/shots/notify-channels.avif)

</Step>
</Steps>

## 编辑渠道

在渠道所在行点击 **编辑**，修改事件和接收配置，再依次点击 **检查变更** 和 **保存渠道**。

表单会填入不属于机密变量的配置。地址、令牌和密码字段会留空，并标注 **不更改**。留空会保留已保存的值，填写后才会替换对应项。Zeabur 不会读取已保存的机密变量。

渠道类型无法修改。要从 Slack 改为电子邮件等其他类型，先添加另一个渠道、发送测试并确认收到，再移除旧渠道。

## 用 kubectl 完成相同操作

一个渠道由两个名为 `zeabur-notify-<名称>` 的对象组成，都带有标签 `zeabur.com/notification-channel: <名称>`：Secret 存储地址、令牌和密码，`VMAlertmanagerConfig` 配置路由和接收设置。集群的渠道位于 `observability` Namespace，项目的渠道位于项目自己的 Namespace。

下面是项目 `shop` 的 Slack 渠道，接收崩溃重启和部署失败事件：

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: zeabur-notify-ops
  namespace: shop
  labels:
    zeabur.com/notification-channel: ops
type: Opaque
stringData:
  url: https://hooks.slack.com/services/T000/B000/XXXX
---
apiVersion: operator.victoriametrics.com/v1beta1
kind: VMAlertmanagerConfig
metadata:
  name: zeabur-notify-ops
  namespace: shop
  labels:
    zeabur.com/notification-channel: ops
  annotations:
    zeabur.com/notification-kind: slack
spec:
  route:
    receiver: events
    matchers:
      - zeabur_event=~"crash-loop|deploy-failed|test"
      - zeabur_channel=~"|ops"
    group_by: ["..."]
    group_wait: 30s
    group_interval: 5m
    repeat_interval: 12h
    routes:
      - receiver: states
        matchers:
          - zeabur_kind="state"
        group_by: [alertname]
  receivers:
    - name: events
      slack_configs:
        - api_url: {name: zeabur-notify-ops, key: url}
          title: '{{ if eq .Status "resolved" }}Resolved: {{ end }}{{ (index .Alerts 0).Annotations.summary }}'
          text: "{{ range .Alerts }}{{ .Annotations.description }}\n{{ end }}"
          send_resolved: false
    - name: states
      slack_configs:
        - api_url: {name: zeabur-notify-ops, key: url}
          title: '{{ if eq .Status "resolved" }}Resolved: {{ end }}{{ (index .Alerts 0).Annotations.summary }}'
          text: "{{ range .Alerts }}{{ .Annotations.description }}\n{{ end }}"
          send_resolved: true
```

以下几处需要按示例填写：

- 第一个 matcher 列出要接收的事件，最后要加上 `test`，才能收到 **发送测试** 发出的告警。项目可用的事件有 `build-failed`、`build-succeeded`、`deploy-failed`、`deploy-succeeded`、`crash-loop`、`out-of-memory`、`database-unhealthy`、`backup-failed`、`volume-almost-full`、`certificate`。集群的渠道可用 `node-not-ready`、`runtime-security`、`crash-loop`、`volume-almost-full`、`certificate`、`backup-failed`。
- 第二个 matcher 中的 `|ops` 让该渠道既接收常规告警，也接收指定发送给 `ops` 的测试告警。
- `events` 和 `states` 的接收配置相同，只有 `send_resolved` 不同。状态类告警恢复时会再次发送通知。

其他类型的 Secret 键和接收配置：

| 类型 | Secret 的键 | 接收配置 |
| --- | --- | --- |
| Discord | `url` | `discord_configs`，`webhook_url_secret` 指向 `url` |
| Telegram | `token` | `telegram_configs`，`bot_token` 指向 `token`，`chat_id` 填写数字 |
| 电子邮件 | `password`（填写后才有） | `email_configs`，`to`、`from`、`smarthost`、`require_tls: true`，`auth_username`、`auth_password` 为选填项 |
| Webhook | `url`，`token` 为选填项 | `webhook_configs`，`url_secret` 指向 `url`；使用令牌时添加 `http_config.authorization`（`type: Bearer`，`credentials` 指向 `token`） |
| ntfy | `url`，`token` 为选填项 | 同 Webhook。`url` 填写 `https://ntfy.sh/<主题>?template=alertmanager`，使用自建服务器时替换域名 |

发送测试会创建一个带有 `zeabur.com/notification-test: <名称>` 标签的 Job。指标组件的告警规则检测到它后，就会发送一条指定给该渠道的测试告警：

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: zeabur-notify-test-ops-1761456000
  namespace: shop
  labels:
    zeabur.com/notification-test: ops
spec:
  activeDeadlineSeconds: 120
  ttlSecondsAfterFinished: 300
  backoffLimit: 0
  template:
    metadata:
      labels:
        zeabur.com/notification-test: ops
    spec:
      restartPolicy: Never
      automountServiceAccountToken: false
      enableServiceLinks: false
      securityContext:
        runAsNonRoot: true
        runAsUser: 65535
        seccompProfile: {type: RuntimeDefault}
      containers:
        - name: wait
          image: registry.k8s.io/pause:3.10
          resources:
            requests: {cpu: 1m, memory: 4Mi}
            limits: {cpu: 10m, memory: 8Mi}
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: {drop: [ALL]}
```

移除渠道就是删除这两个对象：

```sh
kubectl -n shop delete vmalertmanagerconfig,secret zeabur-notify-ops
```

## 确认结果

- 渠道所在行不再显示 **等待中**，也没有 **被拒绝**。
- `kubectl -n shop get vmalertmanagerconfig zeabur-notify-ops -o jsonpath='{.status.updateStatus}'` 输出 `operational`。如果输出 `failed`，将路径改为 `{.status.reason}` 查看原因。
- 发送测试后一两分钟内，接收位置收到一条测试消息。

## 常见失败情况

- **等待中**：Alertmanager 尚未加载该渠道，稍后再查看。
- **被拒绝**：该行会显示原因，例如地址不完整、已保存的地址或令牌丢失、SMTP 服务器未填写端口。点击 **编辑**，修正后保存。
- 收不到测试：核对接收服务的地址和令牌。如果页面提示未安装 Zeabur 的告警规则，重新安装指标组件。
- 能添加渠道但无法测试：发送测试需要创建 Job 的权限，请管理员确认这项权限。
- **不是在 Zeabur 中创建的，请到原创建位置修改**：回到原来的 Helm 或 GitOps 配置中修改。

## 移除渠道

在渠道的操作菜单中选择 **移除**，确认要删除的渠道和机密变量后，点击 **移除渠道**。后续告警只会发送到其他已勾选该事件的渠道。

测试 Job 结束五分钟后，Kubernetes 会自动删除它，无需另行清理。
