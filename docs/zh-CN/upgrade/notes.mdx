这一页列出每一版不兼容的变更，以及升级前要先做的事。升级的步骤本身见[升级 Zeabur 开源版](steps.mdx)。

一次跨好几版升级时，从你当前的版本开始，依次看过到目标版本为止的每一节。新的版本写在最上面。

## v0.2 → v0.3

下面的步骤不用自己动手。粘贴[交给 Agent 升级](steps.mdx#交给-agent-升级)中的提示，Agent 就会按这一节替你升级。到了创建快照和登录的步骤，Agent 会停下来等你。

zeabur-installer 已经移除。一条 `helm install` 就能把 Zeabur 开源版装进现有的集群；全新的服务器先用 [Zeatend](../install/one-command.mdx) 装好 Kubernetes。

chart 现在会一起安装 Zeabur Identity 和 cert-manager，并启用 Ingress，用 ClusterIssuer `letsencrypt` 申请证书。要继续使用你自己部署的 Zeabur Identity，升级时加上 `--set identity.enabled=false`。要继续使用你自己创建的 TLS 机密变量，加上 `--set ingress.clusterIssuer=`。升级不会安装 cert-manager。

chart 现在自带 `zeabur-system-hosts` 准入策略。在没有标上 `zeabur.com/platform: "true"` 的命名空间里，新增或修改的 Ingress 规则都要写主机名，HTTPRoute 都要写 hostnames，而且不能用 Zeabur 开源版或 Zeabur Identity 的域名。已经存在的对象照常运行，直到改了 `spec` 为止。不想要这个策略，就设置 `systemHosts.enabled: false`。

Zeabur 开源版改为在安装 VictoriaMetrics 和 VictoriaLogs 时，自己写入告警规则，以及让 Zeabur Proxy 读取日志的网络规则。Catalog 的组件不再带这些内容，自定义资源的指标也改名为 `kube_customresource_*`。如果你用 Helm、Flux 或 Argo CD 安装 VictoriaMetrics，先从 Zeabur Catalog 升级，再用 `zeaburctl components export victoria-metrics victoria-logs` 输出 Zeabur 开源版的对象，应用每个组件最后面的那几个。如果旧的 `zeabur-notifications` VMRule 还在，通知页面又无法更新，先用 `kubectl -n observability delete vmrule zeabur-notifications` 删除，再到通知页面点击**安装规则**。

### 用 zeabur-installer 安装的集群

zeabur-installer v0.2 用 K3s 的 `HelmChart` 安装 Zeabur 开源版，再用普通 manifest 安装 Zeabur Identity、它的准入策略和登录客户端。v0.3 改用一个 Helm release 安装这些内容。下面的步骤会把安装程序创建的对象交给这个 release 管理，不会删除它们。项目、服务、数据库、域名、成员和通行密钥都保持不变，也不用重新注册账号。

这些内容不会改变：

- K3s、RKE2 或 KubeSolo，以及让 Kubernetes 接受 Zeabur Identity 令牌的文件。以后要升级 Kubernetes，用 Zeatend，见[用 zeabur-installer 安装的服务器](steps.mdx#用-zeabur-installer-安装的服务器)。
- 安装程序装好的组件，例如 Traefik、cert-manager、Zeabur Builder 和 CloudNativePG。Zeabur 开源版不会改动不是自己安装的组件，所以这些组件会保持当前版本。
- Zeabur Identity 的 Service 地址和签名密钥，账号和通行密钥照常可用，kube-apiserver 也继续接受 Zeabur Identity 的令牌。

升级后，不要再运行 `zeabur-installer apply`，否则会重新装回 v0.2 的 `HelmChart` 和 Zeabur Identity v0.1。

这些步骤适合交给 Claude Code 或 Codex 这类 Coding Agent 操作。遇到下面这些情况，Agent 要停下来，等待服务器所有者操作或确认：

- 做任何改动之前：所有者先检查新的 values 文件，再给每台服务器创建快照（第 3 步）。
- 第 1 步的检查发现这些步骤没有涵盖的情况。
- 升级之后：所有者用通行密钥登录（第 8 步）。
- 删除任何内容之前，包括第 9 步清理剩余对象时。

#### 1. 检查安装程序创建的内容

所有命令都在第一台服务器上用 root shell（`sudo -i`）运行。先让 `kubectl` 和 `helm` 连接到集群：

| 发行版 | 命令 |
| --- | --- |
| K3s | `export KUBECONFIG=/etc/rancher/k3s/k3s.yaml` |
| RKE2 | `export KUBECONFIG=/etc/rancher/rke2/rke2.yaml PATH=$PATH:/var/lib/rancher/rke2/bin` |
| KubeSolo | `export KUBECONFIG=/var/lib/kubesolo/pki/admin/admin.kubeconfig PATH=$PATH:/var/lib/zeabur-installer/bin` |

服务器还需要 Helm 4。下面的命令都在 `/root/zeabur-upgrade` 中运行：

```sh
umask 077
mkdir -p /root/zeabur-upgrade && cd /root/zeabur-upgrade
```

如果 `helm version --short` 的输出里没有 `v4`，就用下面这段安装 Helm 4。它从 get.helm.sh 下载，用同一个网站公布的校验值检查文件，再装到 `/usr/local/bin`。校验值和文件来自同一个网站，只能发现下载损坏，不能证明是谁构建的。

```sh
arch=$(uname -m | sed 's/x86_64/amd64/; s/aarch64/arm64/')
helm=$(curl -fsSL https://get.helm.sh/helm-latest-version)
curl -fsSLO "https://get.helm.sh/helm-$helm-linux-$arch.tar.gz" &&
  curl -fsSLO "https://get.helm.sh/helm-$helm-linux-$arch.tar.gz.sha256sum" &&
  sha256sum -c "helm-$helm-linux-$arch.tar.gz.sha256sum" &&
  tar -xzf "helm-$helm-linux-$arch.tar.gz" --strip-components=1 "linux-$arch/helm" &&
  install -m 0755 helm /usr/local/bin/helm &&
  helm version --short
```

`umask` 只在运行它的 shell 里有效。下面每段会写出文件的命令，开头都有 `umask 077` 和 `cd /root/zeabur-upgrade`，所以每段在新的 shell 里运行时，新建的文件也只有 root 能读写。

接着逐项检查。结果和右栏不符时，先停下来询问所有者。

| 命令 | 预期结果 |
| --- | --- |
| `kubectl -n kube-system get configmap zeabur-installer -o jsonpath='{.data.installer}'` | `0.2.0` 或其他 `0.2.x`。如果是 `0.1.x`，先完成 [v0.1 → v0.2](#v01--v02)。 |
| `kubectl -n kube-system get helmchart zeabur` | 一个 `HelmChart`。如果没有，说明安装程序运行时设置了 `zeabur: false`，没有安装 Zeabur 开源版：改为按[在现有集群安装 Zeabur 开源版](../install/existing-cluster.mdx)操作。 |
| `helm status zeabur -n zeabur` | `STATUS: deployed` |
| `kubectl -n zeabur-identity get deployment zeabur-identity -o jsonpath='{.spec.template.spec.containers[0].args}'` | 没有输出，或只有 `["--invitations"]`。其他选项是有人手动加的，Zeabur Identity v0.3 不再接受许多旧选项，见[它的升级须知](https://oss.zeabur.com/docs/identity/operations/upgrade)。 |
| `kubectl get crd upstreamproviders.identity.zeabur.com` | `NotFound`。如果存在，说明有人手动配置了 GitHub 或 Google 登录；先按 Zeabur Identity 的升级须知处理这些登录方式。 |

保存当前的 values 和安装程序的配置：

```sh
umask 077
cd /root/zeabur-upgrade
helm get values zeabur -n zeabur -o yaml > old-values.yaml
cp /etc/zeabur-installer/config.yaml installer-config.yaml
```

从这两个文件中记下：

- **访问模式**：`installer-config.yaml` 中的 `access.mode`。`domain` 表示为真实 DNS 域名申请 Let's Encrypt 证书。`local` 表示使用服务器上创建的 CA，ClusterIssuer 是 `zeabur-local-ca`。
- **邀请链接**：`access.invitations: false` 表示 Zeabur Identity 不接受邀请链接。没有这个键时，默认启用邀请。
- **Zeabur 开源版使用哪个 Zeabur Identity**：`old-values.yaml` 中的 `issuer.url`。如果是 `https://` 加上 `access.identity`，用的就是安装程序创建的 Zeabur Identity。如果是其他地址，说明有人让 Zeabur 开源版使用外部的 Zeabur Identity。继续之前先询问所有者，再按第 2 步中对应的说明编写 values。
- **项目自己的域名**：`kubectl get ingress,httproute,certificate -A > domains-before.txt`。再选一个项目域名，保存 `curl -sS -o /dev/null -w '%{http_code}\n' https://<domain>/` 的输出。local 模式要加上 `--cacert /var/lib/rancher/zeabur-installer/local-ca.crt`，KubeSolo 则用 `/var/lib/zeabur-installer/local-ca.crt`。升级不会改动这些对象。
- **数据库**：`kubectl get clusters.postgresql.cnpg.io,statefulsets -A > databases-before.txt`。升级不会改动这些对象。

#### 2. 编写新的 values 文件

根据 `old-values.yaml` 编写 `values.yaml`。不要用 `--reuse-values` 或 `--reset-then-reuse-values`：它们会保留安装程序设置的 `image`，让版本停在 v0.2。

按下表修改各个键。使用外部 Zeabur Identity 时有三点不同：设置 `identity.enabled: false`，原样保留 `issuer.url` 和 `issuer.clientSecret`，下表和表后列表要添加的其他 `identity` 键都不要添加。

| `old-values.yaml` 中的内容 | `values.yaml` 中的写法 |
| --- | --- |
| `image` | 不要保留，让 chart 使用自己的镜像。 |
| `issuer.url` | 原样移到 `identity.issuer`。 |
| `issuer.clientSecret` | 不要保留。chart 会创建 Secret `zeabur-client`，并把它的哈希值注册到 Zeabur Identity。 |
| `issuer.caBundle`（仅 local 模式） | 保留。 |
| `ingress.annotations` 中的 `cert-manager.io/cluster-issuer: <issuer>` | 去掉这条注解。把 `ingress.clusterIssuer` 和 `identity.ingress.clusterIssuer` 都设为 `<issuer>`。 |
| `ingress.className` | 保留，并把 `identity.ingress.className` 设为相同的值。 |
| 其他所有键，例如 `publicUrl`、`clusterName`、`planKey`、`domains`、`ingress.enabled`、`ingress.tls`、`builds`、`proxy`、`telemetry` 和 `updateCheck` | 原样保留。 |

再加上：

- `identity.admin.setupLink: false`。管理员已经存在，不需要 chart 创建新的设置链接。
- 只有 `access.invitations` 为 `false` 时，才加上 `identity.invitations: false`。

参考你所用模式的示例，换成自己的地址和名称。local 模式的服务器最后会类似下面这样：

```yaml
publicUrl: https://zeabur.203.0.113.10.sslip.io
clusterName: vps-1
identity:
  issuer: https://login.203.0.113.10.sslip.io
  admin:
    setupLink: false
  ingress:
    className: traefik
    clusterIssuer: zeabur-local-ca
issuer:
  caBundle:
    configMap: zeabur-identity-ca
planKey:
  existingSecret: zeabur-plan-key
ingress:
  className: traefik
  clusterIssuer: zeabur-local-ca
  tls:
    secretName: zeabur-tls
domains:
  clusterIssuer: zeabur-local-ca
  suffixes: [203-0-113-10.sslip.io]
builds:
  registry: zot.zot.svc:5000
  caBundle:
    configMap: zeabur-registry-ca
```

domain 模式要把 `ingress.clusterIssuer`、`identity.ingress.clusterIssuer` 和 `domains.clusterIssuer` 都设为 `letsencrypt`，也不要添加 `issuer.caBundle`。domain 模式的服务器最后会类似下面这样：

```yaml
publicUrl: https://zeabur.example.com
clusterName: vps-1
identity:
  issuer: https://login.example.com
  admin:
    setupLink: false
  ingress:
    className: traefik
    clusterIssuer: letsencrypt
planKey:
  existingSecret: zeabur-plan-key
ingress:
  className: traefik
  clusterIssuer: letsencrypt
  tls:
    secretName: zeabur-tls
domains:
  clusterIssuer: letsencrypt
  suffixes: [apps.example.com]
```

示例没列出的 key，例如 `builds`、`proxy`、`telemetry` 和 `updateCheck`，除非上面的表格要你改，否则按 `old-values.yaml` 原样保留。

#### 3. 备份并创建快照

保存这次升级要接管的对象，方便对比或还原：

```sh
umask 077
cd /root/zeabur-upgrade
kubectl get crd -o name | grep identity.zeabur.com | xargs kubectl get -o yaml > identity-crds.yaml
kubectl -n zeabur-identity get users,credentials,grants,invitations,oauthclients,secrets,configmaps,services -o yaml > identity.yaml
kubectl -n zeabur get secrets,configmaps -o yaml > zeabur.yaml
kubectl -n kube-system get helmchart zeabur -o yaml > helmchart.yaml
kubectl -n kube-system get configmap zeabur-installer zeabur-identity-authn --ignore-not-found -o yaml > installer-record.yaml
```

这些文件含有机密信息，例如 Zeabur Identity 的签名密钥。请留在服务器上。

**先停下来**。把 `values.yaml` 和第 1 步的检查结果交给所有者查看。请所有者给每台服务器创建快照，完成后再告诉你。需要退回旧版时，就还原这份快照。

#### 4. 让安装程序的 `HelmChart` 不再管理 release

K3s 的 helm-controller 通过 `HelmChart` `kube-system/zeabur` 管理 release。直接删除这个 `HelmChart` 会卸载 Zeabur 开源版。先告诉 helm-controller 不要再管理这个 release，然后再删除 `HelmChart`：

```sh
kubectl -n kube-system annotate helmchart zeabur helmcharts.helm.cattle.io/unmanaged=true
kubectl -n kube-system patch helmchart zeabur --type=json -p '[{"op":"remove","path":"/metadata/finalizers"}]'
kubectl -n kube-system delete helmchart zeabur
```

确认 release 和它的副本都还在，再继续：

```sh
helm status zeabur -n zeabur          # STATUS: deployed
kubectl -n zeabur get pods
```

#### 5. 更新 Zeabur Identity 的 CRD

Helm 只在首次安装时安装 chart 中的 CRD，不会升级它们。下载 chart，再自己应用新版 CRD。把 `<version>` 换成要升级到的版本；除非所有者指定了别的版本，就用 [GitHub Releases](https://github.com/zeabur-oss/zeabur/releases) 上最新的那一版：

```sh
helm pull oci://ghcr.io/zeabur-oss/charts/zeabur --version <version> --untar
kubectl apply --server-side --force-conflicts -f zeabur/charts/identity/crds/
```

安装程序应用旧 CRD 时用了自己的 field manager，所以这里需要 `--force-conflicts`。

#### 6. 升级

```sh
helm upgrade zeabur ./zeabur -n zeabur -f values.yaml \
  --take-ownership --force-conflicts --wait --timeout 10m
```

- `--take-ownership` 让 release 接管安装程序创建的 Zeabur Identity、登录客户端和准入策略。
- `--force-conflicts` 接管安装程序设置的字段。chart 没有设置的字段会保持不变，例如 Zeabur Identity 的 Secret 中的签名密钥。

如果命令失败，先读错误信息，修改 `values.yaml`，再运行同一条命令。失败的尝试会留下一条失败的修订版本记录，下次尝试会替换它。

#### 7. 检查集群

```sh
helm status zeabur -n zeabur                                   # STATUS: deployed
kubectl -n zeabur rollout status deployment/zeabur
kubectl -n zeabur-identity rollout status deployment/zeabur-identity
kubectl -n zeabur-identity get service zeabur-identity -o jsonpath='{.spec.clusterIP}'
```

地址必须和 `installer-record.yaml` 中 `discoveryURL` 的地址相同。如果变了，kube-apiserver 就无法连接 Zeabur Identity，所有人都会登录失败：先停下来询问所有者。

再确认其他内容都没变：

- `kubectl get ingress,httproute,certificate -A` 列出的名称和 `domains-before.txt` 相同，每个 Certificate 的 `READY` 都是 `True`。
- `kubectl get clusters.postgresql.cnpg.io,statefulsets -A` 列出的名称和 `databases-before.txt` 相同，并且都已就绪。
- 第 1 步的 `curl` 输出相同的状态码。
- `curl -sS <identity.issuer>/.well-known/openid-configuration` 返回 JSON，其中的 `issuer` 和升级前相同。

#### 8. 登录

**先停下来**。请所有者打开 Zeabur 开源版，用通行密钥登录，再打开一个项目，检查服务和数据库。通行密钥只能由本人使用。如果方便，也请一位成员登录检查。

Zeabur 开源版的副本已经换新，所有人都需要重新登录一次。

#### 9. 清理

Secret `zeabur/zeabur-oidc` 是安装程序创建的登录客户端密钥。使用外部 Zeabur Identity 时，`values.yaml` 还指向它，要保留。其他情况下 Zeabur 开源版不再读取它，征得所有者同意后再删除：

```sh
kubectl -n zeabur delete secret zeabur-oidc
```

先保留 `/root/zeabur-upgrade` 和快照，等一切正常运行几天后再清理。

## v0.1 → v0.2

用 zeabur-installer 安装的服务器，要先改配置文件、移除 v0.1 装的 zot，再运行 `plan` 和 `apply`。有后来加入的节点时，例如工作节点或 RKE2 的其他服务器，服务器升级完要让每个节点重新加入。

用 Helm、Argo CD 或 Flux 安装的，chart 的值没有不兼容的变更。只有自己在 Deployment 加过 v0.2 去掉的参数时，要先删掉，见下面的说明。

### 用 zeabur-installer 安装

下面的 `kubectl` 在服务器上运行。K3s 用 `sudo k3s kubectl`，RKE2 用 `sudo /var/lib/rancher/rke2/bin/kubectl --kubeconfig /etc/rancher/rke2/rke2.yaml`。

#### 1. 修改配置文件

编辑服务器的 `/etc/zeabur-installer/config.yaml`，改掉下面三种旧写法。

v0.2 没有 `preset`。默认会装组件目录建议的组件，再加上 Zeabur Builder、Keel 和 CloudNativePG。按你原来的 `preset` 调整：

| 原来 | 改成 |
| --- | --- |
| `standard`，或没写 | 删掉 `preset` 这一行就行 |
| `secure` | 删掉 `preset`，加上 `enable: [runtime-security, vulnerability-scanning, intrusion-prevention]` |
| `minimal` | 删掉 `preset`，运行 `plan` 看会新增哪些组件，把不要的加进 `disable` |

Zeabur Builder 是新加的默认组件，用来从 Git 构建。用不到的话，在 `disable` 加上 `builds`。

`inputs` 和 `secretFiles` 里的输入名称改成 camelCase，新版不会读旧名称。必填的输入用旧名称时，`plan` 会提示缺少这一项。选填的会被当成没写，改用默认值。用到下面这些组件时，把旧名称改成新的：

| 组件 | 旧名称 | 新名称 |
| --- | --- | --- |
| `builds/zeabur-builder` | `cluster-ip` | `clusterIp` |
| `intrusion-prevention/crowdsec` | `bouncer-key`、`lapi-secret`、`registration-token` | `bouncerKey`、`lapiSecret`、`registrationToken` |
| `remote-access/tailscale-operator` | `oauth-client-id`、`oauth-client-secret` | `oauthClientId`、`oauthClientSecret` |
| `volume-backup/velero` | `s3-url`、`repository-password`、`backup-key`、`file-backup` | `s3Url`、`repositoryPassword`、`backupKey`、`fileBackup` |

`enable` 或 `disable` 里有 `container-registry/zot` 时，把它删掉。zot 现在是 Zeabur Builder 的一部分。

#### 2. 移除 v0.1 装的 zot

v0.1 的默认组件里有独立的 zot。v0.2 不会把它换成 Zeabur Builder 的 zot，所以要先自己移除。先确认这台服务器有没有：

```sh
kubectl -n kube-system get helmchart zot \
  -o jsonpath='{.metadata.annotations.installer\.zeabur\.com/component}'
```

输出 `container-registry/zot` 才需要移除。输出 `builds/zeabur-builder`，或找不到 `zot`，就跳到下一步。

```sh
kubectl -n kube-system delete helmchart zot
kubectl -n zot get pods      # 等到没有任何 Pod
kubectl delete namespace zot
```

zot 存的镜像会一起删掉。之后 `apply` 会安装 Zeabur Builder 和它自己的 zot，构建时会重新推送镜像。

#### 3. 升级服务器

`profile` 是 `multi-node` 的话，先运行下面两条命令。v0.1 在 `multi-node` 给 VictoriaMetrics 20 GiB 的卷，v0.2 设定的是 5 GiB，但卷不能缩小，VictoriaMetrics operator 会因此停止更新 vmsingle。第一条命令让 operator 保留卷现在的大小，第二条让它重新处理 vmsingle：

```sh
kubectl -n observability annotate pvc vmsingle-vm-victoria-metrics-k8s-stack operator.victoriametrics.com/pvc-allow-volume-expansion=false
kubectl -n observability rollout restart deployment victoria-metrics-operator
```

下载 v0.2 的 installer，运行 `plan`，确认后再 `apply`。

`plan` 会列出这次新增的组件。System Upgrade Controller 不再是默认组件，`apply` 不会移除，只是不再更新，`plan` 会写成 `not removed, no longer updated`。installer 本来就固定了 K3s 和 RKE2 的版本，不需要 System Upgrade Controller。要保留，在 `enable` 加上 `node-updates/system-upgrade-controller`。不要的话，`apply` 完再删掉：

```sh
kubectl delete namespace system-upgrade
kubectl delete crd plans.upgrade.cattle.io
kubectl delete clusterrolebinding system-upgrade system-upgrade-drainer
kubectl delete clusterrole system-upgrade-controller system-upgrade-controller-drainer
```

第 2 步移除的 zot 也会在 `plan` 显示 `not removed, no longer updated`。这是因为安装记录里还有它，`apply` 之后就不会再出现。

v0.2 会给系统预留内存，避免 Pod 用光内存拖垮整台服务器，所以 `apply` 会重启 K3s 或 RKE2。Kubernetes API 约有 10 秒不响应，运行中的应用照常服务。预留的内存，会先从 Pod 能申请到的量扣掉，原本就快满的服务器，Pod 可能放不下，会一直停在 `Pending`。节点上的 Pod 已经申请的比剩下的多时，`plan` 会给出警告。请在 `apply` 前删除那个节点上的服务或减少副本、把服务移到其他节点，或者加一个节点。

#### 4. 让其他节点重新加入

后来加入的节点，配置文件里都有 `join`，包括工作节点，以及 RKE2 在第一台之后加入的服务器。没有这种节点的话，可以跳过这一步。

这些节点的配置文件里，v0.1 的 `join.zot` 在 v0.2 改成了 `join.registry`，zot 的地址也换了，所以要用新的配置重新加入：

1. 在升级好的服务器运行 `sudo zeabur-installer node add`。RKE2 后来加入的服务器要加上 `--role server`，才会保留服务器的角色。
2. 在每个节点换上 v0.2 的 installer，备份 `/etc/zeabur-installer/config.yaml`，再用 root 粘贴 `node add` 输出的内容。它会写入新的配置文件，再运行 `plan` 和 `apply`。
3. 节点都 `Ready` 后，有工作节点重新加入的话，在服务器运行 `sudo zeabur-installer node sync`，再按 `node add` 输出的最后一行撤销令牌。没有运行 `node sync` 的话，网络策略会拦住重新加入的节点。

`node add` 的选项和令牌怎么撤销，见[管理节点](../cluster/nodes.mdx)。

### 用 Helm、Argo CD 或 Flux 安装

Zeabur 开源版和 Zeabur Proxy 去掉了调整会话时长和 proxy 限制的参数，数值保持不变：空闲 1 小时或总共 12 小时后要重新登录。proxy 超时 30 秒、请求上限 16 MiB。chart 从来没有设置这些参数。你自己在 Deployment 的 `args` 或 `env` 加过的话，先删掉再升级：

- `zeabur`：`--session-idle-minutes`、`--session-max-hours`，或环境变量 `ZEABUR_SESSION_IDLE_MINUTES`、`ZEABUR_SESSION_MAX_HOURS`。
- `zeabur-proxy`：`--timeout`、`--max-bytes`、`--review-cache`、`--max-inflight`、`--max-inflight-per-person`，或环境变量 `ZEABUR_PROXY_TIMEOUT`、`ZEABUR_PROXY_MAX_BYTES`、`ZEABUR_PROXY_REVIEW_CACHE`、`ZEABUR_PROXY_MAX_INFLIGHT`、`ZEABUR_PROXY_MAX_INFLIGHT_PER_PERSON`。其他 `ZEABUR_PROXY_*` 环境变量照常使用，例如 TLS 证书和私钥。
