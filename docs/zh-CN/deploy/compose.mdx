在项目中选择**新建** → **Docker Compose**，粘贴 `compose.yaml`，点击**读取文件**。逐一确认服务、数据库替换和公开域名后，再**检查变更**并应用。导入后，每个服务都能单独编辑。Zeabur 不会保存或持续同步原来的 Compose 文件。

## 开始前

- 准备 Compose 文件，以及它使用的 `.env`、`env_file` 内容。Compose 文件大小上限为 256 KiB，包含 1 到 50 个服务。
- 每个要部署的服务都有已推送到 registry 的 `image`。只有 `build:` 的服务不会创建，改用[从 Git 部署](git.mdx)或先推送镜像。
- 已有项目和创建服务的权限。导入卷、机密变量、域名或 operator 管理的数据库时，还需要相应的创建权限。
- 要将 PostgreSQL、MongoDB、MySQL、MariaDB、Redis／Valkey 或 MinIO 替换为 operator 管理的服务，先安装相应[组件](../cluster/components.mdx)。

<Callout type="warn">
导入不会迁移 Docker 主机上的数据。选择 operator 管理的数据库或对象存储时，会创建空的存储空间。普通服务的命名卷也会创建新的 PVC。正式切换前，先单独迁移数据，并确认应用能读到。
</Callout>

## 读取并创建服务

<Steps>
<Step>

### 提供 Compose 和变量文件

打开**新建** → **Docker Compose**，在 **Compose 文件**中粘贴 YAML，或点击**上传文件**选择文件，然后点击**读取文件**。

如果文件中有 `${NAME}` 等插值，但没有对应的值，界面会要求提供 `.env` 内容。`env_file` 指向的文件也会分别显示输入框。粘贴或上传这些文件后，再点击**读取文件**。

缺失的插值会变成空字符串，未提供的 `env_file` 变量会跳过。先补齐这些值，避免程序使用空密码或空地址启动。同一个变量同时出现在 `env_file` 和 `environment` 中时，使用 `environment` 的值。

</Step>
<Step>

### 逐一选择数据库的运行方式

如果集群安装了对应的 operator，且你有创建权限，这些服务的**创建由 operator 管理的…**（后面接引擎名称）默认开启：

| Compose 镜像 | 创建的服务 |
| --- | --- |
| PostgreSQL | CloudNativePG 管理的 PostgreSQL |
| MongoDB | Percona Operator 管理的 MongoDB |
| MySQL | MOCO 管理的 MySQL |
| MariaDB | mariadb-operator 管理的 MariaDB |
| Redis、Valkey | Dragonfly Operator 管理的 Dragonfly |
| MinIO | SeaweedFS Operator 管理的对象存储 |

开启后，选项下方会逐项列出新服务与 Compose 服务的差异：版本、启动命令、端口、卷、账号密码变量和实例数。例如，卷这一行会显示新卷的大小，并提醒你新卷最初是空的。

![读取后的服务列表：db 开启由 operator 管理的 PostgreSQL，下方列出与原服务的差异；web 会等 db 可以连接后再启动](../images/shots/compose-services.avif)

要继续使用原来的镜像，关闭这个选项。如果有两个或更多服务可以替换，上方的 **N 个都替换为 operator 管理的服务**可以一次开启或关闭全部选项。缺少 operator、无法确认是否安装，或权限不足时，该服务会直接运行原镜像，界面会说明原因。

选择由 operator 管理后，其他服务中能识别的连接字符串、主机、用户、密码和数据库名称会改写为新服务的连接配置。无法改写的引用会保留原值，并提示你在导入后检查。

</Step>
<Step>

### 选择公开域名

Compose 的 `ports` 不会直接开放节点的主机端口。对于需要对外提供 HTTP 的普通服务，开启**公开域名**，确认建议的域名或自行填写。

例如，`"3000:3000"` 会保留容器的 TCP 端口 `3000`，但不会对外开放主机的 `3000` 端口。**公开域名**默认关闭，DNS 和 HTTPS 仍需按[公开域名](../configure/domains.mdx)配置。

</Step>
<Step>

### 检查并应用

阅读每个服务下方的挂载路径、等待的服务和跳过的字段，再点击**检查变更**。确认服务数量、机密变量、卷、数据库和域名。

导入的服务使用“兼容”安全性，因为大多数 Compose 镜像以 root 运行。

如果修改了 Compose 或变量文件的内容，需要重新**读取文件**才能检查新的结果。

</Step>
</Steps>

## 核对会更改或跳过的配置

| 原来的配置 | 导入后的行为与受影响场景 |
| --- | --- |
| `entrypoint`、`command` | 使用普通镜像的服务会保留容器命令和参数。替换为 operator 管理的服务后，由 operator 启动。例如，Redis 的 `redis-server --appendonly yes` 不会传给 Dragonfly。 |
| 数据服务的 `ports` | 替换为 operator 管理后，使用新服务的私有连接。MinIO 的 `9000` 和管理界面端口 `9001` 不会沿用，应用改为连接 SeaweedFS S3 端点。 |
| 命名卷 | 每个服务的每个挂载都会创建独立的 1 GiB 卷，不迁移原有数据。多个服务共享同名卷的关系也会拆开。后续能否扩容，取决于存储类。 |
| 主机路径、Docker socket | 不会挂载。原来通过主机目录提供的配置文件或数据，需要另行放入卷或配置文件。 |
| `depends_on` | 启动前等待依赖服务的 TCP 端口可以连接。对于无法识别端口的依赖服务，不会等待。 |
| `healthcheck` | 跳过原检查，改用第一个端口的 TCP 连接作为就绪检查，导入后可到**设置**调整。 |
| UDP 端口 | 跳过。导入时创建的 Kubernetes Service 仅支持 TCP。 |
| `privileged`、`cap_add`、`devices`、`network_mode: host`、`pid: host` | 跳过。需要主机设备或主机权限的应用，必须先处理这些依赖条件再部署。 |
| `build:` 同时有 `image` | 直接下载 `image`，跳过本地构建。 |
| 不符合命名规则的服务名称 | 转为小写字母、数字和连字符。检查仍使用旧名称的应用配置。 |
| 普通服务的明文变量 | 有创建机密变量的权限时，保存到 `<服务名称>-env` 机密变量中。例如，改写后的 `S3_ENDPOINT` 也可能出现在这里。 |

## 确认结果

回到项目，确认预期的服务都已出现。依次打开各服务的**概览**和**日志**。数据库和对象存储刚创建时，需要等待 operator 创建实例和连接机密变量。

到应用的**变量**中检查导入后的连接来源，再实际运行一次数据库读写或文件上传。网页能打开后，也要确认它读到的是迁移后的数据。

![项目页列出导入后的各个服务](../images/shots/project-services.avif)

使用 kubectl 确认时，普通服务的对象带有 `app.kubernetes.io/name: <服务名称>`；对于替换为 operator 管理的数据库，Zeabur 写入的数据库对象和机密变量带有 `zeabur.com/database: <名称>`。下面的 `db` 已替换为 PostgreSQL：

```sh
kubectl -n shop get deploy,svc,pvc,secret -l app.kubernetes.io/name=web
kubectl -n shop get clusters.postgresql.cnpg.io,secret -l zeabur.com/database=db
kubectl -n shop get deployment web -o jsonpath='{.spec.template.spec.initContainers[*].name}'
```

有 `depends_on` 的服务会多出 `wait-1`、`wait-2` 等初始化容器。它们用 `nc -z` 等待依赖服务的端口可以连接后才结束。

## 用 kubectl 做同样的事

将 Compose 文件转换为服务的步骤只在界面上执行，Zeabur 不保存 Compose 文件，集群中也没有对应的对象。转换结果是普通的 Kubernetes 对象，与手动创建的一样：

- 普通服务：与[部署容器镜像](./image.mdx#用-kubectl-完成相同操作)的 YAML 相同，安全性固定为**兼容**。
- 数据库和对象存储：与[数据库](./databases.mdx#用-kubectl-完成相同操作)、[对象存储](./object-storage.mdx#用-kubectl-完成相同操作)的 YAML 相同。

不使用界面时，可以参照上面两页自行编写 YAML，或用 [Kompose](https://kompose.io/) 转换后再修改。Zeabur 的转换规则参考了 Kompose，但名称、标签和安全性配置不同，两者的输出不会完全相同。

## 常见失败与清理

- 名称已存在：这个流程只创建对象。回到 Compose 修改服务名称并重新读取，或改用其他项目。
- 某个服务没有创建：检查它是否只有 `build:`。为它指定可下载的镜像，或单独从 Git 部署。
- 应用无法连接新数据库：检查无法改写的引用、改名后的主机和实际变量名称。可以在数据库的**连接**中使用**连接到服务**，详见[数据库](databases.mdx)。
- 原来共享的文件不见了：导入的卷相互独立。检查原 Compose 是否通过多个服务共享同一个卷，重新安排存储方式并迁移文件。
- 只创建了部分对象：Zeabur 按顺序创建对象，如果中途失败，已创建的对象会留在集群中。根据界面列出的结果补建或删除。

要清理这次导入，逐一使用服务的**删除服务**、数据库的**删除数据库**和对象存储的**删除对象存储**，并检查各自的删除列表。Zeabur 没有保存 Compose 文件，因此没有一次删除整次导入的按钮。

<Callout type="warn">
删除列表中的卷、数据库或存储桶时，可能会连同数据一起删除。先导出或复制需要保留的数据，再应用删除操作。
</Callout>
