打开服务的**设置** → **定时任务**，点击**添加定时任务**，填写命令、cron 表达式和时区，再点击**检查变更**。每次运行都会启动新容器，原服务继续运行。

## 开始前

- 项目内已有持续运行的服务，例如 Deployment。定时任务会复制它的容器配置，因此不能从 Job 或 CronJob 创建。
- 有修改服务和创建 CronJob 的权限。手动运行还需要创建 Job 的权限。
- 源镜像包含 `/bin/sh` 和要运行的程序。任务命令通过 `/bin/sh -c` 运行。

## 创建定时任务

<Steps>
<Step>

### 选择命令和源容器

打开应用服务，进入**设置** → **定时任务**，点击**添加定时任务**。

在**命令**中填写镜像内可运行的命令，例如应用已有的 `npm run cleanup`。工作目录沿用源容器的配置。命令所需的程序和文件都必须存在于镜像或挂载的卷中。

如果服务有多个普通容器，在**要复制的容器**中选择包含命令的容器。每个定时任务只复制其中一个，源服务的其他容器不会一起启动。

</Step>
<Step>

### 填写 cron 表达式和时区

在**定时**中填写五个字段，依次为“分、时、日、月、星期”。例如：

| 定时 | 指定时区中的运行时间 |
| --- | --- |
| `0 3 * * *` | 每天 03:00 |
| `*/15 * * * *` | 每 15 分钟 |
| `0 9 * * 1-5` | 每周一至周五 09:00 |
| `0 3 * * 0` | 每周日 03:00 |

**时区**默认填入浏览器的时区，创建时写入 CronJob 的 `spec.timeZone`。例如，要在台湾时间每天凌晨 03:00 运行，填写 `0 3 * * *`，并确认**时区**为 `Asia/Taipei`。要使用 UTC，填写 `Etc/UTC`。

![新增定时任务的表单，命令为 npm run cleanup，定时表达式 0 3 * * * 下方显示换算结果：Asia/Taipei 每天 03:00](../images/shots/cron-job-form.avif)

清空**时区**时，CronJob 不会设置 `spec.timeZone`，运行时间改用 kube-controller-manager 的时区，通常是 UTC，界面也按 UTC 显示这类定时任务。

</Step>
<Step>

### 选择重叠和保留方式

确认**名称**：最多 52 个字符，只能使用小写字母、数字和连字符，开头和结尾必须是字母或数字。

在**上一次还在运行时**中选择：

| 选项 | 到达下一个定时时间时的处理方式 |
| --- | --- |
| **跳过这次** | 上一次尚未结束时，不启动本次任务。这是默认选项。 |
| **两次同时运行** | 允许多个任务同时运行。 |
| **停止上一次，改运行这次** | 停止尚未完成的任务，启动新任务。 |

设置**保留的成功记录**和**保留的失败记录**，范围为 0 到 100。默认保留 3 次成功记录、1 次失败记录。设为 0 次时，任务完成后也会清除任务记录。

</Step>
<Step>

### 检查并应用

点击**检查变更**，核对源服务、容器、镜像、命令、定时表达式、时区和重叠策略，再应用。创建定时任务不会重启原服务。

任务创建后，可以从源服务的**定时任务**列表打开，也可以在项目服务列表中找到它。

</Step>
</Steps>

## 立即运行并查看结果

打开定时任务的**概览**，在**运行记录**中点击**立即运行**，检查变更后应用。这会新增一个 Job，不改变定时时间。手动运行的记录会标注**手动运行**。

**立即运行**也会遵循**上一次还在运行时**的配置：

- **跳过这次**：上一次仍在运行时，按钮不可用，将鼠标指针悬停在按钮上可查看原因。
- **停止上一次，改运行这次**：检查页面会列出将先停止的运行记录。
- **两次同时运行**：直接再创建一个 Job。

在**运行记录**中等待**成功**或**失败**。如果有读取日志的权限，且该次运行的副本仍然存在，点击该行的**日志**查看输出。再到应用中确认结果，例如报表是否已生成。

## 源服务更新后，定时任务使用哪个版本

创建时会复制源容器的镜像、环境变量配置、工作目录、资源、安全配置和卷挂载，也会保留运行身份、镜像拉取凭证和节点放置配置。端口和健康检查不会复制。

此后，即使源服务更换镜像，定时任务仍使用创建时复制的镜像。要同时更新任务，打开定时任务的**设置**，切换到 **YAML**，点击**编辑**，更新 `spec.jobTemplate.spec.template.spec.containers` 中相应容器的 `image`，再点击**检查变更**。

环境变量的明文值也是创建时的副本。对机密变量或配置文件的引用则仍指向原对象，每次启动新容器时读取当时的值。修改共享对象时，也要将定时任务纳入影响范围。

<Callout type="warn">
卷挂载会指向同一个 PVC，不会为定时任务复制数据。源服务和任务可能同时修改同一份文件。只能挂载到单个节点的卷，也可能导致定时任务一直等待挂载。先确认存储空间和命令能接受这种共享方式。
</Callout>

## 修改或暂停定时任务

打开定时任务的**设置** → **定时**，修改**定时**、**时区**、**命令**、**上一次还在运行时**、**保留的成功记录**或**保留的失败记录**，再点击**检查变更**并应用。新配置从下一次运行开始生效，正在运行的任务会继续。只有通过**添加定时任务**创建的任务才有**命令**字段。

要暂停自动定时运行，在**概览**的**运行记录**旁点击**暂停**，检查后应用。暂停后仍可使用**立即运行**。要恢复，点击同一位置的**恢复**。

## 确认结果

定时任务创建后，**运行记录**会列出每次运行，并标注**成功**或**失败**。用 kubectl 查看：

```sh
kubectl -n shop get cronjob nightly-report
kubectl -n shop get jobs -l app.kubernetes.io/name=nightly-report
kubectl -n shop logs job/<Job 名称>
```

CronJob 的 `SCHEDULE` 和 `TIMEZONE` 是你填写的值，暂停时 `SUSPEND` 为 `True`，`LAST SCHEDULE` 表示距上次运行的时间。每次运行对应一个 Job，`STATUS` 为 `Complete` 表示成功，为 `Failed` 表示失败。手动运行的 Job 名称为 `<定时任务名称>-manual-<时间>`。

## 用 kubectl 完成相同操作

定时任务就是一个 CronJob。下面的 YAML 等同于从服务 `web` 创建 `nightly-report`，每天台湾时间 03:00 运行 `npm run report`：

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-report
  labels:
    app.kubernetes.io/name: nightly-report
    zeabur.com/task-of: web
spec:
  schedule: "0 3 * * *"
  timeZone: Asia/Taipei
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      template:
        metadata:
          labels:
            app.kubernetes.io/name: nightly-report
        spec:
          securityContext:
            runAsNonRoot: true
            seccompProfile:
              type: RuntimeDefault
          restartPolicy: Never
          containers:
            - name: web
              image: ghcr.io/acme/web:1.4
              command: ["/bin/sh", "-c", "npm run report"]
              envFrom:
                - secretRef:
                    name: web-env
              resources:
                requests:
                  cpu: 100m
                  memory: 128Mi
                limits:
                  memory: 256Mi
              securityContext:
                allowPrivilegeEscalation: false
                capabilities:
                  drop: [ALL]
```

- 标签 `zeabur.com/task-of` 的值是源服务的名称，界面据此将任务列在源服务的**定时任务**中。如果源服务有 `zeabur.com/group` 标签，也会一并复制。
- 容器的 `image`、`env`、`envFrom`、`workingDir`、`imagePullPolicy`、`resources`、`securityContext`、`volumeMounts` 从源容器复制，Pod 的 `serviceAccountName`、`securityContext`、`imagePullSecrets`、`nodeSelector`、`affinity`、`tolerations` 从源 Pod 复制。如果挂载了卷，也会复制用到的 `volumes`。
- 命令统一写成 `["/bin/sh", "-c", "<命令>"]`。
- `concurrencyPolicy` 的 `Forbid`、`Allow`、`Replace` 依次对应**跳过这次**、**两次同时运行**、**停止上一次，改运行这次**。

其他操作：

| 界面操作 | kubectl |
| --- | --- |
| **立即运行** | `kubectl -n shop create job --from=cronjob/nightly-report nightly-report-manual-$(date +%s)` |
| **暂停** | `kubectl -n shop patch cronjob nightly-report -p '{"spec":{"suspend":true}}'` |
| **恢复** | `kubectl -n shop patch cronjob nightly-report -p '{"spec":{"suspend":false}}'` |
| 删除 | `kubectl -n shop delete cronjob nightly-report` |

Zeabur 的**立即运行**与 `kubectl create job --from` 一样，Job 带有注解 `cronjob.kubernetes.io/instantiate: manual`，所有者是 CronJob。

## 常见失败

| 情况 | 处理方式 |
| --- | --- |
| 找不到**定时任务** | 从持续运行的服务的**设置**中打开。Job 和 CronJob 不提供创建另一个定时任务的区域。 |
| 创建时拒绝 cron 表达式或时区 | 检查五个字段的格式和时区名称，根据集群返回的字段错误原因修正。 |
| 提示找不到 `/bin/sh` 或命令 | 改用包含 shell 和所需程序的镜像，并确认命令路径、工作目录和用户权限。 |
| 创建时提示每个副本各有卷 | 源服务使用的卷来自 StatefulSet 的卷模板，无法直接复制为任务挂载，先为定时任务安排可用的存储方式。 |
| 任务一直等待启动 | 检查**部署记录**中的事件、可用资源和卷挂载，确认没有因源服务占用而产生的限制。 |
| 未在预期时间运行 | 到**设置** → **定时**检查定时表达式和时区，确认运行记录旁未显示**已暂停**，并检查上一次任务是否仍在运行。 |
| 看不到旧日志 | 检查成功和失败记录的保留数量。已完成的 Job 和副本清除后，页面无法再读取该副本的日志。 |

## 删除定时任务

在定时任务右上角点击**更多** → **删除服务**，检查删除列表后应用。删除 CronJob 后，它拥有的运行记录和副本也会一并清除，源服务仍会保留。

如果只想停止自动运行，点击**暂停**即可，无需删除。
