在服务的**网络**标签页中，找到域名所在行，打开**维护与错误页面**，开启**维护模式**，添加变更后检查并应用。访问该域名的访客会看到维护页面和 HTTP 503，原服务仍继续运行。维护完成后，在同一位置关闭维护模式，流量就会回到原后端。

## 开始前

- 服务有[公开域名](./domains.mdx)。Ingress 和 HTTPRoute 提供的域名都能开启维护模式。
- 有修改路由的权限。如果项目还没有[页面服务器](#页面服务器)，还需要创建 Deployment、Service、ConfigMap 和 NetworkPolicy 的权限。
- 自定义错误页面需要 Traefik 提供的 Ingress。HTTPRoute 和其他 Ingress controller 的域名可以开启维护模式，但面板中没有**显示错误页面**。

维护模式只改变当前域名的转发目标，服务本身继续运行。同一服务的其他域名、私有地址和对外端口仍能访问应用，定时任务也照常运行。

<Callout type="warn">
如果维护是为了迁移数据或修改表结构，需要另外停止会通过私有网络、其他域名或定时任务写入数据的程序，例如将 worker 的副本数设为 0。
</Callout>

## 开启维护模式

<Steps>
<Step>

### 选择要维护的域名

进入服务的**网络**标签页，在目标域名所在行点击 **app.example.com 的维护与错误页面**。

![服务的网络标签页，域名行上的维护与错误页面按钮](../images/shots/domain-pages-open.avif)

</Step>
<Step>

### 设置访客看到的页面

开启**维护模式**。保留默认 HTML，或在**要编辑的页面**中选择**维护**，修改 **HTML**。

![shop.example.com 的维护与错误页面面板，已开启维护模式并显示维护页面的 HTML](../images/shots/domain-pages-maintenance.avif)

每个页面必须小于 64 KiB。项目中的所有域名共用同一组页面，因此在这里修改维护页面后，项目中其他处于维护状态的域名也会显示新内容。

如果项目还没有页面服务器，面板顶部会显示**这个项目还没有页面服务器**。继续操作即可，检查变更时会同时将 Zeabur Catalog 的 **Error pages** 模板部署到项目，并写入维护、502、503、504 四份默认页面。如果只修改维护页面，其他三份页面会保留默认内容。

</Step>
<Step>

### 检查并应用

在侧边面板点击**加入变更**，域名行会标记为**已修改**。再点击页面底部的**检查变更**，确认目标域名和 HTML，然后应用。如果需要部署页面服务器，列表中也会列出它的 Deployment、Service、ConfigMap 和 NetworkPolicy。

![检查变更窗口，说明 shop.example.com 将改为显示维护页面](../images/shots/domain-pages-review.avif)

该域名下的所有路径都会转到维护页面，同一 Ingress 的其他域名不受影响。对于 Ingress 域名，会新增一个名称以 `-maintenance` 结尾的 Ingress，Traefik 优先使用它，原 Ingress 保持不变。对于 HTTPRoute 域名，会将原后端的权重改为 0，再添加页面服务器。HTTPRoute 的维护模式作用于整条路由；如果同一条 HTTPRoute 还有其他域名，会先将当前域名移到单独的路由。

</Step>
<Step>

### 从访客端确认

打开目标域名的首页和一个原本可用的子路径，确认都显示维护页面。也可以在自己的终端中检查响应：

```sh
curl -i https://app.example.com/
```

将 `app.example.com` 替换为自己的域名。响应状态码应为 `503`，内容应为维护页面的 HTML。回到服务的**网络**标签页，域名行会标记为**维护中**，服务副本仍在运行。

![域名行中的 shop.example.com 标记为维护中](../images/shots/domain-maintenance-on.avif)

</Step>
</Steps>

如果 Ingress 域名设置了[重定向或密码](./domains.mdx)，维护期间两者都不生效，访客无需输入密码就会直接看到维护页面。维护页面只包含你编写的 HTML，不会经过应用。如果 HTTPRoute 域名正在重定向，则无法开启维护模式，需要在目标域名开启，或先取消重定向。

## 维护完成后恢复流量

1. 确认应用已准备好接收流量，所需的[环境变量](./variables.mdx)和[卷](./volumes.mdx)都正确。
2. 回到同一域名的**维护与错误页面**，关闭**维护模式**。
3. 在面板中点击**加入变更**，再点击页面底部的**检查变更**，确认域名会转回原服务，然后应用。
4. 重新打开域名和子路径，确认应用正常响应，域名行不再显示**维护中**。

关闭维护模式时，对于 Ingress 域名，会删除对应的 `-maintenance` Ingress；对于 HTTPRoute 域名，会移除页面服务器，并将权重为 0 的后端改回 1。原有规则始终保留在对象上，即使维护期间修改过规则，也会照常还原。删除原 Ingress 时，Kubernetes 会同时删除它的维护 Ingress。

## 显示自定义错误页面

在 Traefik Ingress 域名的**维护与错误页面**中开启**显示错误页面**，再分别选择以下页面修改 **HTML**：

| 页面 | 提供内容的文件 |
| --- | --- |
| **502 网关错误** | `502.html` |
| **503 服务不可用** | `503.html` |
| **504 网关超时** | `504.html` |

点击面板中的**加入变更**，再从页面底部检查并应用。之后服务返回 502、503 或 504 时，Traefik 会改为返回项目的错误页面。要查看实际效果，可以使用会返回这些状态码的测试服务，无需停止生产服务。

这个开关作用于整个 Ingress，面板会列出同时受影响的其他域名。页面 HTML 则由整个项目共用。在 `app.example.com` 修改 502 页面后，其他开启错误页面的域名也会显示新内容。

同一 Ingress 中有域名处于维护状态时，其他域名仍会显示自定义的 502、503 和 504 页面。

HTML 保存在 ConfigMap 中，页面服务器每次收到请求都会读取挂载的文件。修改 HTML 后，等 kubelet 下次同步并更新挂载文件就会生效，无需重启。

## 页面服务器

维护页面和错误页面由项目中的页面服务器提供，它来自 Zeabur Catalog 的 **Error pages** 模板：一个小型 nginx，HTML 保存在 ConfigMap `error-pages` 中。Zeabur 根据标签 `zeabur.com/page-server: "true"` 查找页面服务器，不依赖名称：

| 对象 | 必需内容 |
| --- | --- |
| Service | 带有此标签，端口 `pages` 按文件名提供页面，端口 `maintenance` 对每个请求返回维护页面和 503 |
| ConfigMap | 带有此标签，键为 `502.html`、`503.html`、`504.html` 和 `maintenance.html` |

每个项目只能有一个带此标签的 Service。也可以自行用 `kubectl` 部署这个模板，或改用符合上表要求的其他服务器，Zeabur 都能识别。这些都是普通的 Kubernetes 对象，不使用 Zeabur 也能照常运行。

## 用 kubectl 完成相同操作

维护模式和错误页面只用到 Ingress、HTTPRoute、Traefik Middleware 和页面服务器，移除 Zeabur 后仍能运行。以下以项目 `demo`、Ingress `web-app-example-com`、域名 `app.example.com` 为例，假设项目已有页面服务器 `error-pages`。

### 开启维护模式（Ingress）

新增一个 Ingress，名称为 `<服务>-<域名，点换成连字符>-maintenance`，将同一域名的所有路径转发到页面服务器的 `maintenance` 端口。`router.priority` 必须高于该域名的所有其他路由，Traefik 才会优先使用它。`ownerReferences` 指向原 Ingress，Zeabur 通过它识别维护用的 Ingress，因此先查询原 Ingress 的 `uid`：

```sh
kubectl -n demo get ingress web-app-example-com -o jsonpath='{.metadata.uid}'
```

将查到的值填入 `uid`：

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-app-example-com-maintenance
  namespace: demo
  annotations:
    traefik.ingress.kubernetes.io/router.priority: "1000"
  ownerReferences:
    - apiVersion: networking.k8s.io/v1
      kind: Ingress
      name: web-app-example-com
      uid: 0b8f9a52-5d6e-4c1a-9f3e-2a7b1c4d5e6f
spec:
  ingressClassName: traefik
  tls:
    - hosts: [app.example.com]
      secretName: web-app-example-com-tls
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: error-pages
                port:
                  name: maintenance
```

Zeabur 创建的版本还会：

- 将 `router.priority` 设为该域名现有路由的最高优先级加 1。如果没有指定优先级，Traefik 会使用规则长度作为优先级，因此这个数值通常不大。上面的 `1000` 只需高于原路由即可。
- 复制原 Ingress 的 `traefik.ingress.kubernetes.io/router.*` annotation（`router.middlewares` 和 `router.priority` 除外）、`ingressClassName` 和该域名的 `tls`。

有了 `ownerReferences`，删除原 Ingress 时，Kubernetes 会同时删除维护用的 Ingress。

关闭维护模式只需删除这个 Ingress：

```sh
kubectl -n demo delete ingress web-app-example-com-maintenance
```

### 开启维护模式（HTTPRoute）

HTTPRoute 不会另外创建对象。Zeabur 会将每条规则中原后端的 `weight` 改为 `0`，再添加页面服务器的 `maintenance` 端口，权重设为 `1`。用 `kubectl edit httproute <名称>` 按以下方式修改，例如：

```yaml
rules:
  - backendRefs:
      - name: web
        port: 8080
        weight: 0
      - name: error-pages
        port: 8081
        weight: 1
```

将 `8081` 替换为页面服务器 Service 上 `maintenance` 端口的端口号。恢复时，将 `web` 的权重改回 `1`，并移除 `error-pages` 项。

### 显示错误页面

错误页面通过 Middleware `<Ingress 名称>-error-pages` 提供，`ownerReferences` 指向 Ingress。Traefik 遇到 502 到 504 的响应时，会改为向页面服务器的 `pages` 端口请求 `/<状态码>.html`：

```yaml
apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata:
  name: web-app-example-com-error-pages
  namespace: demo
spec:
  errors:
    status: ["502-504"]
    service:
      name: error-pages
      port: 8080
    query: /{status}.html
```

将 `8080` 替换为页面服务器 Service 上 `pages` 端口的端口号。再将它添加到 Ingress 的 `traefik.ingress.kubernetes.io/router.middlewares`，写为 `demo-web-app-example-com-error-pages@kubernetescrd`。如果已有其他 Middleware，用 `kubectl edit` 将它加入列表，重定向仍需排在第一位。

要修改页面内容，直接编辑 ConfigMap `error-pages`：

```sh
kubectl -n demo edit configmap error-pages
```

## 确认结果

在服务的**网络**标签页中，处于维护状态的域名行会标记为**维护中**。面板中**维护模式**和**显示错误页面**的开关会反映集群中的配置，通过 kubectl 开启的也一样。

用 kubectl 确认对象，再从集群外查看响应：

```sh
kubectl -n demo get ingress
kubectl -n demo get middleware.traefik.io
kubectl -n demo get svc,configmap -l zeabur.com/page-server=true
curl -sI https://app.example.com/
```

维护期间，`kubectl get ingress` 会多出一个以 `-maintenance` 结尾的 Ingress，`curl` 返回的状态码为 `503`。关闭维护模式后，这个 Ingress 会消失，`curl` 会收到服务原本的响应。

## 遇到问题

| 界面或结果 | 处理方法 |
| --- | --- |
| 无法点击维护与错误页面按钮 | 确认你有修改路由的权限，且路由未标记为由其他工具管理。 |
| 应用变更后仍看到应用 | 确认打开的网址对应已切换到维护模式的域名，并检查前面是否有 CDN 或代理缓存。回到**网络**，查看域名行是否显示**维护中**。 |
| 维护页面本身无法打开 | 查看项目中 `error-pages` 的副本和事件，并确认 NetworkPolicy `error-pages` 允许集群的 Ingress controller 连接。 |
| 检查变更提示项目有多个页面服务器 | 只保留一个带 `zeabur.com/page-server` 标签的 Service，移除其他 Service 的该标签。 |
| 页面仍是旧的 HTML | 等挂载文件更新后再刷新。 |
| HTTPRoute 域名无法开启维护模式，提示路由按权重分流 | 路由的后端权重不全为 1。用 kubectl 将流量切到页面服务器，或先将权重改回 1。 |
| 没有**显示错误页面** | 域名并非由 Traefik 提供，需要使用对应 Ingress controller 自身的错误页面配置。 |

## 停用并清理页面服务器

关闭**维护模式**会让域名转回原服务。关闭**显示错误页面**会移除该 Ingress 的错误页面规则。页面服务器和 HTML 都会保留，以后可以直接复用。

整个项目都不再需要这些页面时，先关闭每个域名的维护模式和错误页面，确认流量都已恢复，再到项目的**对象**页面删除 `error-pages` 的 Deployment、Service 和 NetworkPolicy，以及 ConfigMap `error-pages` 和 `error-pages-nginx`。对每个对象，在 **YAML** 中点击**删除**，检查后应用。

<Callout type="warn">
如果仍有域名处于维护状态或开启了错误页面，此时删除页面服务器，这些域名的访客会直接看到错误，无法看到你设置的页面。
</Callout>
