服务运行缓慢、内存不足，或需要让故障副本自动重启时，到服务 **设置** 调整 **计算资源** 和 **健康检查**，修改后点击页面底部的 **检查变更**，再应用变更。**安全性** 决定容器能否以 root 运行，选择后会直接打开检查页面。

## 开始前

- 有权限修改这个服务。如果服务由 Helm、Argo CD 或 Flux 管理，这些字段无法编辑，需要回到原来的 values 或 Git 仓库修改。
- 除副本数外，其他配置都写在 Pod template 上，修改后会替换副本。只有一个副本的服务在替换时可能中断几秒。

## 计算资源

<Steps>
<Step>

### 调整副本数

到服务 **设置** → **计算资源**，修改 **副本数**（0 到 1000）。副本数为 0 时，服务停止，但不会删除任何配置或数据。

</Step>
<Step>

### 调整 CPU 和内存

填写 **CPU 预留量**、**CPU 上限**、**内存预留量** 和 **内存上限**，例如 CPU 预留 0.25 核、内存预留 256 MiB、上限 512 MiB。

- 预留量：节点为每个副本预留的资源量，调度时也按这个数值选择节点。留空时不预留。
- 上限：内存超过上限时，容器会重启；CPU 超过上限时会限速。留空时不设上限。

字段下方会显示集群中 **最大的节点** 有多少 CPU 核心和内存。如果预留量超过该节点的资源，副本将无法调度到任何节点。

从镜像或 Git 创建服务时选择的 **规格**，就是这几个字段的初始值：

| 规格 | CPU 预留量 | 内存预留量 | 内存上限 |
| --- | --- | --- | --- |
| 小 | 0.1 核 | 128 MiB | 256 MiB |
| 中 | 0.25 核 | 256 MiB | 512 MiB |
| 大 | 0.5 核 | 512 MiB | 1 GiB |

![服务设置中的计算资源，包括副本数、CPU 和内存的预留量与上限，下方显示最大节点的资源](../images/shots/service-compute.avif)

</Step>
<Step>

### 检查并应用

点击页面底部的 **检查变更**。检查页面会显示副本数的变化、各个服务是否会中断，以及节点的可用资源是否足够。确认后应用变更。

</Step>
</Steps>

Job 只运行一次，不能通过 **计算资源** 修改，需要使用 YAML。

**计算资源** 下方还有 **配置文件或机密变量变更时自动重启**，用法见[让运行中的服务读取新值](./variables.mdx#让正在运行的服务读到新值)。这个开关写在工作负载本身，不会替换副本。

## 健康检查

到服务 **设置** → **健康检查**，分别配置三种检查：

| 检查 | 用途 |
| --- | --- |
| **就绪检查** | 只有通过检查的副本才会接收流量。 |
| **存活检查** | 容器持续未通过检查时，集群会重启它。 |
| **启动检查** | 应用启动前，暂缓其他检查。 |

每种检查都可以在 **检查方式** 中选择 **不检查**、**HTTP GET**、**TCP** 或 **命令**：

- **HTTP GET**：填写 **路径** 和 **端口**，例如 `/healthz` 和 `8080`。响应状态码为 200 到 399 时算通过。
- **TCP**：填写 **端口**，能建立连接就算通过。
- **命令**：填写要在容器内运行的 **命令**，退出码为 0 时算通过。

**间隔（秒）** 表示多久检查一次，**失败次数** 表示连续失败几次才判定为失败。如果服务声明了端口，表单会显示 **HTTP，端口 8080** 这类按钮，点击即可填入路径 `/` 和对应端口。端口必须是容器声明过的，否则无法保存。

![服务设置中的健康检查，就绪检查选择 HTTP GET，路径为 /healthz，另有存活检查和启动检查](../images/shots/service-health.avif)

修改后，点击页面底部的 **检查变更**，再应用变更。只有定时任务和 Job 没有健康检查。

<Callout type="warn">
存活检查失败会重启容器。如果应用启动很慢，先配置启动检查，或提高存活检查的失败次数，否则集群可能在应用启动完成前反复重启容器。
</Callout>

## 启动命令

Zeabur 没有启动命令字段。要修改容器启动时运行的命令，到服务 **设置**，将顶部的切换项从 **设置** 切换到 **YAML**，点击 **编辑**，修改容器的 `command`（替换镜像的 `ENTRYPOINT`）和 `args`（替换 `CMD`），再检查并应用：

```yaml
containers:
  - name: web
    image: nginxinc/nginx-unprivileged:1.29
    command: ["nginx"]
    args: ["-g", "daemon off;"]
```

## 安全性

到服务 **设置** → **安全性**，选择容器可以执行哪些操作：

- **严格**：以非 root 用户运行，且无法提升权限。以 root 运行的镜像（例如 `nginx:latest`）无法启动，需要改用不需要 root 的版本，例如 `nginxinc/nginx-unprivileged`。Railpack 构建的镜像以用户 1000 运行，可以选择严格。Dockerfile 需要用数字指定非 root 用户，例如 `USER 1000`。
- **兼容**：允许以 root 运行，但仍无法访问宿主机或提升权限。

![服务设置中的安全性，当前选择兼容，下方说明允许以 root 运行但无法访问宿主机](../images/shots/service-security.avif)

选择后会直接打开检查页面，确认并应用后，副本会替换为新的副本。从镜像创建服务时，Zeabur 会根据镜像配置的用户预先选择：用数字指定非 root 用户时选择严格，其他情况选择兼容。

如果服务的配置超出兼容范围（例如访问宿主机），这里会显示 **不受限**，需要使用 YAML 修改。项目的 Pod Security 级别为 `restricted` 时，只有严格的服务才能启动，见[调整 Pod Security 级别](./projects.mdx#调整-pod-security-级别)。

## 用 kubectl 做同样的事

这些配置都是 Deployment 或 StatefulSet 的标准字段，移除 Zeabur 后仍然生效。以下以项目 `demo`、服务 `web` 为例。

副本数和资源：

```sh
kubectl -n demo scale deployment/web --replicas=2
kubectl -n demo set resources deployment/web -c web --requests=cpu=250m,memory=256Mi --limits=memory=512Mi
```

`set resources` 只修改命令中列出的项目，未列出的会保留，例如原有的 `cpu` 上限。

健康检查、启动命令和安全性都写在 Pod template 上：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: demo
  labels:
    app.kubernetes.io/name: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: web
  template:
    metadata:
      labels:
        app.kubernetes.io/name: web
    spec:
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: web
          image: nginxinc/nginx-unprivileged:1.29
          command: ["nginx"]
          args: ["-g", "daemon off;"]
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              memory: 512Mi
          readinessProbe:
            httpGet:
              path: /
              port: 8080
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 8080
            periodSeconds: 10
            failureThreshold: 3
          startupProbe:
            httpGet:
              path: /
              port: 8080
            failureThreshold: 30
            periodSeconds: 2
          securityContext:
            allowPrivilegeEscalation: false
            capabilities:
              drop: [ALL]
```

上面是 **严格** 的写法。**兼容** 需要移除 Pod 的 `runAsNonRoot: true` 和容器的 `capabilities.drop: [ALL]`，保留 `seccompProfile` 和 `allowPrivilegeEscalation: false`。

## 确认结果

**计算资源** 和 **健康检查** 显示集群中的当前值，**安全性** 标明当前选择的是严格还是兼容。**概览** 会显示副本是否就绪，**用量** 会绘出预留量和上限，旁边显示实际用量。

```sh
kubectl -n demo get deployment web
kubectl -n demo get deployment web -o jsonpath='{.spec.template.spec.containers[0].resources}'
kubectl -n demo describe pod -l app.kubernetes.io/name=web
```

`get deployment` 的 `READY` 是 `2/2` 这样的数值，前后相同表示所有副本都通过了就绪检查。`describe pod` 会列出 `Readiness`、`Liveness` 和 `Startup` 的配置；检查失败时，`Events` 中会出现 `Unhealthy`。

## 遇到问题

| 界面或结果 | 处理方法 |
| --- | --- |
| 修改资源后，副本一直等待调度 | 预留量超过了每个节点的剩余资源。降低预留量，或增加节点。 |
| 副本反复重启，事件显示 `OOMKilled` | 内存用量超过上限，提高 **内存上限**。 |
| 副本反复重启，事件显示 `Liveness probe failed` | 确认存活检查的路径和端口，或添加启动检查，给应用更多启动时间。 |
| 副本一直未就绪 | 就绪检查未通过。查看 **日志**，确认应用在检查的端口上响应。 |
| 改为严格后，副本无法启动，事件显示 `container has runAsNonRoot and image will run as root` | 镜像以 root 运行。改回兼容，或换用以非 root 用户运行的镜像。 |
