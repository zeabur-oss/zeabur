Kubernetes is open-source software that runs containers on one or more servers, and Zeabur OSS runs on top of it. Helm is Kubernetes' package installer; the commands below use it to install and upgrade Zeabur OSS. Coming from Zeabur and want to know what is different first? See [Coming from Zeabur](../get-started/from-zeabur-com.mdx).

## Before you begin

- **A Kubernetes cluster**, version 1.30 or later, and a kubeconfig that can manage it. A kubeconfig is the file `kubectl` uses to reach a cluster.
- **An Ingress controller** that is the cluster's default IngressClass, such as the Traefik that K3s and RKE2 include. Ports 80 and 443 must be open to the internet, so that Let's Encrypt can check the addresses and issue their certificates.
- **Tools on your computer**: `kubectl`, Helm 4, and `zeabur-identityctl`.
- **The version to install.** The examples use `<version>`. The chart is published at `oci://ghcr.io/zeabur-oss/charts/zeabur`, and its default image is pinned to the digest of the same version. See [Release files and verification](../reference/releases.mdx) for the versions and how to verify them.

Kubernetes must be 1.30 or later because, by default, the chart creates project member roles and uses `ValidatingAdmissionPolicy` to limit which namespace fields Developers can change. That API is generally available starting in 1.30. A namespace is how Kubernetes groups things, and each Zeabur OSS project is one namespace.

## Install Zeabur OSS

<Steps>
<Step>

### Choose the domain

Zeabur OSS opens at `zeabur.<domain>`, and Zeabur Identity, which handles sign-in, at `identity.<domain>`. With no domain of your own, use `<IP>.sslip.io`, where `<IP>` is the server's public IP address. sslip.io is a public DNS service that answers each such name with the IP address in it, so there is no DNS record to add:

```sh
DOMAIN=203.0.113.10.sslip.io
```

To use your own domain, such as `example.com`, point `zeabur.example.com` and `identity.example.com`, or `*.example.com`, at the Ingress controller, and set `DOMAIN=example.com`.

</Step>
<Step>

### Let the cluster trust sign-in

Zeabur OSS acts on the cluster with each person's own sign-in token, so kube-apiserver must accept the tokens Zeabur Identity issues. On K3s, this prints the configuration and where to put it:

```sh
zeabur-identityctl kube-config --issuer "https://identity.$DOMAIN" --distro k3s --discovery public
```

On RKE2, use `--distro rke2`. Follow the printed steps on each server node. The cluster starts accepting tokens once Zeabur Identity is up in the next step.

</Step>
<Step>

### Install with Helm

Replace `<version>` with the version to install:

```sh
helm install zeabur oci://ghcr.io/zeabur-oss/charts/zeabur \
  --version <version> \
  --namespace zeabur --create-namespace \
  --set global.domain="$DOMAIN"
```

This one command does all of the following:

- Installs Zeabur OSS in the `zeabur` namespace, and Zeabur Identity in `zeabur-identity`.
- Registers Zeabur OSS in Zeabur Identity and stores the client secret in the cluster. The value stays out of Helm's release records.
- Installs cert-manager from Zeabur Catalog, the same way **Cluster** → **Components** does, with the ClusterIssuer `letsencrypt`. Helm waits for this, which takes a few minutes.
- Adds the ClusterRoles and namespace admission policy for project members. The chart doesn't give the member roles to anyone. After signing in, an admin sets each person's access on **Members**.

When `helm install` finishes, it prints the link that creates the first admin account. Keep it: the link works once and expires in 24 hours.

</Step>
<Step>

### Create the admin account

Open the link from the previous step and create a passkey. The certificates can take a minute after the install. If the browser warns about the certificate, wait and reload.

When the passkey is saved, the page links to Zeabur OSS. Open it and sign in with the passkey. An admin account has full rights over the cluster, with nothing more to set up in Zeabur OSS.

If the link has expired, `helm install` printed the command that issues another.

</Step>
<Step>

### Find your applications

Go to **Projects**. The applications already in the cluster are under **Other namespaces**.

![Other namespaces on the Projects page lists namespaces in the cluster that aren't projects yet](../images/shots/existing-namespaces.avif)

To keep one listed as a project, select **Use this namespace**, then review and apply. This only adds a project label. The services and data inside don't move.

</Step>
</Steps>

Next, [invite members](../cluster/members.mdx) or [deploy your first service](../get-started/first-project.mdx). The install added cert-manager. For other components, see [View and install cluster components](../cluster/components.mdx). For admin accounts, session limits, and the sign-in options on **Settings**, see [Permissions](../reference/permissions.mdx#admin-accounts-and-regular-accounts).

## Give new services a public URL

With an sslip.io domain, new services already get a public URL with HTTPS. When you deploy `web` in the `shop` project, the form suggests `web-shop.203.0.113.10.sslip.io`.

With your own domain, choose an application domain, such as `apps.example.com`, and point the DNS record for `*.apps.example.com` at the Ingress controller's address. Then update the same release:

```sh
helm upgrade zeabur oci://ghcr.io/zeabur-oss/charts/zeabur \
  --version <version> \
  --namespace zeabur --reset-then-reuse-values \
  --set 'domains.suffixes={apps.example.com}'
```

With `--reset-then-reuse-values`, Helm starts from the new chart's defaults, including the image, then applies the values you set. With `--reuse-values`, Helm also keeps the old chart's defaults, and the image stays on the old version.

You can list multiple application domains separated by commas; the first is the default. You can also change them later in the **Domains** section of the **Cluster** page, which checks DNS records and lists the records to add. See [Set up DNS records](../configure/dns.mdx). If `domains.suffixes` is empty and the domain is your own, enter the full domain by hand. New services' certificates come from the ClusterIssuer in `domains.clusterIssuer`, `letsencrypt` by default.

## If something goes wrong

| What you see | What to check |
| --- | --- |
| The browser can't open Zeabur OSS | Check that `kubectl -n zeabur rollout status deployment/zeabur` succeeds, then check DNS, the Ingress class, and that ports 80 and 443 are open. |
| The browser warns about the certificate for minutes | Run `kubectl get certificate -A`. A certificate that stays not ready usually means Let's Encrypt can't reach port 80, or the IP address in an sslip.io domain isn't the public one. |
| `helm install` says the `zeabur-components` job failed | Zeabur OSS is installed, but cert-manager isn't. `kubectl -n zeabur logs job/zeabur-components` shows why. Fix that, then run the commands that `zeaburctl components export cert-manager --format helm` prints. |
| The cluster already has cert-manager | The install leaves it as it is. Make sure it has a ClusterIssuer named `letsencrypt`, or set `ingress.clusterIssuer`, `identity.ingress.clusterIssuer` and `domains.clusterIssuer` to yours. |
| Every page says you are not signed in to the cluster | kube-apiserver doesn't accept the tokens yet. Check the steps of [Let the cluster trust sign-in](#let-the-cluster-trust-sign-in). |
| You can sign in but see no services | Zeabur OSS reads the cluster with the signed-in person's own rights. An admin gives them project roles on [Members](../cluster/members.mdx). |
| Reads are denied after sign-in | Check the member's identity and groups in Zeabur Identity, then the namespace's RoleBinding. See [Permissions](../reference/permissions.mdx). |
| A new service is ready, but its URL doesn't open | Check the application domain's DNS and certificate. Zeabur OSS and your services use different domains, set up separately. |
| You have to sign in again after an upgrade | The chart runs one Zeabur OSS replica, and sessions live in memory. A new replica means signing in again. |

Zeabur OSS's own ServiceAccount can only use kubectl terminal replicas in `zeabur-terminals`. It doesn't read the cluster on behalf of the signed-in person.

## Trust a private CA

If Zeabur Identity, a registry, object storage, or GitHub Enterprise uses a certificate signed by a private CA, or the cluster connects through a proxy that inspects TLS, put the CA certificates in a ConfigMap in Zeabur OSS's namespace and set `extraTrustedCA.configMap`:

```sh
kubectl -n zeabur create configmap corp-ca --from-file=ca.crt=corp-ca.pem
helm upgrade zeabur oci://ghcr.io/zeabur-oss/charts/zeabur \
  --version <version> \
  --namespace zeabur --reset-then-reuse-values \
  --set extraTrustedCA.configMap=corp-ca
```

If the certificates are in a secret, set `extraTrustedCA.secret` instead. Use only one of these settings. The key is `ca.crt` by default; change it with `extraTrustedCA.key`. The file may hold several certificates.

Zeabur OSS trusts these certificates in addition to the built-in Mozilla CA bundle when signing in to Identity, reading images, reading backups from object storage, and connecting to GitHub. Zeabur OSS reads the file when it starts, so after you change the config file, run `kubectl -n zeabur rollout restart deployment/zeabur`.

## Send outbound traffic through a proxy

If the cluster can only reach the internet through a proxy, turn on `outboundProxy`. Zeabur OSS then sends the requests it makes itself through that proxy, which are reading images from registries, reading backups from object storage, and connecting to GitHub.

```sh
helm upgrade zeabur oci://ghcr.io/zeabur-oss/charts/zeabur \
  --version <version> \
  --namespace zeabur --reset-then-reuse-values \
  --set outboundProxy.enabled=true \
  --set outboundProxy.httpsProxy=http://proxy.corp.example:3128
```

Set `outboundProxy.httpsProxy` for HTTPS destinations, `outboundProxy.httpProxy` for HTTP ones, or both. The address must start with `http://`. Zeabur OSS reaches an HTTPS destination through the proxy with a `CONNECT` tunnel. If the proxy needs a user name and password, write them in the address (`http://user:password@proxy.corp.example:3128`).

Some destinations never go through the proxy.

- Local addresses, such as `localhost` and `127.0.0.1`.
- Names ending in `.svc` or `.cluster.local`, and the cluster's pod and Service ranges. They default to `10.42.0.0/16` and `10.43.0.0/16`, the k3s and RKE2 defaults. If your cluster uses other ranges, set `outboundProxy.clusterNetwork`.
- Anything you add to `outboundProxy.noProxy`, as domain suffixes (`.corp.example`), addresses, or CIDR ranges.

Zeabur OSS still refuses the same targets as without a proxy. A registry or backup address that points to this machine, a link-local address, or a cloud metadata address is refused even when the proxy could reach it. Zeabur OSS checks the address itself and asks the proxy to connect to that address, so the proxy's DNS answer cannot send the request somewhere else. The proxy's own address can be on a private network.

This setting does not change Zeabur Proxy (`proxy.*`), which serves logs and metrics. Signing in with Identity and requests to the Kubernetes API don't use the proxy. If the proxy inspects TLS, also trust its CA. See [Trust a private CA](#trust-a-private-ca).

## Manage the chart with GitOps

Zeabur OSS uses a key to sign reviewed changes, and a client secret to sign people in through Zeabur Identity. The chart creates both on the first install and reads them back on subsequent `helm upgrade` runs. Argo CD and `helm template` generate manifests without connecting to the cluster, so they create new ones each time. A new key invalidates changes you reviewed but haven't applied yet, and a new client secret stops sign-in until Zeabur OSS restarts. For these tools, create both first:

```sh
kubectl -n zeabur create secret generic zeabur-plan-key \
  --from-literal=plan-key="$(openssl rand -hex 32)"
CLIENT_SECRET="$(openssl rand -hex 32)"
kubectl -n zeabur create secret generic zeabur-client \
  --from-literal=client-secret="$CLIENT_SECRET"
printf 'sha256:%s\n' "$(printf %s "$CLIENT_SECRET" | openssl dgst -sha256 -r | cut -d' ' -f1)"
```

Set `planKey.existingSecret` to `zeabur-plan-key`, `issuer.clientSecret.existingSecret` to `zeabur-client`, and `issuer.clientSecret.hash` to the last line the commands print. These tools can't read the server's IP address either, so set `global.domain`. To view all chart settings, run `helm show values oci://ghcr.io/zeabur-oss/charts/zeabur --version <version>`.
