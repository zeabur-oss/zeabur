This page is the manual install. [Let an agent install it](agent.mdx) and [Zeatend's one-command install](one-command.mdx) are still in development.

This page installs Zeabur by hand with Helm, for cluster admins who want to see every object Zeabur adds. Kubernetes is open-source software that runs containers on one or more servers, and Zeabur runs on top of it. Helm is Kubernetes' package installer; the commands below use it to install and upgrade Zeabur. Coming from zeabur.com and want to know what is different first? See [Coming from zeabur.com](../get-started/from-zeabur-com.mdx).

## Before you begin

Have these ready. Most are things a cluster administrator already has:

- **A Kubernetes cluster**, version 1.30 or later, and a kubeconfig that can manage it. A kubeconfig is the file `kubectl` uses to reach a cluster.
- **Tools on your computer**: `kubectl`, Helm 4, and `zeabur-identityctl`.
- **Zeabur Identity**, which handles sign-in to Zeabur. Sign-in must work over HTTPS, and the cluster must already trust the sign-in tokens it issues. See [Zeabur Identity's get started guide](https://oss.zeabur.com/docs/identity/get-started).
- **An address and HTTPS certificate for Zeabur**: a domain such as `zeabur.example.com`, an Ingress controller in the cluster that routes the address to Zeabur, such as Traefik, and a certificate for the domain, such as a TLS secret named `zeabur-tls`.
- **The version to install.** The examples use `<version>`. The chart is published at `oci://ghcr.io/zeabur-oss/charts/zeabur`, and its default image is pinned to the digest of the same version. See [Release artifacts](../reference/releases.mdx) to download and verify it.

Kubernetes must be 1.30 or later because, by default, the chart creates project member roles and uses `ValidatingAdmissionPolicy` to limit which namespace fields Developers can change. That API is generally available starting in 1.30. A namespace is how Kubernetes groups things, and each Zeabur project is one namespace.

Zeabur's own address and the addresses of services you deploy later are set up separately. Get sign-in to Zeabur working first, then set up addresses for services.

## Install Zeabur

<Steps>
<Step>

### Register Zeabur in Zeabur Identity

This lets Zeabur Identity know Zeabur, so sign-in returns to Zeabur. The example uses `https://identity.example.com` as Zeabur Identity's address. Replace both domains with yours, and run this with the cluster admin's kubeconfig:

```sh
zeabur-identityctl client create zeabur \
  --type confidential \
  --audience kubernetes \
  --display-name Zeabur \
  --redirect-uri https://zeabur.example.com/auth/callback \
  --home-url https://zeabur.example.com/ \
  | kubectl apply -f -
```

The command prints the client secret once, on stderr. Zeabur uses it to prove who it is to Zeabur Identity. You need it in the next step.

</Step>
<Step>

### Store the client secret in the cluster

Create the `zeabur` namespace, then read the client secret in Bash:

```bash
kubectl create namespace zeabur
read -rs CLIENT_SECRET
printf %s "$CLIENT_SECRET" | kubectl -n zeabur create secret generic zeabur-oidc \
  --from-file=client-secret=/dev/stdin
unset CLIENT_SECRET
```

After running `read`, paste the client secret and press Enter. Keeping the value out of command arguments stops other users on the machine from seeing it in the process list. The chart records only the secret's name, so the value stays out of Helm's release records.

</Step>
<Step>

### Install with Helm

Make sure `zeabur-tls` is in the `zeabur` namespace, then run:

```sh
helm install zeabur oci://ghcr.io/zeabur-oss/charts/zeabur \
  --version <version> \
  --namespace zeabur \
  --set clusterName=production \
  --set publicUrl=https://zeabur.example.com \
  --set issuer.url=https://identity.example.com \
  --set issuer.clientSecret.existingSecret=zeabur-oidc \
  --set ingress.enabled=true \
  --set ingress.className=traefik \
  --set ingress.tls.secretName=zeabur-tls
kubectl -n zeabur rollout status deployment/zeabur
```

- `clusterName` is the cluster name shown in the interface.
- The domain in `publicUrl` must match the callback domain from the first step. The chart refuses an address that uses HTTP or includes a path.

When `rollout status` reports success, Zeabur is installed. The install adds Zeabur's Deployment, Service, Ingress, configuration, and the key that signs changes, along with the ClusterRoles and namespace admission policy for project members. The chart doesn't give the member roles to anyone. After signing in, an admin sets each person's access on **Members**.

</Step>
<Step>

### Sign in and find your applications

Open `https://zeabur.example.com` and sign in with a passkey. An admin account has full rights over the cluster, with nothing more to set up in Zeabur.

Go to **Projects**. The applications already in the cluster are under **Other namespaces**.

![Other namespaces on the Projects page lists namespaces in the cluster that aren't projects yet](../images/shots/existing-namespaces.avif)

To keep one listed as a project, select **Use this namespace**, then review and apply. This only adds a project label. The services and data inside don't move.

</Step>
</Steps>

Next, [invite members](../cluster/members.mdx) or [deploy your first service](../get-started/first-project.mdx). For admin accounts, session limits, and the sign-in options on **Settings**, see [Permissions](../reference/permissions.mdx#admin-accounts-and-regular-accounts).

## Give new services a public URL


Prepare an application domain, such as `apps.example.com`. Point the DNS record for `*.apps.example.com` at the Ingress controller's address, and prepare a cert-manager ClusterIssuer that can issue certificates, such as `letsencrypt`. Update the same release:

```sh
helm upgrade zeabur oci://ghcr.io/zeabur-oss/charts/zeabur \
  --version <version> \
  --namespace zeabur --reset-then-reuse-values \
  --set 'domains.suffixes={apps.example.com}' \
  --set domains.clusterIssuer=letsencrypt
```

With `--reset-then-reuse-values`, Helm starts from the new chart's defaults, including the image, then applies the values you set. With `--reuse-values`, Helm also keeps the old chart's defaults, and the image stays on the old version.

When you deploy `web` in the `shop` project, the form suggests `web-shop.apps.example.com`. You can list multiple application domains separated by commas; the first is the default. You can also change them later in the **Domains** section of the **Cluster** page, which checks DNS records and lists the records to add. See [Set up DNS records](../configure/dns.mdx). If `domains.suffixes` is empty, enter the full domain by hand. If `domains.clusterIssuer` is empty, new services' public URLs use HTTP.

These settings only name the issuer services should use. Prepare the ClusterIssuer and DNS first; Zeabur doesn't create them from these two values.

## If something goes wrong

| What you see | What to check |
| --- | --- |
| The browser can't open Zeabur | Check that `kubectl -n zeabur rollout status deployment/zeabur` succeeds, then check public DNS, the Ingress class, the TLS secret, and connectivity to the entry point. |
| Sign-in doesn't return to Zeabur | Check `publicUrl`, the `/auth/callback` registered in Zeabur Identity, and `issuer.url`. |
| Zeabur Identity uses a private CA | Set `extraTrustedCA` so Zeabur trusts the CA that signed Zeabur Identity's certificate. See [Trust a private CA](#trust-a-private-ca). |
| You can sign in but see no services | Zeabur reads the cluster with the signed-in person's own rights. An admin gives them project roles on [Members](../cluster/members.mdx). |
| Reads are denied after sign-in | Check the member's identity and groups in Zeabur Identity, then the namespace's RoleBinding. See [Permissions](../reference/permissions.mdx). |
| A new service is ready, but its URL doesn't open | Check the application domain's DNS and certificate. Zeabur and your services use different domains, set up separately. |
| You have to sign in again after an upgrade | The chart runs one Zeabur replica, and sessions live in memory. A new replica means signing in again. |

Zeabur's own ServiceAccount can only use kubectl terminal replicas in `zeabur-terminals`. It doesn't read the cluster on behalf of the signed-in person.

## Trust a private CA

If Zeabur Identity, a registry, object storage, or GitHub Enterprise uses a certificate signed by a private CA, or the cluster connects through a proxy that inspects TLS, put the CA certificates in a ConfigMap in Zeabur's namespace and set `extraTrustedCA.configMap`:

```sh
kubectl -n zeabur create configmap corp-ca --from-file=ca.crt=corp-ca.pem
helm upgrade zeabur oci://ghcr.io/zeabur-oss/charts/zeabur \
  --version <version> \
  --namespace zeabur --reset-then-reuse-values \
  --set extraTrustedCA.configMap=corp-ca
```

If the certificates are in a secret, set `extraTrustedCA.secret` instead. Use only one of these settings. The key is `ca.crt` by default; change it with `extraTrustedCA.key`. The file may hold several certificates.

Zeabur trusts these certificates in addition to the built-in Mozilla CA bundle when signing in to Identity, reading images, reading backups from object storage, and connecting to GitHub. Zeabur reads the file when it starts, so after you change the config file, run `kubectl -n zeabur rollout restart deployment/zeabur`.

## Send outbound traffic through a proxy

If the cluster can only reach the internet through a proxy, turn on `outboundProxy`. Zeabur then sends the requests it makes itself through that proxy, which are reading images from registries, reading backups from object storage, and connecting to GitHub.

```sh
helm upgrade zeabur oci://ghcr.io/zeabur-oss/charts/zeabur \
  --version <version> \
  --namespace zeabur --reset-then-reuse-values \
  --set outboundProxy.enabled=true \
  --set outboundProxy.httpsProxy=http://proxy.corp.example:3128
```

Set `outboundProxy.httpsProxy` for HTTPS destinations, `outboundProxy.httpProxy` for HTTP ones, or both. The address must start with `http://`. Zeabur reaches an HTTPS destination through the proxy with a `CONNECT` tunnel. If the proxy needs a user name and password, write them in the address (`http://user:password@proxy.corp.example:3128`).

Some destinations never go through the proxy.

- Local addresses, such as `localhost` and `127.0.0.1`.
- Names ending in `.svc` or `.cluster.local`, and the cluster's pod and Service ranges. They default to `10.42.0.0/16` and `10.43.0.0/16`, the k3s and RKE2 defaults. If your cluster uses other ranges, set `outboundProxy.clusterNetwork`.
- Anything you add to `outboundProxy.noProxy`, as domain suffixes (`.corp.example`), addresses, or CIDR ranges.

Zeabur still refuses the same targets as without a proxy. A registry or backup address that points to this machine, a link-local address, or a cloud metadata address is refused even when the proxy could reach it. Zeabur checks the address itself and asks the proxy to connect to that address, so the proxy's DNS answer cannot send the request somewhere else. The proxy's own address can be on a private network.

This setting does not change Zeabur Proxy (`proxy.*`), which serves logs and metrics. Signing in with Identity and requests to the Kubernetes API don't use the proxy. If the proxy inspects TLS, also trust its CA. See [Trust a private CA](#trust-a-private-ca).

## Manage the chart with GitOps

Zeabur uses a key to sign reviewed changes. The chart creates that key on the first install and reads it back on subsequent `helm upgrade` runs. Argo CD and `helm template` generate manifests without connecting to the cluster, so they generate a new key each time, and the new key invalidates changes you reviewed but haven't applied yet. For these tools, create a fixed key first, then set `planKey.existingSecret`:

```sh
kubectl -n zeabur create secret generic zeabur-plan-key \
  --from-literal=plan-key="$(openssl rand -hex 32)"
```

Set `planKey.existingSecret` to `zeabur-plan-key`. To view all chart settings, run `helm show values oci://ghcr.io/zeabur-oss/charts/zeabur --version <version>`.

## Install the components Zeabur needs

On K3s and RKE2, a cluster administrator installs components from **Cluster** → **Components**. See [Install from the page](../cluster/components.mdx#install-from-the-page). Zeabur downloads the list of components from Zeabur Catalog; for a cluster without internet access, see [Use a mirror](../cluster/components.mdx#use-a-mirror).

On other clusters, or to keep components in a GitOps repository, use [`zeaburctl components export`](../reference/zeaburctl.mdx#components-export) to print a component's manifests, then apply them with `kubectl` or commit them:

```sh
zeaburctl components export cert-manager --format flux > cert-manager.yaml
```

The default `helmchart` format is for the built-in helm-controller of K3s and RKE2. For other clusters, use `helm`, `flux`, or `argocd`.

## Remove the management interface

```sh
helm uninstall zeabur --namespace zeabur
```

Applications and the components that provide ingress, certificates, and storage stay in place. The member roles the chart created are removed with the release, so give members their rights another way. See [Remove Zeabur](../leave/uninstall.mdx) for the full list of what stays and the steps to migrate sign-in.
